# 第 6 章 生成循环

> 状态：初稿。本章的代码已在第 5 章的 8 层随机小模型上通过全部对拍，并在目标机器上用 Qwen3.8-27B 的真实权重通过了验收，见“在真实权重上验证”一节。

## 要解决的问题

第 5 章的引擎已经能说话了，但说得很慢，也很死板：

1. **慢。** 每生成一个 token，都把整个序列从头算一遍。第 5 章从 3 个 token 生成 8 个，8 次前向一共算了 52 个 token，726 秒。序列越长越糟：生成第 k 个 token 要算 n + k 个 token，生成 m 个的总量随 m 平方增长。
2. **死板。** 每次都选分数最高的 token（贪心解码），同一个问题永远是同一个回答，而且容易陷进重复。官方的 `generation_config.json`（第 3 章）建议的是按概率随机挑：温度 1.0，top-k 20，top-p 0.95。
3. **不会停。** 第 5 章生成固定个数，不认识结束符。模型说完一句话会输出 `<|im_end|>`，引擎应该在那里停下。

这一章把这三件事做完：缓存、采样、停止条件。做完以后，引擎第一次能按对话模板（第 2 章）回答一个问题，并在回答完的地方自己停下。

前言里这一章的验收标准是“带缓存与不带缓存的输出一致”。我们把它定得更严：

**一、带缓存与不带缓存逐位相同。** 同样的参数和种子，带缓存、不带缓存（第 5 章的做法）、提示词分成几块交给模型，生成工具的输出逐字节相同；每一步的 logits，与对整段序列做一次不带缓存的前向（第 5 章已经与官方对拍过）得到的对应那一行逐位相同。

**二、采样分两层对拍。** 第一层：标准库 Python 独立实现随机数、温度、top-k、top-p 和停止条件，要求每一步的随机数完全相同、保留的 token 完全相同、概率的相对误差不超过 10⁻⁹、选中的 token 相同、在同一个地方停下。第二层：官方 transformers 的 logits 处理器作用在 C 的 logits 上，结果与 C 的分布相同；小模型上再让官方的 `generate` 照着 C 的选择走一遍，官方算出的分布与 C 相同，并且停在同一个地方。

第二条怎么定，是本章要说清楚的事，见“和谁比”一节。

## 几个新概念

**缓存（KV 缓存）。** 第 5 章说过，模型是因果的：第 t 个位置的结果只取决于第 0 到 t 个 token。所以生成下一个 token 时，前面那些 token 的中间结果和上一步算的完全一样，没必要重算，存起来就行。全注意力层要存的是每个 token 的 k 和 v（下一节解释为什么只要这两个），所以叫 KV 缓存。

**状态。** 线性注意力层（第 4 章）不需要每个 token 的 k 和 v，它把看过的所有 token 压进一个固定大小的状态矩阵 S。对它来说，“缓存”就是 S 本身，外加因果卷积要往前看的最近 3 个 token。这类“只带着一个固定大小的状态往前走”的网络叫循环网络，状态也常叫“循环状态”。

**预填充和解码。** 有了缓存，生成分成两个阶段：先把整个提示词一次交给模型，把缓存填好，同时得到第一个生成 token 的 logits，这叫预填充（prefill）；之后每一步只把刚生成的那一个 token 交给模型，这叫解码（decode）。

**温度。** 把 logits 除以一个正数 T 再做 softmax（第 3 章）。T < 1 时分数之间的差距被放大，分布更“尖”，更像贪心；T > 1 时更“平”，更随机；T = 1 不改变分布。

**top-k 和 top-p。** 两种“只在靠前的几个里挑”的办法。top-k 只保留分数最高的 k 个 token；top-p（又叫 nucleus 采样）从概率最高的开始往下数，保留到累计概率达到 p 为止。两者都是为了不让模型偶尔挑中一个概率很小、多半是胡言乱语的 token。

**随机数生成器和种子。** 程序里的随机数其实是一个确定的数列：从一个初始值（种子）出发，按固定的公式一个接一个算出来，看起来没有规律而已。种子相同，数列就相同，所以“随机”采样也能复现。这一点是本章对拍的基础。

**结束符（eos）。** end of sequence，表示“说完了”的特殊 token。Qwen3.8 有两个：`<|im_end|>`（248046，对话里一轮说完）和 `<|endoftext|>`（248044），写在 `generation_config.json` 的 `eos_token_id` 里。

## 缓存里存什么

### 全注意力层：RoPE 之后的 k，和 v

回顾第 4 章，全注意力层对第 t 个 token 算的是：

```
q[t], k[t], v[t] = 投影(x[t])，再分别做 RMSNorm 和 RoPE（v 不做）
y[t] = Σ_{s ≤ t} softmax_s(q[t]·k[s] / √d) · v[s]
```

新来一个 token t，它要的是自己的 q[t]，和**所有** s ≤ t 的 k[s]、v[s]。前面 token 的 q 再也用不到了：它们的输出 y[s] 早就算完了。所以只存 k 和 v。

存的是 RoPE **之后**的 k。RoPE 把第 p 个位置的 k 旋转 p 倍的角度（第 3 章），旋转只取决于这个 token 自己的位置，与后面来的 token 无关，旋转之后存进去，以后直接用。第 5 章最后提醒过的事在这里兑现：新 token 的位置必须从缓存里已有的 token 数接着往下编，不能每一步都从 0 开始，否则新 token 的 q 和缓存里的 k 之间的相对距离就错了。

27B 有 16 个全注意力层，每层 4 个键值头，每个头 256 维，k 和 v 各一份，我们用 float 存：每个 token 16 × 2 × 4 × 256 × 4 字节 = 128 KB。上下文的上限 `max_position_embeddings` 是 262144 个 token，填满就是 32 GB。

### 线性注意力层：状态矩阵和卷积的窗口

第 4 章的线性注意力层里有两个“往前看”的地方：

- **因果卷积**：第 t 个 token 的输出要用第 t − 3 到 t 个 token 卷积之前的输入（卷积核长 4）。所以要存最近 3 个 token 的 qkv，每个 10240 维。
- **门控 delta 规则**：逐 token 更新状态矩阵 S，第 t 个 token 的输出只取决于更新到它为止的 S。所以存 S：48 个值头，每个 128 × 128。

两者都与序列多长无关。我们的 S 全程用 double（第 4 章），48 层一共 48 × 48 × 128 × 128 × 8 字节 ≈ 302 MB；卷积窗口 48 × 3 × 10240 × 4 字节 ≈ 5.9 MB。

对比一下：序列不到 2400 个 token 时，线性注意力层的固定状态比全注意力层的 KV 缓存还大；序列越长，KV 缓存越占主导。这正是 Qwen3.8 这种“四层里只有一层是全注意力”的混合结构想要的效果：64 层如果全是全注意力，KV 缓存是现在的 4 倍。

### 缓存的生命周期

```c
typedef struct {
    float *k, *v;            /* 全注意力层：[cap, kv_heads * head_dim] */
    float *conv;             /* 线性注意力层：[conv_k - 1, 卷积的通道数]，旧的在前 */
    double *S;               /* 线性注意力层：[lv_heads, lk_dim, lv_dim] */
} layer_cache;

typedef struct {
    size_t n_layers;
    size_t cap, len;         /* 最多能放多少个 token、已经放了多少个 */
    int broken;              /* model_step 中途出错后为 1，缓存不能再用 */
    layer_cache *layers;
} model_cache;
```

`model_cache_init` 按容量一次分配好，`cap` 不能超过 `max_position_embeddings`。`model_step` 把 n 个新 token 接在缓存里的 `len` 个后面算一遍，位置是 `len` 到 `len + n − 1`，成功后 `len` 加 n。放不下就报错，缓存不变。

`broken` 这个字段值得说一句。`model_step` 是一层一层往下算的，如果在第 30 层出了错（比如内存不足），前 30 层的缓存里已经有了这 n 个 token，后 34 层还没有。这样的缓存再接着用，结果一定是错的，而且不会有任何报错。所以出错时把它标记为损坏，之后的调用一律拒绝。严格拒绝，绝不猜测。

## 为什么能做到逐位相同

带缓存的结果和不带缓存的“差不多”很容易做到，逐位相同要多想一步。

浮点加法不满足结合律，`(a + b) + c` 和 `a + (b + c)` 可能差一个 ulp（第 3 章）。所以只要求和的项或者次序变了，结果就可能不同。我们把缓存涉及的三个算子都改写成“接着上一次往下算”的样子，并且保证求和的项和次序与一次算完时**完全一样**：

- **注意力**：`op_attention_past` 多了一个参数 past。第 t 个新 token 的位置是 past + t，它对位置 0 到 past + t 的 k 依次做点积、取最大值、求指数和、加权求和，循环的写法与第 4 章的 `op_attention` 一字不差，只是 k、v 的前 past 行来自缓存。缓存里的 k、v 就是当初算出来的那些 float，原样存、原样取。
- **因果卷积**：`op_conv1d_hist` 把缓存里的 nh 行历史和新来的 n 行看成一条序列，只算后 n 行的输出。每个输出的 4 项乘积按同样的顺序加起来；序列开头之前的项同样跳过，而不是当作 0 加进去（加 0 一般没事，但 −0 和 +0 在浮点里是两个数，没必要冒这个险）。
- **门控 delta 规则**：`op_gated_delta_state` 的状态 S 由调用方传进来，进来时是处理完前面 token 的状态，出去时更新好。S 是 double，存在缓存里也是 double，没有任何舍入。

原来的三个算子变成它们的特例：`op_attention` 就是 past = 0 的 `op_attention_past`，`op_conv1d` 是没有历史的 `op_conv1d_hist`，`op_gated_delta` 是从全零状态出发的 `op_gated_delta_state`。第 3、4 章的测试照样跑，照样通过，说明特例没有被改坏。

其余的步骤（矩阵乘、归一化、激活、RoPE）都是每个 token 各算各的，算一个和算一批没有区别。

这件事不是理所当然的。官方 transformers 的预填充用第 4 章说过的分块算法（64 个 token 一块），解码用逐 token 的递推，两种写法数学上相等，舍入不同；GPU 上的实现为了速度更会按批大小换求和顺序。那些实现里，带缓存和不带缓存只能做到“差不多”。我们的第一卷故意只用最朴素的循环，换来的就是这一条可以用 `cmp` 检查的标准。第 7 章换成 GPU 以后，这条标准还能不能保持，到时再看。

## 代码

### 一层、整个模型都走同一份代码

第 4 章的 `layer_forward`、第 5 章的 `model_forward` 没有另写一份带缓存的版本，而是改成调用同一个内部函数，缓存指针为 NULL 时就是原来的行为：

```c
static int layer_run(float *h, size_t n, const int32_t *pos, size_t past, const model_cfg *c, const layer_w *w,
                     layer_cache *lc, trace_fn T, void *ctx, char *err, size_t cap);

int layer_forward(...) { return layer_run(h, n, pos, 0, c, w, NULL, T, ctx, err, cap); }
```

这样做的好处是第 4、5 章所有的对拍（逐步对拍、官方对拍、已知答案）仍然在检查本章的代码路径；“带缓存和不带缓存一致”检查的就只剩缓存本身：存进去的是不是对的东西、取出来的是不是对的位置。

全注意力层的改动只有三处：新 token 的 v 抄进缓存；RoPE 之后的 k 直接写进缓存的第 past 行；注意力对缓存里的全部 past + n 行算。线性注意力层在卷积之后，把“历史加新 token”的最后 3 行留作下一次的历史；门控 delta 规则传进缓存里的 S。

### 生成循环

```c
预填充：提示词按 chunk 个一块交给 model_step（默认一次全给），只有最后一块的最后一行有用
循环：
    分布 = sample_dist(最后一行 logits)          温度 → top-k → top-p
    u = 下一个随机数（贪心时不取）
    tok = sample_pick(分布, u)
    输出 tok
    tok 是结束符 → 停（结束符本身算在输出里）
    已经生成 max_new 个 → 停
    model_step(tok)，得到新的最后一行
```

`generate` 还有一个 `no_cache` 开关，打开时每一步都调用第 5 章的 `model_forward` 从头算，给测试当标准答案。提示词加上 `max_new` 超过 `max_position_embeddings` 时一开始就报错，而不是生成到一半再说。

预填充时我们对提示词的每一行都算了 logits，其实只用得上最后一行。27B 的输出层每行约 13 亿次乘加，占一个 token 总计算量的 5%，按“先正确，后性能”先不省。

### 采样

`sample_dist` 把一行 logits 变成“保留哪些 token、各自多大概率”，规则照抄 transformers 5.23.0 的 `generation/logits_process.py`，顺序照抄 `GenerationMixin._get_logits_processor`：先温度，再 top-k，再 top-p。

1. **温度**：z = logits / T，在 double 里算。
2. **top-k**：按分数从高到低排序（同分时 id 小的在前），分数不低于第 k 名的都保留。注意是“不低于第 k 名”：如果第 k 名和第 k + 1 名同分，两个都留下，保留的个数会超过 k。官方 `TopKLogitsWarper` 就是这么写的（`scores < topk(scores, k)[..., -1]` 的才去掉），我们跟着它。
3. **top-p**：在剩下的 token 里从高到低数，**排在它前面的**累计概率还不到 p 的就保留。官方的写法反过来：从低到高累加，去掉累计概率不超过 1 − p 的。两种说法在数学上是一回事（某个 token 前面的累计是 a，它自己加后面的累计就是 1 − a；a < p 与 1 − a > 1 − p 等价），舍入不同，只在“正好压线”时可能有分歧，测试会报告离这条线有多远。
4. 剩下的重新做 softmax，按 id 从小到大输出。

`sample_pick` 拿一个 [0, 1) 里的随机数 u，按 id 从小到大累加概率，返回第一个使累计值大于 u 的 token，这叫逆变换采样：概率为 p 的 token 正好占据长度为 p 的一段区间。按 id 的顺序而不是按概率的顺序累加，是因为 id 的顺序不会有并列，两边实现起来不会有分歧。

贪心解码是特例：分布里只有分数最大的那一个（同分取 id 小的，与第 5 章相同），概率为 1，不取随机数。

### 随机数

随机数生成器用 splitmix64：一个 64 位整数的状态，每次加上一个常数 0x9e3779b97f4a7c15，再经过三次“异或右移、乘常数”的搅拌输出。

```c
uint64_t rng_next(rng64 *r) {
    uint64_t z = (r->s += 0x9e3779b97f4a7c15u);
    z = (z ^ (z >> 30)) * 0xbf58476d1ce4e5b9u;
    z = (z ^ (z >> 27)) * 0x94d049bb133111ebu;
    return z ^ (z >> 31);
}

double rng_uniform(rng64 *r) { return (double)(rng_next(r) >> 11) * 0x1p-53; }
```

选它的理由：五行代码，C 和 Python 各写一遍不会写出分歧；统计性质对采样足够好；还有一个现成的独立实现可以当已知答案，Java 标准库的 `java.util.SplittableRandom` 用的是同一个算法。`rng_uniform` 取高 53 位除以 2⁵³，得到的是 2⁻⁵³ 的整数倍，在 double 里是精确的，两边算出的 u 必然逐位相同。

我们没有用 C 标准库的 `rand()`：它的算法由各家 C 库自己定，同一个种子在 glibc 和 macOS 上给出的数不同，书里的结果就没法复现。

### 停止条件和 generation_config.json

`gen_cfg_load` 读 `generation_config.json`。27B 的这个文件只有 7 个字段（第 3 章），我们只接受这几个字段加上 `transformers_version`，其余一律报错：比如有人加了 `repetition_penalty`（重复惩罚，降低已经出现过的 token 的分数），我们没有实现，就不能假装用了它。

`do_sample` 为 true 时，`temperature`、`top_k`、`top_p` 必须都写明。transformers 不同版本对缺省值的规定不同（较早的版本 `top_k` 缺省是 50，5.x 里缺省是“不用”），我们不猜。

停止条件只有两个：生成了 `eos_token_id` 里的任何一个（结束符本身算在输出里，这与官方 `generate` 相同），或者生成满 `max_new` 个。

### 命令行工具

```
generate <config.json> <generation_config.json> <token id，逗号分隔> <max_new> [选项 ...] <分片 ...>
```

选项 `--greedy`、`--sample`、`--temperature`、`--top-k`、`--top-p` 覆盖 `generation_config.json` 里的值；`--seed` 是种子；`--chunk C` 把提示词 C 个一块交给模型；`--no-cache` 每一步从头算；`--dump` 打印每一步的 logits、分布和随机数。不带 `--dump` 时每生成一个 token 就打印一行并立刻刷新输出，这是最朴素的流式输出。

## 和谁比、差多少算对

### 缓存：和自己比

缓存的标准答案就是第 5 章：同一个 `generate`，加上 `--no-cache`，每一步都调用第 5 章的 `model_forward` 从头算。两次运行的输出（每一步的 logits、分布、随机数、token）用 `cmp` 逐字节比较。提示词一个一个给（`--chunk 1`）、三个三个给（`--chunk 3`），也必须逐字节相同，这检查的是预填充分块时缓存的衔接，尤其是卷积窗口：块长 1 和 3 都小于等于卷积往前看的 3 个 token，历史有时来自上一块、有时跨两块。

此外再用第 5 章的因果性论证做一次：把“提示词加上除最后一个之外的生成 token”交给第 5 章的 `forward` 一次算完，后面 m 行 logits 必须与 `generate` 每一步的逐位相同。这次前向本身再交给第 5 章的 `model_ref.py` 逐步检查。这样，生成时用到的每一行 logits，都间接地经过了第 5 章的全部对拍。

### 采样：先把随机的部分变成确定的

采样的麻烦在于随机。我们和官方各抽一次，抽到不同的 token 是正常的，没法逐 token 比较。可选的办法有三种：

1. **统计检验**：两边各抽几千次，用卡方检验看分布是否一致。结果本身带概率性（检验总有一定概率冤枉一个正确的实现），只能在小模型上做，而且要抽很多次。
2. **只比分布**：只检查温度、top-k、top-p 之后的概率分布，抽到哪个不管。
3. **把采样拆成确定的一半和随机的一半**：分布是确定的，与官方严格对拍；随机数用我们自己写的生成器，Python 按同一个种子复现出同样的随机数，于是选中哪个 token 也变成了确定的，可以逐 token 对拍。

我们用第 3 种（Wei 定的方案）。它包含第 2 种，又比第 1 种严格得多：只要分布对、随机数对、“随机数落在哪个 token 上”的规则对，结果就对。

第一层 [`tests/06-generate/gen_ref.py`](../tests/06-generate/gen_ref.py) 只用标准库：

- 用 Python 再写一遍 splitmix64，开头先用 `SplittableRandom` 算出的数自检。每一步的 u 必须与 C 打印的完全相等。
- 用 C 打印的每一行 logits 独立地做一遍温度、top-k、top-p。z = logits / T 是一次 IEEE 双精度除法，两边结果必然相同，所以排序和 top-k 的取舍可以要求完全一致；概率用 `decimal` 以 40 位有效数字算，当作精确值，C 的相对误差不超过 10⁻⁹（C 在 double 里求和，24.8 万项的舍入误差上界约 3 × 10⁻¹¹）。
- 用精确的概率和同一个 u 做逆变换采样，选中的 token 必须与 C 相同。
- 生成了结束符就必须停，没生成结束符就必须生成满 `max_new` 个，打印的停止原因要对。

第二层 [`tests/06-generate/gen_official.py`](../tests/06-generate/gen_official.py) 调用官方代码：

- **官方的 logits 处理器。** 对 C 打印的每一行 logits，在 float64 下依次套上 `TemperatureLogitsWarper`、`TopKLogitsWarper`、`TopPLogitsWarper`（什么条件下加哪一个、按什么顺序，照抄 `_get_logits_processor`），再做 softmax。保留的 token 必须与 C 相同，概率的相对误差不超过 10⁻⁹。这一条在真实模型上也做。
- **官方的整条流水线（小模型）。** 构造官方的 `Qwen3_5ForCausalLM`（float64），调用它的 `generate`。官方 `generate` 用自己的缓存（预填充走分块算法，解码走逐 token 递推，与我们的写法都不同）、自己的停止条件。抽样那一步官方调用的是 `torch.multinomial`，用的是 torch 自己的随机数，我们把它临时换成一个函数：记下官方传进来的概率，返回 C 在这一步选的 token。这样官方就“照着 C 的选择”走完全程，我们检查：
  - 每一步官方算出的分布（来自官方自己的 logits，不是 C 的）与 C 的分布保留相同的 token，概率最多差 2⁻¹²（与第 4、5 章的容差同一个量级）；
  - 官方在同样的地方停下：C 因为结束符停了，官方也必须停；C 生成满了个数，官方也不能提前停。官方要多生成一个时，替换函数会发现“C 已经没有下一个了”，直接报失败。
  - 贪心解码时不用替换，官方自己选，生成的 token 必须完全相同。

最后这个替换 `torch.multinomial` 的办法，是本章对拍里我们最喜欢的一个：它没有绕开官方代码的任何一部分，只把唯一不确定的那一步换成确定的。

### 离边界有多远

和第 5 章“第一名领先多少”一样，逐 token 对拍有一个风险：如果 u 恰好落在两个 token 的分界附近，或者某个 token 的累计概率恰好压在 top-p 的线上，正常的舍入差异就可能让两边选得不一样。所以 `gen_ref.py` 每次都报告“随机数离累计概率的边界最近有多远”和“top-p 边界的余量”。小模型上最小的是 3 × 10⁻⁵ 和 6 × 10⁻⁶，比 C 与精确值之间的误差（10⁻¹⁶ 量级）大十个数量级以上。真遇到压线的情况，测试会失败并把余量打印出来，到时再看。

## 踩过的坑

**带缓存与不带缓存第一次就逐位相同。** 这不算坑，但值得记一笔：我们是先把三个算子改成“接着往下算”、确认求和的项和次序不变，再写缓存的。第一次跑，四种跑法的输出 md5 就完全一样，贪心解码的 8 个 token 也和第 5 章的 `forward` 相同。如果反过来，先写出“差不多对”的缓存，再去追查最后几位为什么不同，会难得多。

**top-k 的同分规则一开始没有测试能发现。** 做“故意改坏”时，把 top-k 改成遇到同分也只留 k 个，三层检查全部通过。原因很简单：随机小模型的 logits 是随机的，两个 token 分数正好相等的概率几乎为零，同分的那条分支从来没有走到过。我们为此加了“并列”的用例：输出层两两相同的模型，每一步都有并列。改坏之后，第一层、第二层都立刻失败。

真实模型上并列会不会出现？会，而且不稀奇：logits 是 float，24.8 万个数里有两个正好相等并不罕见；输出层里也可能有完全相同的行，那样对应的两个 token 每一步都同分（这一点我们没有在 27B 上核实）。规则没测到，就等于没有规则。

**top-p 的同分没有对拍。** top-p 也会遇到并列：累计概率越过 p 的那个位置上如果有两个同分的 token，留哪个取决于排序时谁在前。我们规定 id 小的在前，官方用 `torch.sort`，这个排序不保证同分元素的先后，两边可能留下不同的那一个。我们没有为它造用例，因为官方本身就没有确定的答案。真遇到时，第一层会通过，第二层会报“保留的 token 不同”，`gen_ref.py` 打印的 top-p 余量会是 0。

**一个内存泄漏。** 命令行工具解析到不认识的选项时，原来写的是 `return 1`，ASan 的泄漏检查报告提示词的数组没有释放。改成和其他错误一样调用 `exit(1)`。错误路径上的资源释放，前几章的工具都是这样处理的：进程马上就退出了，由操作系统回收。

## 还没做的事

- 重复惩罚、停止字符串（遇到某段文字就停）等其他生成参数：`generation_config.json` 里没有，暂不做，遇到就报错。
- 预填充时只算最后一行 logits、KV 缓存改存 BF16、缓存按需增长而不是一次分配：都是性能和内存上的优化，留到后面。
- 流式输出到文字：现在流式输出的是 token id。一个汉字可能被切在两个 token 里（第 2 章），要把 id 及时变成用户能看的文字，得处理半个字符的情况，第 8 章做服务层时一起做。
- 多个请求共用一次前向（批处理）：第 8 章。
