# 第 4 章 单层前向

> 状态：初稿。本章的代码已在一个结构与 Qwen3.8 相同的随机小模型上通过两层对拍，并在目标机器上用 Qwen3.8-27B 的真实权重通过了验收，见“在真实权重上验证”一节。

## 要解决的问题

第 3 章把十来种算子一个一个写对了。这一章把它们拼成模型的一层：给定一串 token 的向量，算出这一层的输出。Qwen3.8-27B 有两种层，48 个线性注意力层和 16 个全注意力层，两种都要做。把 64 层串起来、得到 logits 是第 5 章的事。

拼起来看似只是按顺序调用算子，其实是全书第一次要回答“整件事算对了没有”。第 3 章每个算子的定义只有一两行，对着官方代码看一眼就知道读得对不对；一层有二十多步，哪个张量切成几段、第几个头和第几个头配对、先衰减还是先更新，任何一处读错，程序都照样输出一堆看起来正常的数。第 3 章还留下了两个问题：

1. 官方的 transformers 在 BF16 下每一步都舍入，我们的输出不会和它逐位相同。那么该和谁比、差多少算对？
2. 最终归一化的权重均值是 0.94，“零中心的权重应当在 0 附近”这个旁证判断不了 `1 + w` 的写法对不对，要靠和官方逐层对拍来确认。

本章的验收标准分两层：

**第一层：C 的每一步，以它自己的输入为准，都要与精确值相差不超过第 3 章的容差（1 个 ulp 加一项抵消余量）。第二层：C 的结果与官方 transformers 代码在 float64 下算出的结果相比，每个张量的最大误差不超过这个张量均方根的 2⁻¹²（约 2.4 × 10⁻⁴）。**

为什么要两层、第二层为什么只能这么松，是本章的核心，见“和谁比、差多少算对”一节。

## 几个新概念

第 3 章“几个基本概念”一节讲过张量、残差流、注意力、注意力头、线性注意力和门控。这一章还要用到下面几个。

**解码层。** 模型里结构相同、一层接一层串起来的单元，transformers 里叫 `Qwen3_5DecoderLayer`。“解码”这个名字来自 Transformer 最初的“编码器加解码器”结构，现在的大模型只剩解码器那一半，名字就留下来了。本章说的“一层”就是一个解码层。

**token 混合器。** 每一层里负责让 token 之间交换信息的那一部分，在 Qwen3.8 里就是注意力。全注意力层和线性注意力层的区别只在这一部分，层的其余部分（两次 RMSNorm、前馈层、两次残差）完全相同。

**状态矩阵。** 线性注意力不保留每个 token 的 k 和 v，而是给每个头维护一个固定大小的矩阵 S，处理每个 token 时更新一次。它就像一块“记忆”：读的时候拿 q 去乘它，写的时候把新 token 的信息加进去。Qwen3.8 的每个状态矩阵是 128 × 128，48 个值头就是 48 个。

**delta 规则。** 一种更新状态矩阵的规则。先用当前 token 的键 k 从状态里“读出”一个预测值 Sᵀk，和真正的 v 相减得到误差，只把误差写回状态。名字里的 delta 就是这个差。和“直接把 k vᵀ 加进去”相比，它不会把同一条信息重复写很多次。

**衰减和门控 delta 规则。** 每处理一个 token，先把整个状态乘一个 0 到 1 之间的系数 e^g，让旧的记忆按比例淡去，再按 delta 规则写入。这个系数由当前 token 算出来，相当于模型自己决定“这一步要忘掉多少”，所以叫“门控”。β（beta）是另一个由 token 算出来的 0 到 1 之间的系数，决定误差写回多少，相当于写入的“力度”。

**分块算法。** 门控 delta 规则按定义是逐 token 循环的。GPU 不擅长这种一步依赖上一步的循环，于是官方代码把序列切成 64 个 token 一块，块内用矩阵运算一次算完，块与块之间再循环。数学上与逐 token 循环相等，但浮点舍入不同，这一点在后面会变得重要。

**eager 注意力。** transformers 里注意力有几种实现：`eager` 是按定义一步步写的 PyTorch 代码，`sdpa`、`flash_attention_2` 等是调用融合好的快速内核。对拍时我们用 eager，因为它就是公式本身。

## 一层的结构

这一节的结构来自 transformers 5.23.0 版 `models/qwen3_5/modeling_qwen3_5.py` 里的 `Qwen3_5DecoderLayer`、`Qwen3_5Attention`、`Qwen3_5GatedDeltaNet`。第 3 章“先看模型由哪些算子组成”一节给过一个简版，这里补上全部细节，特别是那些容易读错的地方。

两种层的骨架相同：

```
x = RMSNorm(h)                  input_layernorm，1 + w 形式
h = h + token混合器(x)           全注意力或线性注意力
x = RMSNorm(h)                  post_attention_layernorm，1 + w 形式
h = h + down(silu(gate(x)) · up(x))
```

### 全注意力层

```
qg = q_proj(x)                   [n, 24 × 512]
q, 门控 = 把 qg 按头切开           每个头 512 维：前 256 维是 q，后 256 维是门控
k = k_proj(x), v = v_proj(x)     [n, 4 × 256]
q = RMSNorm(q), k = RMSNorm(k)   按头做，每个头 256 维，1 + w 形式（q_norm、k_norm）
q = RoPE(q), k = RoPE(k)         每个头只转前 64 维
y = 注意力(q, k, v)               因果，第 h 个查询头用第 h / 6 组键值，缩放 1/√256
y = y · sigmoid(门控)
输出 = o_proj(y)                 [n, 5120]
```

有三处要小心。

**q 和门控怎么切。** 官方代码是 `torch.chunk(q_proj(x).view(n, -1, 2 * head_dim), 2, dim=-1)`：先把 12288 维看成 24 个头、每个头 512 维，再把每个头的 512 维切成两半。所以 q 和门控是**按头交错**的：头 0 的 q、头 0 的门控、头 1 的 q、头 1 的门控……如果凭直觉写成“前 6144 维是 q，后 6144 维是门控”，形状完全对得上，结果却是错的。

**键值组怎么分。** 24 个查询头共用 4 组键值，官方的 `repeat_kv` 把每组键值重复 6 次、**相邻**排列，所以查询头 0 到 5 用第 0 组，6 到 11 用第 1 组。另一种分法“头 h 用第 h mod 4 组”同样形状对得上。

**掩码。** 第 t 个 token 只看位置 0 到 t。我们直接让循环只跑到 t，不去构造一个 n × n 的掩码矩阵。

### 线性注意力层

```
qkv = in_proj_qkv(x)             [n, 10240]：q 16×128、k 16×128、v 48×128 连在一起
z   = in_proj_z(x)               [n, 48 × 128]，给最后的门控归一化用
b   = in_proj_b(x), a = in_proj_a(x)    [n, 48]，每个值头一个数
qkv = silu(因果卷积(qkv))          在切开之前，对全部 10240 个通道做
q, k, v = 切开 qkv
q = L2(q), k = L2(k)             按头做，eps 固定为 1e-6
β = sigmoid(b)
g = −e^(A_log) · softplus(a + dt_bias)    衰减的对数，g ≤ 0
y = 门控delta规则(q, k, v, g, β)   第 j 个值头用第 j / 3 个键头
y = RMSNorm门控(y, z)             按头做，每个头 128 维，w 形式，乘 silu(z)
输出 = out_proj(y)               [n, 5120]
```

同样有几处要小心。

**卷积在切开之前。** 卷积作用在拼在一起的 10240 个通道上，切成 q、k、v 是之后的事。因为卷积是逐通道的，先切再分别卷积结果其实一样，但卷积核是一个 [10240, 1, 4] 的整体，按“先卷再切”写最不容易对错通道。

**键头怎么分给值头。** 16 个键头服务 48 个值头。官方代码用的是 `repeat_interleave(3, dim=2)`，每个键头重复 3 次、相邻排列，所以值头 0、1、2 用键头 0。这和全注意力的 `repeat_kv` 是同一种分法。

**g 是对数。** 状态每一步乘的是 e^g，不是 g。A_log 也是对数：真正的 A 是 e^(A_log)，所以 g = −A · softplus(a + dt_bias)。softplus 的结果总是正的，所以 g 总是负的，e^g 在 0 和 1 之间。

**q 的缩放。** 官方代码在 delta 规则里把 L2 归一化之后的 q 再乘 1/√128。这一步藏在 `torch_chunk_gated_delta_rule` 函数内部，从层的代码里看不到。

**门控 delta 规则本身。** 官方的逐 token 版本（`torch_recurrent_gated_delta_rule`）写的是：

```
S    = e^g · S                   S 是 dk × dv（128 × 128），初值为 0
u    = β · (v − Sᵀ k)            Sᵀk 是状态对 v 的预测，u 是缩放后的误差
S    = S + k uᵀ
y    = Sᵀ q / √dk
```

注意顺序：先衰减，再用衰减之后的状态做预测和更新，最后用更新之后的状态读出 y。三步中任意两步换个顺序，形状都不变。

**两种 RMSNorm。** 层的两次归一化、q_norm、k_norm 都是 `Qwen3_5RMSNorm`，`1 + w` 形式；线性注意力最后那个是 `Qwen3_5RMSNormGated`，`w` 形式。第 3 章已经讲过，这里再强调一次，因为它正是第 3 章遗留的第二个问题。

## 代码

代码分三处：

- [`src/model.h`](../src/model.h)、[`src/model.c`](../src/model.c)：读配置、加载一层的权重、算一层的前向。
- [`src/ops.c`](../src/ops.c)：新增四个算子。逐元素加法和乘法（残差和门控用）、线性注意力的衰减量 g、因果分组查询注意力、门控 delta 规则。
- [`tools/layer.c`](../tools/layer.c)：命令行工具，算“嵌入 → 某一层 → 最终归一化”，把每一步的结果都打印出来。最终归一化本来在第 64 层之后才做，这里接在一层后面，只为了让它的权重也得到对拍。

`layer_forward` 每算完一步，就调用一次调用方给的回调函数，把这一步的结果交出去：

```c
op_rmsnorm(x, h, w->in_norm, n, H, c->eps);                tr(T, ctx, "attn_in", x, n, H);
...
op_add(h, h, y, n * H);                                    tr(T, ctx, "resid", h, n, H);
```

推理时回调是 NULL，什么也不做；测试时工具把每一步按“名字 [行,列]”加上 `%a` 格式的数打印出来。一层大约二十多步，全部可见，后面的对拍就靠它。

### 两个新算子

注意力照定义写：对每个查询头、每个位置 t，先算出它和位置 0 到 t 的全部分数，减去最大值，求 e 的幂和总和，再按权重把 v 加起来。全程 double，最后舍入一次。

门控 delta 规则写的是逐 token 的版本，而不是官方的分块版本：

```c
for (size_t t = 0; t < n; t++) {
    double decay = exp((double)g[t * hv + j]), b = (double)beta[t * hv + j];
    for (size_t i = 0; i < dk * dv; i++) S[i] *= decay;
    for (size_t c = 0; c < dv; c++) {               /* u = beta (v - Sᵀk) */
        double pred = 0;
        for (size_t r = 0; r < dk; r++) pred += S[r * dv + c] * (double)kt[r];
        u[c] = b * ((double)vt[c] - pred);
    }
    for (size_t r = 0; r < dk; r++)
        for (size_t c = 0; c < dv; c++) S[r * dv + c] += (double)kt[r] * u[c];
    for (size_t c = 0; c < dv; c++) {
        double o = 0;
        for (size_t r = 0; r < dk; r++) o += S[r * dv + c] * (double)qt[r];
        y[(t * hv + j) * dv + c] = (float)(o * scale);
    }
}
```

逐 token 的写法和公式一一对应，而且生成时（第 6 章）本来就是一个 token 一个 token 地来，正好是这个循环的一步。分块算法是 GPU 上的性能优化，留到第二卷。

状态矩阵 S 全程是 double。config.json 里的 `mamba_ssm_dtype` 要求状态至少用 float32 保存（第 3 章），double 比它更精确。后面会看到，把 S 每一步舍入成 float，第一层对拍就会失败。

### 读配置

第 3 章说过，加载模型时从 `config.json` 读维度，读到不认识的取值就报错。`model_cfg_load` 只接受 Qwen3.8 的那一种配置：

| 检查 | 原因 |
| --- | --- |
| `model_type` 必须是 `qwen3_5`，必须有 `text_config` | 别的架构公式不同 |
| `hidden_act` 必须是 `silu`，`output_gate_type`（如果有）必须是 `swish` | 我们只实现了这一种激活函数 |
| `rope_parameters.rope_type` 必须是 `default` | 别的取值会改变旋转频率 |
| `head_dim × partial_rotary_factor` 必须是不超过 `head_dim` 的正偶数 | transformers 写的是 `int(...)`，会悄悄截掉小数，我们要求恰好是整数 |
| `attention_bias` 必须是 false | 我们没有实现偏置 |
| `attn_output_gate`（如果有）必须是 true | transformers 根本不读它，门控总是开着（第 3 章）。写成 false 的配置，读者会以为关掉了门控 |
| `layer_types` 的项数必须等于层数，每项只能是两种之一 | 防止层号和层类型对不上 |
| 头数必须能整除 | 否则分组没法均分 |
| 整数字段必须是正整数，eps 不能是负数 | 拼错一个数不会崩溃，只会悄悄算错 |

权重也一样：每个张量的名字、dtype、形状都按配置算出来的值检查，比如 q_proj 必须是 [24 × 256 × 2, 5120]。少了门控那一半的 q_proj、长度不对的 q_norm、形状不对的卷积核，都在加载时报错，而不是算到一半越界。

## 和谁比、差多少算对

这是第 3 章留下的第一个问题。

### 官方的 BF16 不能当标准答案

官方代码在 BF16 下运行时，每个线性层、每个归一化的输出都舍入成 BF16，只有 8 位有效数字，相对误差约 0.4%。我们在小模型上实测，官方 BF16 一层的结果和精确值的相对误差在 0.4% 到 9% 之间（后面有具体数字）。如果拿它当标准答案，容差至少要放到 10⁻¹ 量级，第 3 章那张“故意引入的错误”表里，大部分错误都会混过去。

反过来让 C 模仿官方的 BF16 舍入，逐位复现官方的结果，也不行：舍入发生在哪里、用什么顺序累加，取决于 PyTorch 选了哪个内核，CPU 和 GPU 都不一样。何况那会让我们的 CPU 实现失去“标尺”的作用（第 3 章“用 double 算”一节），第 7 章没法区分 GPU 内核写错和舍入不同。

### 官方的 float64 也不精确

那么让官方代码在 float64 下运行呢？权重从 BF16 转成 float64 是精确的，矩阵乘也是 float64。但读一下代码就会发现，它在好几处会自己转成 float32：

- `Qwen3_5RMSNorm` 是 `self._norm(x.float())`。`.float()` 在 PyTorch 里就是转成 float32，即使 x 本来是 float64，所以所有 `1 + w` 形式的 RMSNorm 都在 float32 里算。
- `Qwen3_5RMSNormGated` 是 `hidden_states.to(torch.float32)`，同样。
- RoPE 的频率和角度用 float32 算。
- softmax 写的是 `softmax(..., dtype=torch.float32)`。
- 门控 delta 规则的开头把 q、k、v、g、β 全部转成 float32，整个分块算法都在 float32 里做。
- g 的计算里有 `A_log.float()` 和 `a.float()`。

这些地方写成 float32 是有道理的：模型平时用 BF16 运行，把关键的几步提升到 float32 可以减少误差。但对我们来说，这意味着官方代码怎么跑都只有 float32 的精度，比不上第 3 章那种 1 个 ulp 的标准。

### 两层对拍

所以这一章把“算对了”拆成两件事，分别检查：

1. **每一步都算准了吗？** 这是精度问题，标准答案用标准库 Python 按定义算，和第 3 章一样严。
2. **公式读对了吗？** 这是语义问题，标准答案用官方代码，容差放宽到能容纳官方自己的 float32 误差。

为什么第一件事不够？因为第一层的参考实现 [`tests/layer_ref.py`](../tests/layer_ref.py) 和 C 代码出自同一份对官方代码的理解。如果我们把 `1 + w` 读成了 `w`，Python 里也会写成 `w`，两边错成一样，第一层照样通过。第 3 章的 RMSNorm 测试就是这样：它保证了 `1 + w` 算得精确，却保证不了 `1 + w` 本身是对的。

为什么第二件事不够？因为容差放宽之后，精度上的错误就看不出来了。比如矩阵乘改用 float 累加，结果比精确值差几个 ulp，和官方的 float32 误差混在一起，第二层分不出来。

两层各管一半，下面“测试本身也要测”一节会用故意改坏的代码说明，它们正好互补。

### 第一层：逐步对拍

C 端把每一步的结果都打印出来，`layer_ref.py` 对每一步，**拿 C 打印出来的这一步的输入**，用双精度独立地算出精确值，再用第 3 章的标准比较：

```
|g − r| ≤ ulp(r) + 2⁻³² · s
```

为什么用 C 的中间结果做输入，而不是从头独立地算一遍？因为如果从头算，C 每一步的 0.5 个 ulp 舍入误差会一路传下去、被后面的步骤放大，到这一层的输出已经差了很多个 ulp，容差就只能放宽，又回到了“多宽才够、多宽太宽”的老问题。拿 C 的输入算，每一步的误差只来自这一步本身，标准可以和第 3 章完全一样。

这样做会不会漏掉“把错的张量当成了输入”这类错误？不会。哪一步的输入是哪个张量、张量怎样切成头，由 `layer_ref.py` 自己决定，不看 C 端怎么做。比如 C 把 q_proj 的输出切成 q 和门控之后，并不打印切好的结果；`layer_ref.py` 从 q_proj 的完整输出自己切一遍，算出它认为的 q_norm，和 C 的 q_norm 比。C 切错了，这一步就对不上。步骤的名字和顺序也必须和参考实现的计划一字不差。

大部分步骤沿用第 3 章的算子定义。新的两个步骤要说明一下容差里的 s，也就是“所有求和项绝对值之和”：

- **注意力**：输出是 Σ p_s v_s，s 就是 Σ p_s |v_s|。
- **门控 delta 规则**：输出经过了一串递推，求和项没法直接列出来。我们把同一个递推用绝对值再跑一遍：状态的每个元素取绝对值，u 换成 β(|v| + Aᵀ|k|)，最后读出 Aᵀ|q| / √dk。每一步的每一项都被它的绝对值代替，所以这样算出来的数是“所有中间项有多大”的一个上界，正好当 s 用。

double 递推本身的误差远小于 float 的 ulp，所以 C 的输出仍然应当是精确值的正确舍入。

### 第二层：和官方代码比

[`tests/layer_official.py`](../tests/layer_official.py) 直接用 transformers 里的类：

```python
dec = M.Qwen3_5DecoderLayer(tc, layer)          # 一层，按配置构造
dec.load_state_dict(这一层的权重)                  # 从 safetensors 读，BF16
norm = M.Qwen3_5RMSNorm(...)                    # 最终归一化
rot = M.Qwen3_5TextRotaryEmbedding(tc)          # RoPE 的 cos、sin
dec.to(torch.float64)
```

然后给嵌入、位置和因果掩码，跑一遍，用 PyTorch 的“钩子”（挂在某个模块上、在它算完之后被调用的函数）把 13 个中间结果取出来，和 C 打印的同名张量比较。不需要加载整个 55.6 GB 的模型，只加载用到的那一层。

有两处设置要说明：

- 注意力用 eager 实现，原因见前面的“几个新概念”。
- 脚本开头让 Python 找不到 `fla`（flash-linear-attention）和 `causal_conv1d` 这两个包。它们是门控 delta 规则和因果卷积的 GPU 加速版，装了的话 transformers 会优先用它们；找不到时，transformers 退回到自己的纯 PyTorch 写法，那才是我们要比的“官方公式”。

**判定标准。** 对每个张量，最大误差除以这个张量所有元素的均方根，不超过 2⁻¹² ≈ 2.4 × 10⁻⁴。用均方根而不是逐元素的相对误差，是因为官方的 float32 误差是按整个向量的大小产生的：一个接近 0 的元素，相对误差可以很大，但这不说明公式错了。

这个数是怎么定的？有三个量级可以参考：

| | 相对误差 |
| --- | --- |
| C 与官方 float64，小模型上实测 | 最大 2.2 × 10⁻⁵ |
| 官方 BF16 与 C，小模型上实测 | 4 × 10⁻³ 到 9 × 10⁻² |
| 公式读错（下一节的几种错误），小模型上实测 | 0.5 到 8 |

2⁻¹² 比实测的最大误差留了 10 倍余量，比任何一种读错公式造成的误差小三个数量级以上，也比官方 BF16 的误差小一个数量级以上。最后这一条的意思是：我们和官方 float64 的距离，比官方自己的 BF16 和 float64 的距离近得多。

**最初的容差定得太紧。** 我们一开始定的是 2⁻¹⁶ ≈ 1.5 × 10⁻⁵，理由是“float32 的相对精度约 10⁻⁷，算上一层几十步的累积，10⁻⁵ 足够”。结果 7 个小模型用例里有 6 个通过，70 个 token 的线性注意力用例失败了：门控归一化那一步差了 2.2 × 10⁻⁵。

是我们错了，还是官方的 float32 误差比预想的大？我们把 C 的 delta 规则的输入原样交给官方的三个版本：

| 官方版本 | 与 C 的相对误差 |
| --- | --- |
| 分块算法，float32（transformers 默认用的） | 2.8 × 10⁻⁵，最差的是第 61 个 token |
| 分块算法，把代码里的 float32 全部换成 float64 | 7.8 × 10⁻⁷ |
| 逐 token 算法，float32 | 2.5 × 10⁻⁶ |

把 float32 换成 float64，差距就降到了 10⁻⁶ 以下，说明 C 的公式没错，误差来自官方分块算法本身的 float32 舍入。原因在分块算法的写法：它先在块内对 g 做累加 `cum_decay = decay.cumsum()`，再计算 `exp(cum_decay)` 和 `exp(cum_decay[-1] − cum_decay)` 这样的量，分别乘在 q 和 k 上。我们的随机小模型里 g 最小到 −25，一块 64 个 token 累加下来是几百，e 的几百次幂超出了 float32 的范围或精度，误差就大了。离块的开头越远，累加得越多，所以最差的是第 61 个 token；8 个 token 的用例累加得少，误差只有 10⁻⁶ 量级，所以只有 70 个 token 的用例失败。

所以 2⁻¹⁶ 是把官方的误差估小了，容差改成了 2⁻¹²。真实模型的 g 大概不会这么极端，但容差应当按官方代码的写法来留余量，而不是按我们的随机数据。

### 顺带的观察：官方 BF16 离精确值有多远

`layer_official.py` 还会用 BF16 再跑一遍官方代码（这才是模型平时实际的运行方式），打印它和 C 的距离，不做判定。小模型上 8 个 token 的线性注意力层：

```
    attn_in      与官方 float64 差 2.4e-07，官方 BF16 差 6.9e-03
    qkv          与官方 float64 差 2.2e-07，官方 BF16 差 1.0e-02
    gnorm        与官方 float64 差 1.3e-06，官方 BF16 差 3.2e-02
    attn_out     与官方 float64 差 8.8e-07，官方 BF16 差 3.0e-02
    mlp_out      与官方 float64 差 8.6e-07，官方 BF16 差 2.4e-02
    out          与官方 float64 差 4.7e-07，官方 BF16 差 1.3e-02
```

BF16 一层就差了 1% 到 3%。第 5 章把 64 层串起来时，官方 BF16 的结果会离精确值多远、最后选出的 token 会不会因此不同，是那一章要回答的问题。

## 测试本身也要测

和第 3 章一样，我们故意把代码改坏，看哪一层测试能发现。“两边”指 C 和 `layer_ref.py` 改成同一种错误，模拟“我们把官方代码读错了”：

| 故意引入的错误 | 第一层（逐步） | 第二层（官方） |
| --- | --- | --- |
| C 的 RMSNorm 把 `1 + w` 写成 `w` | 失败 | 失败 |
| 两边都把 RMSNorm 写成 `w` | **通过** | 失败，相对误差约 2 到 7 |
| 两边都把线性注意力的键头对应写成 j mod 16 | **通过** | 失败，约 8 |
| 两边都把 q 和门控切反 | **通过** | 失败 |
| 两边都在 delta 规则里先更新再衰减 | **通过** | 失败，约 4 |
| 两边都忘了 q 除以 √dk | **通过** | 失败，约 0.5 |
| 两边都把前馈层的残差漏掉 | **通过** | 失败 |
| C 的注意力不加因果掩码 | 失败 | 失败 |
| C 的 delta 规则状态每一步舍入成 float | 失败 | **通过** |
| C 的矩阵乘用 float 累加 | 失败 | **通过** |
| C 的 L2 归一化 eps 写成 1e-5 | 失败 | **通过** |

前七行里有六行是第一层发现不了的读错，第二层全部抓住；最后三行是第二层发现不了的精度问题，第一层全部抓住。这就是要两层的原因。

第二行就是第 3 章遗留的第二个问题：如果 `1 + w` 写错了，第二层会立刻失败，相对误差是 2 到 7，不是什么细微的差别。所以只要真实权重上第二层通过，就证明 `1 + w` 是对的。最终归一化的权重均值是 0.94 也好，0 也好，都不影响这个结论。

“两边都把前馈层的残差漏掉”还被一个不依赖 Python 的已知答案抓住了：把每一层最后的输出投影（`o_proj`、`out_proj`、`down_proj`）全部置零，这一层的输出就必须与输入逐位相同。

第二层对拍在这一轮全部失败了，原因不在 C 代码：5.8.0.dev0 里 `Qwen3_5DecoderLayer` 记录层类型的属性叫 `layer_type`，5.23.0 里叫 `block_type`，测试脚本读了后者。改成直接从配置读层类型（提交 `9ff63f0`）之后，四层的第二层对拍：

**官方 BF16 在真实权重上差得更多。** 小模型上官方 BF16 一层差 1% 到 3%，真实权重上更大：第 0 层的输出差 0.50 个均方根，线性注意力的门控归一化差 0.31 到 0.46。这些是“最大误差除以均方根”，说明有个别元素差得很远，而不是所有元素都差这么多。第 5 章串起 64 层时，我们要弄清这些误差会不会改变最后选出的 token。

## 踩过的坑

**参考实现跟着版本变。** 第 2 章就遇到过参考库随版本变化的例子，这一章又遇到两次，都是在目标机器上第一次跑的时候：

- transformers 5.8.0.dev0 的 `Qwen3_5DecoderLayer` 用 `layer_type` 记录层的类型，5.23.0 改名成了 `block_type`。我们的脚本读了后者，在 5.8 上直接报 `AttributeError`。现在改成从配置里读，不再依赖这个属性。
- 第 2 章的对话模板对拍，有一条请求是空对话，按模板应当报错。5.23.0 抛的是 `ValueError`，被我们当作“应当报错”；5.8.0.dev0 还没进模板就在 `conversation[0]` 上抛了 `IndexError`，参考实现整个退出了。现在空对话直接按“应当报错”处理，不再依赖 transformers 报什么异常。

两次都是参考实现出错，C 端没有任何问题；但第一次看到的现象只是“FAIL”，因为测试脚本把参考实现的错误输出丢掉了。现在第二层对拍失败时会把参考实现的最后一行报错一起打印出来。

**第二层容差一开始定得太紧**，见“和谁比、差多少算对”一节。
