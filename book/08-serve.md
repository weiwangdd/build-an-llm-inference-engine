# 第 8 章 服务层

> 状态：初稿。本章的代码已在随机小模型上通过全部测试：批处理时每个请求的 logits、分布、随机数和生成的 token 都与单独生成逐字节相同，HTTP 服务端的端到端测试通过；在 Qwen3.8-27B 上，GPU 版服务端同时回答四个问题，每个回答都与单独生成逐 token 相同（见“在真实权重上验证”一节）。

## 要解决的问题

到第 7 章为止，引擎是一个命令行程序：启动，加载权重，回答一个问题，退出。真正用起来不是这样的。模型应当一直在显卡上待着，别的程序通过网络把问题发过来，回答一边生成一边发回去；同时可能有好几个人在问，有人问到一半不想等了，直接关掉了页面。

这一章写这个“服务端”。前言里这一阶段要做四件事：HTTP 接口、流式输出、取消、批处理；验收标准是“批处理与单条请求的结果一致”。

其中最值得花心思的是批处理。第 7 章结束时，GPU 上每个 token 要 0.8 秒。这 0.8 秒里，GPU 的大部分线程其实闲着：解码时每一步只有一个新 token，矩阵乘只有几千个输出，而这张卡能同时运行十几万个线程。如果同时有 8 个请求，把它们的新 token 放在一起算，一次矩阵乘就有 8 倍的输出，用时却增加得少得多。问题是：放在一起算，结果还和单独算一样吗？

## 几个新概念

**HTTP。** 浏览器和网站之间说话的格式，也是几乎所有网络服务的格式。客户端（发起请求的一方）连上服务端，发一段文字形式的“请求”：第一行是方法（`GET` 取东西，`POST` 交东西）和路径（如 `/v1/chat/completions`），接着是若干行“头部”（`名字: 值`），一个空行，再是“正文”（要交的数据）。服务端回一段同样格式的“应答”，第一行是状态码：200 表示成功，4xx 表示请求有错（400 格式不对、404 没有这个东西），5xx 表示服务端出错。

**JSON。** 一种表示数据的文本格式，第 2 章读 tokenizer.json 时已经用过。现在的网络接口几乎都用它做请求和应答的正文。

**OpenAI 兼容接口。** OpenAI 公司为它的模型定的一套 HTTP 接口。因为用的人多，开源的推理服务（vLLM、SGLang、llama.cpp 等）都实现了同样的接口，于是为 OpenAI 写的程序、库、聊天界面，改一下地址就能连到这些服务上。我们也实现它的一个子集：`POST /v1/chat/completions`，正文里给出对话消息，应答里是模型的回答。

**流式输出和 SSE。** 不等全部生成完再一起发，而是生成一个 token 就发一点。OpenAI 接口用的是 SSE（Server-Sent Events，服务器推送事件）：应答的正文不是一个 JSON，而是一串“事件”，每个事件是一行 `data: <JSON>` 加一个空行，客户端边收边处理；最后一个事件是 `data: [DONE]`。

**预填充和解码。** 生成的第一步要把整个提示词交给模型（第 6 章），这一步叫预填充（prefill），一次算几十到几千个 token；之后每一步只交上一步选出的那一个 token，叫解码（decode）。

**批处理和连续批处理。** 批处理是把几个请求放在一起算。最简单的做法是凑齐一批，一起从头生成到尾，等最慢的那个结束再换下一批；但各个请求要生成的长度差别很大，先结束的就在那里空等。连续批处理（continuous batching）以“一步”为单位安排：每一步把所有正在进行的请求各往前推一个 token，谁结束了就离开，排队的马上补进来。现在的推理服务都这样做。

**事件循环。** 服务端同时管着很多连接，每个连接都可能在任何时候来数据、断开或者可以接着发。一种写法是每个连接一个线程；另一种是一个线程反复问操作系统“哪些连接有动静”，有动静就处理一下，再接着问。后一种叫事件循环。问的那个系统调用叫 `poll`。

**非阻塞。** 普通的 `recv`（从连接收数据）在没有数据时会一直等，这一等整个事件循环就停了。把连接设成非阻塞（`O_NONBLOCK`）之后，没有数据时 `recv` 马上返回“现在没有”（`EAGAIN`），程序可以去忙别的。

## 验收标准：批处理与单独生成逐位相同

前言里写的是“批处理与单条请求的结果一致”。什么叫一致？

商用的推理服务通常做不到逐位一致。原因和第 7 章讲的一样：为了快，它们把一个矩阵乘拆成很多块并行地加，怎么拆取决于这一批有几行，行数一变，求和的次序就变，结果就差几个 ulp；再经过几十层放大，采样时就可能选出不同的 token。所以在这些服务上，同一个问题、同一个随机种子，单独问和与别人一起问，回答可能不一样。

我们的算子没有这个问题：第 3 章起，每个输出都由一个求和算出，求和的项和次序只取决于这个输出本身，与同一批里还有几行无关；GPU 版照搬了同样的次序（第 7 章）。所以可以定一个严格得多的标准（Wei 定的方案）：

**任意的到达次序、任意的批大小下，每个请求生成的 token、选每个 token 时看到的那一行 logits、采样的分布、用到的随机数，都与把它单独交给第 6 章的 `generate` 时逐位相同。**

“单独交给 `generate`”是第 6 章已经对拍过的：与 Python 参考实现、官方 transformers 的 logits 处理器和 `generate` 都一致。所以这一条标准等于说：批处理没有给结果带来任何变化。

接口的形态也是 Wei 定的：OpenAI 兼容的子集，支持流式输出，单线程的事件循环。单线程让批处理的结果完全确定，便于逐位对拍；代价在后面讨论。

## 批处理的前向：一张表，按序列分开的三步

第 6 章的 `model_step` 把一个序列的几个新 token 接在它的缓存后面算一遍。本章把它推广成一次算好几个序列（[`src/model.h`](../src/model.h)）：

```c
typedef struct {
    model_cache *kc;         /* 这个序列的缓存 */
    const int32_t *ids;      /* 新 token */
    size_t n;                /* 新 token 的个数，至少 1 */
} model_seq;

int model_step_batch(const model *m, model_seq *seqs, size_t nseq, float *logits, ...);
```

做法是把各序列的新 token 一个接一个排成一张表。比如第 0 个请求在预填充，交了提示词的 5 个 token；第 1、2 个在解码，各交 1 个；表就是 7 行：

```
行 0..4   请求 0 的 5 个 token，位置 0..4
行 5      请求 1 的 1 个 token，位置 37
行 6      请求 2 的 1 个 token，位置 12
```

然后看一层里的每一步，问一个问题：第 r 行的结果，是不是只取决于第 r 行的输入？

- **是的步骤**：嵌入、RMSNorm、矩阵乘（所有的投影和前馈层）、激活函数、门控、残差加法、RoPE（它要的位置，每一行单独给出）、最终归一化和输出层。这些步骤对整张表做一次，和第 4、5 章完全一样，只是行多了。其中矩阵乘占了几乎全部的计算量，正是批处理要省的地方：每个权重从显存里读出来一次，给 7 行用。
- **不是的步骤**，只有三个，都是要“往前看”的：全注意力（看同一序列前面的 k、v）、因果卷积（看同一序列前面 3 个 token）、门控 delta 规则（接着同一序列的状态矩阵往下算）。这三步按序列分开，每个序列用自己的缓存，调用的仍是第 6 章的 `op_attention_past`、`op_conv1d_hist`、`op_gated_delta_state`，只是指针指向表里这个序列的那几行。

以全注意力为例（[`src/model.c`](../src/model.c)，有删节）：

```c
mm(qg, x, &w->q, n);                     /* 投影：整张表 */
...
op_rope(k, t1, pos, n, nkv, hd, c->rot, c->theta);   /* RoPE：整张表，pos[r] 是第 r 行的位置 */
for (size_t b = 0, off = 0; b < nseq; off += seqs[b++].n) {     /* 注意力：按序列分开 */
    size_t nb = seqs[b].n, past = seq_past(&seqs[b]);
    layer_cache *lc = seq_cache(&seqs[b], layer);
    memcpy(lc->k + past * kd, k + off * kd, nb * kd * sizeof *k);   /* 新 k、v 接在自己的缓存后面 */
    memcpy(lc->v + past * kd, v + off * kd, nb * kd * sizeof *v);
    op_attention_past(t1 + off * qd, q + off * qd, lc->k, lc->v, nb, past, ...);
}
op_sigmoid(t2, gate, n * qd);            /* 门控：整张表 */
```

为什么逐位相同：第一类步骤的每个输出，求和的项和次序与表有几行无关；第二类步骤对每个序列做的，与它单独在 `model_step` 里做的一字不差。所以每个序列的每个中间结果都逐位相同，logits 也一样。

第 4、5 章的 `layer_forward`、`model_forward` 和第 6 章的 `model_step`，现在都是它的特例：一批只有一个序列（前两者不带缓存）。所以前面各章的测试原样跑一遍，就检查了重写之后单个序列的情形没有变。GPU 版（[`src/gpu_model.c`](../src/gpu_model.c)）照同样的方式改，仍与 `model.c` 一行一行对应。

有一处要小心：同一个缓存不能在一批里出现两次，否则两个序列会往同一块缓存里写。`model_step_batch` 在开始算之前检查这一点，和第 6 章的其余检查一样：检查不通过时什么都不变；中途出错时这一批的缓存都标记为损坏。

## 连续批处理：engine

[`src/engine.h`](../src/engine.h) 管着所有的请求。它只有四个函数：

```c
int  engine_add(engine *e, const int32_t *prompt, size_t n, const eng_params *p, uint64_t *id, ...);
int  engine_cancel(engine *e, uint64_t id);
int  engine_step(engine *e, ...);
size_t engine_pending(const engine *e);
```

`engine_add` 把一个请求排到队尾，每个请求有自己的采样参数、随机数种子、最多生成几个 token。`engine_step` 往前推一步：

1. **补人。** 按到达顺序，把排队的请求补进这一批，直到这一批有 `max_batch` 个。补进来时才给它建缓存（第 6 章的 `model_cache_init`），大小是“提示词加最多生成的个数”。
2. **每个请求交上这一步的 token。** 还在预填充的，交提示词的下一块（最多 `chunk` 个）；已经在解码的，交上一步选出的那一个。
3. **一次前向。** `model_step_batch`。
4. **选 token。** 提示词已经交完的请求，取它那一段的最后一行 logits，用自己的采样参数和随机数选一个 token（与第 6 章 `generate` 的代码和次序相同），通知调用方；生成了结束符或者达到个数的，通知调用方并从这一批里拿掉。

调度的规则故意定得很简单：先来先服务，排队的按到达顺序补进来，补进来就一直算到结束。它是确定的：同样的请求按同样的时机到达，每一步的组成都相同。

预填充可以分块（`chunk`）。一个几千 token 的提示词如果一次交给模型，这一步会很长，同一批里正在解码的请求都得等；分成小块，每一步只交一块，解码的请求每一步照样前进。第 6 章已经验证过分块与不分块逐位相同，所以分块也不影响结果。

`engine_cancel` 马上把一个请求从队列或这一批里拿掉，释放它的缓存。服务端在客户端断开时调用它。

### batch 工具

为了在没有网络的情况下测试 engine，有一个命令行工具 [`tools/batch.c`](../tools/batch.c)。它读一份请求清单，每行一个请求：

```
# 到达步  提示词                 max_new  选项（与 generate 相同）
0         3,17,17,0,39,5,22,8   12       --seed 1
0         7                     10       --greedy
0         <70 个 token>          8        --seed 2 --chunk 16
2         <3 个 token>           20       --seed 4 --cancel-after 3
...
```

“到达步”是这个请求在第几步之前加进 engine，用来模拟请求在不同时刻到来；`--cancel-after K` 表示生成 K 个之后取消，模拟客户端中途断开。输出按清单的顺序，每个请求一段，格式与 `generate` 完全相同（加 `--dump` 时包括每一步的 logits、分布和随机数），所以可以直接与 `generate` 的输出逐字节比较。`--log` 把每一步这一批的组成写进文件，下面是 `--max-batch 8` 时的开头几步，每一项是“请求编号:这一步交了几个 token”：

```
step 0 0:8 1:1 2:16
step 1 0:1 1:1 2:16 3:5
step 2 0:1 1:1 2:16 3:1 4:8 5:3
step 3 0:1 1:1 2:16 3:1 4:1 5:1 6:12 7:7
```

第 0 步，请求 0 交了 8 个提示词 token，请求 1 的提示词只有 1 个，请求 2 的 70 个提示词交了第一块 16 个。第 1 步，请求 0 和 1 已经在解码（各交 1 个），请求 2 交第二块，刚到的请求 3 交它的 5 个提示词。预填充和解码在同一步里混着算，这就是连续批处理。

## 服务端

### 一个线程

服务端的结构（[`src/server.c`](../src/server.c)）是一个循环，每一圈做四件事：

1. 用 `poll` 看哪些连接有动静。engine 里有活时不等（超时 0），只看一眼；没活时最多等 1 秒。
2. 处理有动静的连接：收数据，收齐一个请求就解析、套模板、分词、交给 `engine_add`；可以发就把发送缓冲区里的东西发出去；客户端断开了，就 `engine_cancel` 它的请求。
3. 接受新连接。
4. engine 里还有请求，就调用一次 `engine_step`。新 token 解码成文字，追加到各自连接的发送缓冲区，下一圈发出去。

只有一个线程，所以没有锁，也不用担心两个线程同时改 engine。批处理的结果因此完全确定，与 `batch` 工具、与逐个单独生成都逐位相同。

代价也很明显：`engine_step` 算的那段时间里，服务端不收也不发。27B 上一步大约 1 秒（第 7 章），这一秒里新来的连接和数据在操作系统内核的缓冲区里等着，下一圈再处理。对“先正确”的第一卷来说可以接受：每一步本来就要那么久，新请求最多晚一步加入。把网络放到另一个线程，是第二卷的事。

每个连接只处理一个请求，应答发完就关闭（应答头里写 `Connection: close`）。这省掉了 HTTP 的连接复用：一个连接上可以接连发好几个请求，服务端要分清前一个请求在哪里结束、下一个从哪里开始。

### HTTP：只认一小部分，其余都拒绝

HTTP 的规范很长，历史上留下了很多写法：没有 `\r` 只有 `\n` 的换行、跨行的头部（下一行以空格开头表示接着上一行）、分块传输（不给出总长度，正文分成一块一块、每块先写长度）。不同的程序对这些写法理解不一致，是一类安全漏洞的来源：前面的代理认为请求在这里结束，后面的服务端认为在那里结束，攻击者就能夹带一个请求进去（这叫请求走私）。

我们按本书一贯的原则处理（[`src/http.c`](../src/http.c)）：只支持用得到的那一小部分，其余一律拒绝，并给出对应的状态码。

| 情况 | 状态码 |
| --- | --- |
| 请求行或头部的格式不对、行不以 `\r\n` 结束、跨行的头部、没有 `Host`、`Content-Length` 重复或不是十进制数 | 400 |
| 不是 HTTP/1.1 | 505 |
| `POST` 没有 `Content-Length` | 411 |
| 用了 `Transfer-Encoding`（比如分块传输） | 501 |
| 头部超过 16 KiB | 431 |
| 正文超过 1 MiB | 413 |
| `Expect` 不是 `100-continue` | 417 |

`Expect: 100-continue` 是客户端发大正文之前的一句询问：“我要发这么长的正文，你收不收？”服务端回一行 `HTTP/1.1 100 Continue`，客户端才接着发。curl 在正文较大时会这样做，所以要支持。

解析函数 `http_parse` 只看收到的字节，不碰网络：返回“还没收完”“头部完整、正文还没齐”“全收齐了”或者“不合法”。这样可以把各种写坏的请求直接交给它测试。

### OpenAI 接口：认识的字段，和不认识的字段

[`src/api.h`](../src/api.h) 里列出了认识的字段：

| 字段 | 含义 |
| --- | --- |
| `model` | 必需，必须是服务端加载的那个模型的名字（`--name`），否则 404 |
| `messages` | 必需，对话消息，交给第 2 章的对话模板；每条消息只认 `role`、`content`、`reasoning_content`、`tool_calls` |
| `stream` | 是否流式 |
| `stream_options` | `{"include_usage": true}` 时流式应答的最后多一个用量事件 |
| `max_tokens` 或 `max_completion_tokens` | 最多生成几个 token；不给时生成到上下文长度的上限 |
| `temperature` | 0 到 2；0 表示贪心解码（OpenAI 的约定） |
| `top_p`、`top_k` | 第 6 章的 top-p、top-k；`top_k` 不是 OpenAI 的字段，但 vLLM 等都支持 |
| `seed` | 随机数种子，不给时是 0 |
| `n` | 一次要几个回答，只能是 1 |
| `chat_template_kwargs` | 对话模板的参数：`enable_thinking`、`reasoning_effort`、`preserve_thinking`（与 vLLM 的写法相同） |

没给的采样参数取 generation_config.json 里的，与第 6 章相同。

其余字段，比如 `tools`（工具调用，第 11 章）、`stop`（遇到某段文字就停）、`logprobs`、`frequency_penalty`，一律以 400 拒绝。很多服务端对不认识的字段是悄悄忽略的。这看起来更“宽容”，其实更糟：客户端以为 `stop` 生效了，实际上没有，回答里多出一截，很难查到原因。

`seed` 不给时是 0，而不是每次随机挑一个，这是有意的：同样的请求总是得到同样的回答。想要不同的回答，换一个种子。

`max_tokens` 不给时，生成到“上下文长度”为止。上下文长度（`--max-ctx`，默认 4096）是每个请求“提示词加生成”的上限，它决定每个请求的缓存有多大。对 27B，每个 token 的 KV 缓存是 16 个全注意力层 × 2（k 和 v）× 4 个键值头 × 256 维 × 4 字节 = 128 KiB，4096 个 token 就是 512 MiB；线性注意力层的状态矩阵与长度无关，48 层 × 48 × 128 × 128 个 double，约 302 MB。所以每个请求约 0.8 GB，同时 8 个约 6.5 GB，权重占了 52 GB 之后，96 GB 的卡放得下。上下文长度设成模型支持的最大值（262144）是放不下的，这正是 vLLM 那样按页分配缓存的原因（见“还没做的事”）。

### 流式输出：半个汉字

每个 token 解码出来的是一串字节（第 2 章），不一定是完整的 UTF-8 字符：一个汉字是 3 个字节，可能被切在两个 token 里。流式输出时，如果把半个汉字发出去，客户端只能把它显示成乱码。

所以每个连接有一个“待发”缓冲区。新 token 的字节追加进去之后，从末尾往前看最多 3 个字节：如果它们是一个合法字符的开头、只是还没完（比如一个汉字的前两个字节），就先留着；前面的部分按第 2 章的 `from_utf8_lossy` 规则（非法字节换成 U+FFFD）转成文字发出去。生成结束时，剩下的全部发出去。

这样分几次发出的文字拼起来，与对全部字节一次做 `from_utf8_lossy` 的结果相同。理由：被留下的那几个字节以一个“开头字节”起头，而开头字节不可能是前面任何字符的后续字节，所以前面那部分怎么处理，与后面还会来什么无关。测试检查了这一点：流式各块拼起来，等于非流式的文字，也等于官方 tokenizers 库对全部 token 的解码。

结束符 `<|im_end|>` 是特殊 token，解码时跳过（与 tokenizers 的 `skip_special_tokens` 相同），所以不会出现在回答里。思考模式的 `<think>`、`</think>` 不是特殊 token，会原样出现在回答里；vLLM 等会把思考的部分拆到单独的 `reasoning_content` 字段，我们没有做。

### 取消

客户端断开时，`poll` 报告这个连接可读，`recv` 返回 0（对方关闭）或者出错。如果这个连接的请求还在 engine 里，就调用 `engine_cancel`，它的缓存马上释放，下一步的批里就没有它了。往已经关闭的连接上写数据，默认会收到 `SIGPIPE` 信号，整个进程退出；服务端启动时忽略这个信号，改为让 `send` 返回错误，同样当作断开处理。

因为只有一个线程，取消只能在两步之间发生。27B 上，客户端断开之后最多再算一步（约 1 秒）才会发现。

有一种情况会被误当成断开：客户端发完请求后关闭自己的发送方向（“半关闭”），只保留接收方向。这时 `recv` 也返回 0。常见的客户端（curl、浏览器、Python 的 http.client 和 openai 库）都不这样做，我们没有区分。

### 关连接也有讲究

应答发完之后直接 `close`，有时客户端反而收不到应答。比如客户端声明了一个 2 MB 的正文，服务端读完头部就回了 413，然后关闭连接；如果这时客户端还在发正文，操作系统发现有数据到达一个已经关闭的连接，会回一个 RST（连接重置），客户端那边的网络栈收到 RST，会把还没来得及读的 413 应答一起丢掉。

所以应答发完之后，服务端先只关闭自己的发送方向（`shutdown(fd, SHUT_WR)`），客户端读到应答的结尾就会关闭连接；服务端把客户端还在发的东西读完丢掉，等到对方关闭（最多 5 秒）再 `close`。

### 一个请求的一生

下面是在目标机器上用 27B 实际跑的一次（GPU 版，端口 8123；为了排版，每个 `data:` 行省略了 `id`、`created`、`model` 等重复字段，它们在每一块里都相同：`"id":"chatcmpl-0"`、`"model":"qwen3.8-27b"`）：

```
$ curl -N localhost:8123/v1/chat/completions -d '{"model":"qwen3.8-27b", "stream":true,
       "messages":[{"role":"user","content":"中国的首都是哪里？"}],
       "chat_template_kwargs":{"enable_thinking":false}}'
data: {…"choices":[{"index":0,"delta":{"role":"assistant","content":""},"finish_reason":null}]}

data: {…"choices":[{"index":0,"delta":{"content":"中国"},"finish_reason":null}]}

data: {…"choices":[{"index":0,"delta":{"content":"的首"},"finish_reason":null}]}

data: {…"choices":[{"index":0,"delta":{"content":"都是"},"finish_reason":null}]}

data: {…"choices":[{"index":0,"delta":{"content":"北京"},"finish_reason":null}]}

data: {…"choices":[{"index":0,"delta":{"content":"。"},"finish_reason":null}]}

data: {…"choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}

data: [DONE]
```

每一块正好是一个 token 的文字：“的首”“都是”在这个词表里各是一个 token，所以切分看起来有点怪。`finish_reason` 是 `stop` 表示模型生成了结束符，`length` 表示达到了 `max_tokens`。这个请求没有写 `temperature`，所以照 `generation_config.json` 采样，种子默认 0；同一个请求再发一遍，回答逐字相同。

服务端的标准错误输出里，每个请求的开始、结束（或取消）各有一行，结束那一行列出生成的全部 token id，测试用它与单独生成比较。上面那次请求的日志是：

```
开始 id=0 提示词=17 max_new=4079 流式=1 采样=1 种子=0
完成 id=0 原因=stop 提示词=17 生成=6 token=96328,102357,96878,98116,1710,248046
停止
```

提示词经过对话模板是 17 个 token。请求没写 `max_tokens`，就用上下文剩下的全部长度：4096 − 17 = 4079。最后一个 token 248046 是 `<|im_end|>`，它不出现在文字里。“停止”是收到 SIGTERM 后服务端退出前的最后一行。

启动服务端：

```
make                                   # 或 make gpu
build/serve $M/config.json $M/generation_config.json $M/tokenizer.json $M/chat_template.jinja \
            [--port 8000] [--max-batch 8] [--max-ctx 4096] [--chunk K] $M/*.safetensors
```

`$M` 是模型目录。GPU 版是 `build/gpu/serve`。默认只监听本机（127.0.0.1）：这个服务端没有身份验证、没有限流（第 11 章），不应当直接暴露在网络上。

## 如何验证正确

测试分三部分，都在 `make test` 里。

**一、批处理与单独生成逐字节相同**（[`tests/run_batch.sh`](../tests/run_batch.sh)）。用第 6 章的 8 层随机小模型（词表 40，结束符 38、39），请求清单由 [`tests/make_batch_fixtures.py`](../tests/make_batch_fixtures.py) 生成，12 个请求：

- 到达时间各不相同，最后一个在别的都结束之后才来；
- 采样参数各不相同（贪心、Qwen 的默认参数、低温加 top-p、高温不限 top-k……）；
- 提示词从 1 个到 70 个 token，有的分块预填充（块长 16、7、3）；
- 两个请求完全相同（同样的提示词和种子），在不同的时间到达；
- 两个请求中途取消（生成 3 个、1 个之后）。

每个请求先单独交给 `generate`（加 `--dump`），作为标准答案；被取消的，标准答案是单独生成的前 K 个 token 再加 `stop cancel`。然后 `batch` 在 `--max-batch` 为 1、3、8 时各跑一遍，每个请求那一段必须与标准答案逐字节相同。因为加了 `--dump`，比较的不只是 token，还有选每个 token 时那一行 logits 的每一位、分布、随机数。

```
标准答案：12 个请求逐个单独生成，共 97 个 token
ok   max_batch=1：12 个请求的 logits、分布、随机数、token、停止都与单独生成逐字节相同（111 步，一批最多 1 个请求，0 步里预填充与解码同批）
ok   max_batch=3：12 个请求的 logits、分布、随机数、token、停止都与单独生成逐字节相同（43 步，一批最多 3 个请求，14 步里预填充与解码同批）
ok   max_batch=8：12 个请求的 logits、分布、随机数、token、停止都与单独生成逐字节相同（34 步，一批最多 8 个请求，16 步里预填充与解码同批）
ok   已知答案：max_batch=8 用了 34 步，max_batch=1 用了 111 步
```

测试还检查了日志：批里确实同时有好几个请求，预填充与解码确实在同一步里，批的大小没有超过上限。否则“全部相同”可能只是因为根本没有发生批处理。最后是 15 个写坏的输入（空清单、id 越界、温度为 0、超过上下文长度、logits 里有 NaN……），都必须以退出码 1 拒绝。

**二、HTTP 端到端**（[`tests/run_serve.sh`](../tests/run_serve.sh)、[`tests/serve_test.py`](../tests/serve_test.py)）。服务端需要分词器，而小模型的词表只有 40 个 token，所以 [`tests/make_serve_fixtures.py`](../tests/make_serve_fixtures.py) 用第 2 章的办法现训练一个约 3000 token 的小词表（有 `<|im_start|>`、`<|im_end|>` 等特殊 token），再造一个词表大小与它相同的随机模型，对话模板是 27B 的那一份。随机模型几乎不会生成 `<|im_end|>`，为了测到 `finish_reason` 为 `stop`，把输出层里 `<|im_end|>` 那一行放大到 2 倍，让它每一步有百分之几的机会被选中。

测试（只用 Python 标准库，另用官方 tokenizers 库解码）启动服务端，通过 HTTP 发请求，检查：

- **结果对。** 每个请求的提示词交给第 2 章的 `tok chat` 套模板、分词，再交给 `generate` 单独生成，作为标准答案。服务端日志里这个请求生成的 token 必须与它逐个相同；应答的文字必须等于官方 tokenizers 对这些 token 的解码；`finish_reason` 和用量统计必须与 token 一致。贪心、采样、不给 `max_tokens`、带系统消息、关掉思考模式，各有用例。
- **同时来的请求。** 7 个请求（流式、非流式混着）陆续发出，每个都与单独生成相同；日志里有一步同时算了 4 个请求（上限），也有预填充与解码同批的步。两个相同的请求结果相同。
- **流式。** SSE 的格式：每个事件是一行 `data:` 加空行，第一块只有 `role`，中间每块只有非空的 `content`，最后一块 `delta` 为空、带 `finish_reason`，`include_usage` 时再加一个用量块，最后是 `[DONE]`。各块拼起来与同一个请求非流式时的文字相同。
- **取消。** 发一个能生成很久的流式请求，收到 3 块后断开。服务端日志必须报告这个请求被取消，已生成的 token 必须是单独生成的前缀；之后服务端照常回答别的请求。为了让小模型像 27B 那样慢、能来得及取消，测试启动服务端时加了 `--slow 15`（每一步多等 15 毫秒）。
- **拒绝。** 44 个写坏的请求：HTTP 层面的（上表的每一行）和接口层面的（不是 JSON、重复的键、不支持的字段、模型名不对、温度越界、`n` 为 2、提示词超过上下文长度、非法的 UTF-8……），每个都必须得到约定的状态码和 JSON 格式的错误信息；之后服务端照常工作。
- **官方客户端。** 装了 OpenAI 的 Python 库（`openai`）时，再用它发一个非流式、一个流式请求，结果同样与单独生成相同；用它发不支持的 `stop` 字段，得到 `BadRequestError`。
- **退出。** 发 `SIGTERM`，服务端取消所有请求、关闭所有连接后退出，退出码 0。小模型测试开着 ASan，退出时没有报告内存泄漏。

```
ok   同时_1：提示词 519 个、生成 4 个 token（stop），与单独生成逐个相同，文字与 tokenizers 解码相同
...
ok   批处理：7 个请求用了 51 步，一批最多 4 个请求（上限 4），17 步里预填充与解码同批
ok   取消：收到 3 块后断开，服务端在生成 4 个（共 57 个）时取消，已生成的与单独生成的前缀相同
ok   拒绝：44/44 个写坏的请求得到约定的状态码和 JSON 错误
ok   官方 openai 3.56.0 客户端_流式：提示词 178 个、生成 10 个 token（length），与单独生成逐个相同，文字与 tokenizers 解码相同

```

**三、前面各章的测试原样通过。** `model_forward`、`model_step` 现在是 `model_step_batch` 的特例，第 4 到 7 章的测试检查了重写没有改变单个序列的任何一位。`make test` 一共 292 项，全部通过。`make test-gpu` 把批处理和服务端的测试也换成 GPU 版再跑一遍。

## 在真实权重上验证

```
make test-serve-real MODEL=/data/models/Qwen3.8-27B PYTHON=$HOME/venvs/x/bin/python
```

用 GPU 版（`-O2`、不带 ASan 另建）启动服务端，把几个问题同时发过去（流式与非流式、贪心与采样各半），记下总用时；再把每个问题单独交给 `generate`，要求生成的 token 逐个相同、文字等于 tokenizers 的解码，并比较两种做法的用时。

在目标机器（两张 RTX PRO 6000，只用第一张）上，四个问题同时发出，全部通过：

| 问题 | 方式 | 生成 | 单独用时 | 回答 |

| 中国的首都是哪里？ | 流式，贪心 | 31 | 30 秒 | 中国的首都是\*\*北京\*\*。北京位于中国北部，是中华人民共和国的首都，也是中国的政治中心、文化中心、国际交往中心和科技创新中心。 |

（第二个问题达到 `max_tokens` = 32 被截断，`finish_reason` 是 `length`；其余三个都以 `<|im_end|>` 结束。回答里的 `**` 是模型输出的 Markdown 加粗记号，原样保留。）

每个回答的 token 与单独交给 `generate` 的结果逐个相同，文字与 tokenizers 的解码相同。服务端日志里前几步的批是这样的：

```
步 0 批=0:17 1:21
步 1 批=0:1 1:1 2:20
步 2 批=0:1 1:1 2:1 3:20
步 3 批=0:1 1:1 2:1 3:1
```

请求是一个接一个连上来的，所以服务端每一步都把新到的请求的整段提示词和已在解码的请求的一个 token 放在同一张表里算；从第 3 步起四个请求一起解码。四个请求先后在第 9、21、29、32 步结束（日志里的 id 是服务端按连接先后编的号，与表里问题的次序不同），结束一个，批就小一个。

用时：

- 服务端加载权重 3 秒；四个问题从发出到全部收完 42.8 秒，共 33 步。
- 每个问题单独用 `generate`，合计 100 秒。其中每次都要重新加载权重，扣掉这部分，单独生成每个 token 仍要约 0.8 秒（与第 7 章相同），而批处理时四个请求一步也只要约 1.3 秒。批处理不改变任何一个结果，换来的是同样的时间里多回答了几个问题。
- 显存：加载完空闲时 51.9 GB，四个请求同时进行时峰值 53.1 GB，每个请求约 0.3 GB，绝大部分是线性注意力层的 delta 状态（48 层 × 48 个头 × 128 × 128 个 double）；全注意力层的 k、v 每个 token 只要 128 KiB，这几十个 token 微不足道。第二张卡没有用到。

同一台机器上，`make test` 292 项、`make test-gpu` 272 项也全部通过。

## 踩过的坑

**只有 `\n` 的请求让服务端一直等。** 第一版的 `http_parse` 先找头部的结尾 `\r\n\r\n`，找不到就认为“还没收完”。测试发了一个每行只以 `\n` 结束的请求，服务端一直等那个永远不会来的 `\r\n\r\n`，测试超时。现在在头部收完之前，先检查已经收到的部分：出现了不以 `\r` 开头的 `\n`，马上以 400 拒绝。“严格拒绝”不只是遇到错误时报错，还要尽早发现错误。

**`json.c` 在两个源文件列表里。** 服务端既要分词器（第 2 章的源文件列表里有 `json.c`）又要模型（第 5 章的列表里也有），合起来 `json.c` 出现两次，链接时报重复定义。Makefile 里用 `$(sort …)` 去掉重复（`sort` 顺便去重）。

**云端编译通过，目标机器上不通过。** 第一次在目标机器上跑 `make test-serve-real`，`-O2` 编译服务端时 gcc 报错：`'port' may be used uninitialized`。`server_run` 里的 `int port` 由 `open_listener` 在成功时填写，失败时函数直接返回，不会用到它；但 gcc 在 `-O2` 下把 `printf` 换成了带检查的 `__printf_chk`（Ubuntu 的 gcc 默认打开 `_FORTIFY_SOURCE`），内联之后看不出这一点，就报了“可能未初始化”，加上 `-Werror` 成了错误。云端的 `make test` 用的是 `-O1`，没有触发。改成 `int port = 0`。以后新增的程序，要在云端也用 `-O2` 编一遍。

**提示词比想象的长。** 用小模型试第一个请求“你好”，提示词有 161 个 token。原因是对话模板默认打开思考模式，并在最前面加上一段“思考强度”的说明（第 2 章）。关掉思考（`"chat_template_kwargs": {"enable_thinking": false}`）只剩十几个 token。

## 还没做的事

- **缓存按请求的最大长度一次分配。** 每个请求一进来就按“提示词加 `max_tokens`”分配缓存，哪怕它三个 token 就说完了。vLLM 的 PagedAttention 把缓存切成小页、用到时才分配，同一张卡能同时服务多得多的请求。
- **网络和计算在同一个线程。** 一步算的时候不收不发。
- **调度只有先来先服务。** 没有优先级，没有“新请求的预填充太长时先让解码的走”这样的策略；排队的请求没有上限（只限制了连接数），也没有超时。
- **相同的前缀没有共享。** 很多请求的开头相同（同一段系统提示），每个请求都从头预填充一遍。
- **只有一个回答（`n` 为 1），没有 `stop`、`logprobs`、工具调用；思考的部分没有单独拆出来。** 工具调用在第 11 章。
- **没有身份验证、限流、日志与指标。** 第 11 章。
- **一个连接只处理一个请求，没有 HTTPS。** HTTPS 通常交给前面的反向代理（如 nginx）。
