# 第 3 章 张量与算子

> 状态：初稿。本章的代码已在自造的小输入上通过对拍，包括 BF16 全部 65536 个位模式的穷举，并在目标机器上拿 Qwen3.8-27B 的真实权重做输入通过了验收，见“在真实权重上验证”一节。

## 要解决的问题

前两章把权重读进了内存，把文字变成了 token id。从这一章开始，我们要让模型真正算起来。

一个大模型的前向计算（从输入的 token 算出输出），拆到底只是十来种基本运算反复组合：矩阵乘、归一化、几个激活函数、softmax、位置编码。这些词在下一节“几个基本概念”里有简单解释。这一章把它们一个一个写出来，每一个单独验收；下一章再把它们拼成一层，第 5 章拼成整个模型。

为什么要单独验收，而不是直接拼成一层再看结果？因为一层的输出错了，你只知道“错了”，不知道是哪一步。而且有些错误在整层的输出里根本看不出来：把 RMSNorm 的 `1 + w` 写成 `w`，模型照样输出一串数字，只是每一层都被缩小了几十倍。一个算子一个算子地比，出错的地方就是那个算子。

本章的验收标准：

**每个算子的每个输出元素，与精确值的误差不超过 float 的 1 个 ulp（加上一项只在大量抵消时起作用的余量）；纯拷贝的算子要求完全相等。**

这个标准比通常的“相对误差小于 1e-3”严得多。后面“误差要多小才算对”一节解释它从哪里来、为什么定这么严。

## 几个基本概念

这一章开始出现大量深度学习的术语。读者会 C 和 Python，但不一定接触过神经网络，所以先用最少的话把要用到的概念交代一遍。每个概念这里只讲“它在计算上是什么”，为什么要这样设计、效果如何，不在本书范围内。

**张量和形状。** 张量就是多维数组。形状 `[n, 5120]` 表示 n 行、每行 5120 个数。第 1 章读出的每个权重都是一个张量。

**token 和向量。** 第 2 章把文字切成了 token id。模型内部不直接处理整数，而是给每个 token 配一个长度为 5120 的浮点向量，可以把它想成这个 token 的“坐标”。一句话有 n 个 token，就是一个 `[n, 5120]` 的张量。

**嵌入。** 把 id 换成向量的那一步。做法就是查表：嵌入表是一个 `[248320, 5120]` 的矩阵，第 i 行就是 id 为 i 的 token 的初始向量。

**前向计算。** 从输入的 token 算出输出的整个过程，也就是“推理”时做的事。（训练时还有一个反向计算，用来调整权重，推理不需要。）

**层和残差流。** 模型由很多结构相同、权重不同的“层”串起来。每一层读入 n 个向量，算出一个修正量，加回到原来的向量上：`h = h + f(h)`。这条一路往下传、不断被加上修正量的向量 h 叫残差流，它的宽度就是 `hidden_size`。

**激活值。** 计算过程中产生的中间结果（相对于事先存好的权重而言）。每一步算子的输入和输出都是激活值。

**线性层（投影）。** 一次矩阵乘法：输入向量 x 乘一个权重矩阵 W，得到另一个向量，长度可以变长也可以变短。把向量从一种长度“投”到另一种长度，所以也叫投影，比如 `q_proj`。有的线性层还会再加一个常数向量，叫偏置；Qwen3.8 的线性层都没有偏置。

**激活函数。** 逐个元素作用的非线性函数，比如 silu、sigmoid。没有它们，多个线性层叠起来仍然只是一次矩阵乘法。

**归一化。** 把一个向量整体缩放到某个固定的“大小”，免得数值在几十层里越滚越大或越来越小。RMSNorm 是其中一种：除以均方根，再乘一组学到的系数。

**前馈层。** 每一层里的第二部分：先用线性层把向量变宽（5120 到 17408），过激活函数，再用线性层变回原来的宽度。它对每个 token 独立计算，token 之间不交换信息。

**注意力。** 每一层里的第一部分，也是 token 之间交换信息的唯一地方。每个 token 从自己的向量算出三样东西：查询 q（“我在找什么”）、键 k（“我有什么”）和值 v（“我要给出的内容”）。一个 token 拿自己的 q 和每个 token 的 k 做点积，点积越大表示越相关；把这些分数用 softmax 变成加起来等于 1 的权重，再按权重把各个 token 的 v 加起来，就是它从别的 token 那里“看到”的东西。

**因果。** 生成文字时，一个 token 只能看它自己和它前面的 token，不能看后面的，因为后面的还没生成出来。“因果掩码”就是把“未来位置”的分数设成 −∞，softmax 之后它们的权重正好是 0。

**注意力头。** 不是用一整个 5120 维的 q 去做一次注意力，而是把 q、k、v 切成若干段，每一段独立做一次注意力，最后把各段的结果拼起来。每一段叫一个“头”，段的长度叫头维度（`head_dim`）。不同的头可以各自关注不同的东西，比如一个头看语法关系，另一个头看指代。Qwen3.8 的全注意力有 24 个查询头。

**分组查询注意力（GQA）。** 让几个查询头共用同一组键和值，以减少要存的 k、v。Qwen3.8 的全注意力有 24 个查询头、4 组键值，每 6 个查询头共用一组。

**线性注意力。** 普通注意力每生成一个 token 都要和前面所有 token 比一遍，上下文越长越慢。线性注意力换了一种做法：不保留所有 token 的 k、v，而是维护一个固定大小的“状态”矩阵，每来一个 token 就按某个规则更新一次状态，输出从状态里读出来。Qwen3.8 用的更新规则叫“门控 delta 规则”，第 4 章再讲。

**门控。** 用另一个向量经过 sigmoid 或 silu 得到一组 0 到 1 附近的系数，逐元素乘在输出上，决定“放多少过去”，像一个可以调节开度的阀门。

**位置编码。** 注意力本身只看 q 和 k 的点积，不知道两个 token 谁前谁后、相隔多远。位置编码把位置信息加进 q 和 k 里。Qwen3.8 用的是 RoPE，按位置把向量旋转一个角度，后面单独讲。

**logits 和采样。** 最后一层之后，再用一个线性层（`lm_head`）把每个向量映射成 248320 个数，每个 token 一个分数，叫 logits。用 softmax 把它们变成概率，再按概率挑出下一个 token。每次挑概率最大的叫贪心解码；按概率随机挑叫采样。

## 读懂 config.json

做哪些算子，不能凭印象。我们手里有三份互相印证的材料：

1. 模型目录里的 `config.json`：模型的“规格书”，写着层数、维度、头数这些数。
2. transformers 库里对应的建模代码：写着这些数怎么用，也就是计算的公式。
3. 权重文件里的张量名和形状（第 1 章读出来的）：最终的事实。代码里有一个线性层，权重里就一定有一个形状对得上的矩阵。

三者有一处对不上，就说明我们读错了某个地方。这一节先读第一份。

### 文件的整体结构

Qwen3.8-27B 的 `config.json` 有 4312 字节（SHA-256 `191e0af2…7203aab`），去掉 64 行的 `layer_types` 之后，骨架是这样的：

```json
{
    "architectures": ["Qwen3_5ForConditionalGeneration"],
    "model_type": "qwen3_5",
    "transformers_version": "5.8.0.dev0",
    "language_model_only": false,
    "tie_word_embeddings": false,
    "image_token_id": 248056,
    "video_token_id": 248057,
    "vision_start_token_id": 248053,
    "vision_end_token_id": 248054,
    "text_config":   { … 语言模型 … },
    "vision_config": { … 图像编码器 … }
}
```

最外层的几个字段决定“去哪里找代码”：

- **`model_type`** 是 `qwen3_5`。transformers 按这个名字找到 `models/qwen3_5/` 目录，里面的 `configuration_qwen3_5.py` 定义每个字段的默认值和含义，`modeling_qwen3_5.py` 定义计算。这个名字说明 Qwen3.8 沿用的是 Qwen3.5 的架构代码。
- **`architectures`** 是 `Qwen3_5ForConditionalGeneration`，即“图像加文字”的多模态模型（多模态指能同时处理不止一种输入，这里是文字和图像）。所以配置分成 `text_config` 和 `vision_config` 两半，这和第 1 章看到的张量名前缀一致：`model.language_model.` 是语言模型，`model.visual.` 是图像编码器。
- **`transformers_version`** 是保存这份配置的 transformers 版本。我们读的建模代码是 5.23.0 版，比它新。同一个字段在不同版本里的用法可能不同（第 2 章就遇到过参考库随版本变化的例子），所以下面凡是说“代码怎么用这个字段”，指的都是 5.23.0 版，以后对拍时要用和模型配套的版本再核对。
- 四个 `*_token_id` 是图像、视频的占位 token，也就是第 2 章对话模板里的 `<|image_pad|>`、`<|vision_start|>` 等。纯文本推理用不到。

第一卷只做文字，所以 `vision_config` 整个跳过：它描述的是一个 27 层、宽 1152 的图像编码器（把图片变成一串向量的网络），`out_hidden_size` 是 5120，意思是它的输出最终要变成和文字 token 一样宽的向量，混进语言模型里。

### text_config：语言模型

下面是 `text_config` 的全部字段，按用途分组。“代码”一列指 5.23.0 版 `modeling_qwen3_5.py` 里用到它的地方。

**整体规模**

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `vocab_size` | 248320 | 词表大小，也是嵌入表和输出层的行数。真正的 token 只有 248077 个，多出的 243 行是填充（第 2 章） |
| `hidden_size` | 5120 | 残差流的宽度：每个 token 在层与层之间传递的向量长度 |
| `num_hidden_layers` | 64 | 层数。“hidden”指输入和输出之间的那些层 |
| `intermediate_size` | 17408 | 前馈层中间那一段的宽度（先变宽再变回来），约为 `hidden_size` 的 3.4 倍 |
| `hidden_act` | `silu` | 前馈层和线性注意力卷积后的激活函数 |
| `rms_norm_eps` | 1e-06 | 所有 RMSNorm 的 eps：加在分母里的一个很小的数，防止除以 0（L2 归一化的 eps 不用它，在代码里写死为 1e-6） |
| `tie_word_embeddings` | false | 输出层不复用嵌入表（有的模型让输入的嵌入表和输出层共用同一个矩阵以节省参数，这里没有）。所以权重里有单独的 `lm_head.weight`，形状和嵌入表一样是 [248320, 5120] |
| `dtype` | `bfloat16` | 权重的类型。第 1 章已确认 27B 的 1199 个张量全是 BF16 |

**层的排布**

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `layer_types` | 64 项 | 每一层用哪种注意力：`linear_attention` 或 `full_attention`，按“3 个线性、1 个全注意力”重复 16 次 |
| `full_attention_interval` | 4 | 同一件事的另一种写法：每 4 层一个全注意力。代码只在没给 `layer_types` 时才用它来生成那 64 项 |

两个字段说的是同一件事，以 `layer_types` 为准。我们的代码读 `layer_types`，不自己按间隔推算。这样即使以后某个模型的排布不规则，也不会算错。

**全注意力层**（16 层）

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `num_attention_heads` | 24 | 查询头数（每个头独立做一次注意力） |
| `num_key_value_heads` | 4 | 键值头数。每 6 个查询头共用一组键值（分组查询注意力，GQA） |
| `head_dim` | 256 | 每个头的维度，即每个头的 q、k、v 各有多长 |
| `attention_bias` | false | q、k、v、o 四个投影（o 是把各头结果合并回 5120 维的输出投影）都没有偏置项，权重里也就没有 `*.bias` |
| `attn_output_gate` | true | 注意力的输出要乘一个门控（一组 0 到 1 之间的系数，决定每一维放多少过去） |
| `attention_dropout` | 0.0 | dropout 是训练时随机丢掉一部分数值以防过拟合的技巧，推理时不用 |

`head_dim` 值得多看一眼：24 × 256 = 6144，不等于 `hidden_size` 的 5120。很多模型的头维度是 `hidden_size / num_attention_heads` 算出来的，这里是单独给定的，所以 q 投影把 5120 维映射到更宽的 6144 维，o 投影再映射回 5120。如果凭“头维度 = 宽度 / 头数”的印象来写，会得到 5120 / 24 ≈ 213.3，根本不是整数。第 1 章的权重形状也能印证这一点：q_proj 是 [12288, 5120]，k_proj 是 [1024, 5120]。12288 = 24 × 256 × 2，多出来的那个 2 就是门控：每个头除了 256 维的 q，还要产出 256 维的门控。1024 = 4 × 256。

`attn_output_gate` 是个有意思的字段。5.23.0 版的代码里没有任何地方读它：门控是无条件写在 `Qwen3_5Attention` 里的。也就是说，把它改成 false，transformers 照样会乘门控。配置里的字段并不全是“开关”，有的只是记录。判断一个字段到底起不起作用，只能去读代码。

**线性注意力层**（48 层）

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `linear_num_key_heads` | 16 | 线性注意力 q、k 的头数 |
| `linear_num_value_heads` | 48 | v 的头数。每个 q/k 头服务 3 个 v 头，道理和 GQA 一样 |
| `linear_key_head_dim` | 128 | q、k 每个头的维度 |
| `linear_value_head_dim` | 128 | v 每个头的维度 |
| `linear_conv_kernel_dim` | 4 | 因果卷积的长度：每个位置的输出由它自己和前面 3 个 token 加权求和得到 |
| `output_gate_type` | `swish` | 输出门控用的激活函数。swish 是 silu 的另一个名字 |
| `mamba_ssm_dtype` | `float32` | 线性注意力的状态矩阵用什么精度保存 |

这几个数同样能和权重形状对上：`in_proj_qkv` 是 [10240, 5120]，10240 = 16 × 128（q）+ 16 × 128（k）+ 48 × 128（v）；卷积核是 [10240, 1, 4]，每个通道（10240 维向量里的每一维）一个长度为 4 的核。注意 transformers 里这个字段的默认值是 32，而 27B 是 48，同系列不同尺寸的模型并不一样，所以必须读文件，不能用默认值。

`output_gate_type` 和 `mamba_ssm_dtype` 在 5.23.0 版的 `qwen3_5` 代码里也没人读。前者与代码里写死的 silu 一致。后者说的是线性注意力的状态矩阵要用 float32 保存，而代码在计算 delta 规则时本来就把所有输入转成了 float32。这一项第 4 章还要再看。`mamba` 这个名字来自另一类同样带“状态”的模型，大约是训练代码沿用的名字。

**位置编码**

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `max_position_embeddings` | 262144 | 支持的最长上下文（模型一次能看到的 token 数，包括输入和已经生成的部分），2¹⁸ 个 token |
| `rope_parameters.rope_type` | `default` | 标准的 RoPE。别的取值会调整旋转频率，让模型能处理比训练时更长的上下文（叫长度外推），这里没有用 |
| `rope_parameters.rope_theta` | 10000000 | 频率的底数 θ，决定各维度对旋转得有多快 |
| `rope_parameters.partial_rotary_factor` | 0.25 | 只转每个头的前 25%，即 256 × 0.25 = 64 维 |
| `rope_parameters.mrope_section` | [11, 11, 10] | mrope 是给图像和视频用的多维位置编码：64 维分成 32 对，分给时间、高、宽三个方向 |
| `rope_parameters.mrope_interleaved` | true | 三个分量交错分配，而不是分成连续的三段 |
| `partial_rotary_factor`（`text_config` 顶层） | 0.25 | 与上面那个重复，旧版本留下的写法 |

`partial_rotary_factor` 出现了两次，值相同。代码读的是 `rope_parameters` 里的那个。重复的字段是隐患：哪天两边不一致，就要靠读代码才知道哪个算数。我们的测试脚本只读 `rope_parameters` 里的那个，和代码一致。

mrope 的两个字段在纯文本时不起作用，原因见后面 RoPE 一节。

**多 token 预测**

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `mtp_num_hidden_layers` | 1 | 额外的一层“多 token 预测”模块 |
| `mtp_use_dedicated_embeddings` | false | 这个模块不用单独的嵌入表 |

这是第 1 章看到的 15 个 `mtp.` 开头的张量。它训练时用来让模型一次预测好几个 token，推理时可以用来做“投机解码”加速：先快速猜出后面几个 token，再让完整的模型一次性检查这些猜测，猜对的就不用再一个个算。transformers 5.23.0 加载权重时明确忽略所有 `mtp.` 开头的张量（`_keys_to_ignore_on_load_unexpected`），普通的逐 token 生成也用不到它，第一卷跳过。

**特殊 token 和其他**

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `bos_token_id` | 248044 | 序列开头（begin of sequence）的 token，这里是 `<|endoftext|>` |
| `eos_token_id` | 248044 | 序列结束（end of sequence）的 token，模型输出它表示说完了 |
| `pad_token_id` | null | 填充用的 token：几条长短不一的输入一起算时，用它把短的补齐。这里没有指定 |
| `use_cache` | true | 生成时默认使用缓存：把已经算过的 token 的中间结果存起来，下一个 token 不用从头再算（第 6 章） |
| `initializer_range` | 0.02 | 训练开始前随机生成初始权重时用的标准差，推理用不到 |

`eos_token_id` 是 248044，但对话时模型说完一句话输出的是 `<|im_end|>`（248046）。真正决定“什么时候停”的是另一个文件。

### generation_config.json

模型目录里还有一个 202 字节的 `generation_config.json`（SHA-256 `e70c136c…c70be550e`），它不描述模型的结构，而是描述“官方建议怎么生成”：

```json
{
    "bos_token_id": 248044,
    "do_sample": true,
    "eos_token_id": [248046, 248044],
    "pad_token_id": 248044,
    "temperature": 1.0,
    "top_k": 20,
    "top_p": 0.95
}
```

- `eos_token_id` 是两个：`<|im_end|>` 和 `<|endoftext|>`，输出其中任何一个都算结束。第 6 章的停止条件以这里为准，而不是 `config.json` 里的那一个。
- `do_sample`、`temperature`、`top_k`、`top_p` 是默认的采样参数：`do_sample` 为真表示按概率随机挑而不是总挑最大的；`temperature` 调节概率分布的“尖锐”程度，1.0 表示不调；`top_k` 是只在概率最高的 20 个 token 里挑；`top_p` 是在这 20 个里再只保留累计概率达到 95% 的那几个。第 6 章实现采样时会用到。第 5 章做整模对拍时我们用贪心解码（每次取概率最高的），不用这些参数，因为随机采样没法逐 token 对拍。

### 从配置到算子

把上面的字段和建模代码对照起来，就得到了这一章要实现的算子和它们的维度。下一节把它们整理成一张清单。第 4 章加载模型时，我们的代码会从 `config.json` 读这些数，而不是写死；读到不认识的取值，比如 `rope_type` 不是 `default`、`hidden_act` 不是 `silu`，就报错，这和第 2 章只接受 Qwen 那一种分词器配置是同一个原则。这一章的真实权重测试已经在这样做：eps、θ、旋转维数、层的类型都从文件里读。

## 先看模型由哪些算子组成

这一节的结构和公式来自 transformers 5.23.0 版的 `models/qwen3_5/modeling_qwen3_5.py`，数字来自上一节的 `config.json` 和第 1 章读出的权重形状。

整个模型是 64 层，每层的骨架相同：

```
h = 嵌入(token id)                                        [n, 5120]
重复 64 次：
    h = h + 注意力(RMSNorm(h))       ← 第 4、8、12 … 层是全注意力，其余 48 层是线性注意力
    h = h + 前馈(RMSNorm(h))
logits = 线性(RMSNorm(h))                                 [n, 248320]
```

每 4 层一组，前 3 层是“线性注意力”，第 4 层是普通的“全注意力”。两种注意力用到的算子不同。

**前馈层**（每层都有）：

```
前馈(x) = down( silu(gate(x)) * up(x) )        gate、up: 5120 → 17408，down: 17408 → 5120
```

**全注意力层**（16 层）：24 个查询头、4 个键值头，每个头 256 维。

```
[q, 门控] = q_proj(x)            5120 → 24 × (256 + 256)，每个头的 512 维里前一半是 q，后一半是门控
k = k_proj(x), v = v_proj(x)     5120 → 4 × 256
q, k 各自按头做 RMSNorm（256 维）
q, k 做 RoPE，只转每个头的前 64 维
每个头：softmax(q kᵀ / 16 + 因果掩码) v      16 = √256
输出 × sigmoid(门控)，再 o_proj: 24×256 → 5120
```

**线性注意力层**（48 层）：16 个键头、48 个值头，每个头 128 维。

```
qkv = in_proj_qkv(x)            5120 → 2×16×128 + 48×128 = 10240
qkv = silu(因果卷积(qkv))         每个通道独立，卷积核长 4
q, k 做 L2 归一化（每个头 128 维）
β = sigmoid(in_proj_b(x)),  g = -exp(A_log) · softplus(in_proj_a(x) + dt_bias)
门控 delta 规则（每个头维护一个 128 × 128 的状态矩阵，逐 token 更新，第 4 章）
输出做带门控的 RMSNorm（门控来自 in_proj_z(x)），再 out_proj: 48×128 → 5120
```

把这些式子里的运算收集起来，就是本章要做的算子：

| 算子 | 用在哪里 |
| --- | --- |
| BF16 转 float | 所有权重 |
| 嵌入（按 id 取行） | 模型入口 |
| 矩阵乘（线性层） | 所有投影、前馈、输出层 |
| RMSNorm（1 + w 形式） | 每层两次、最终归一化、q/k 归一化 |
| 带门控的 RMSNorm（w 形式） | 线性注意力的输出 |
| L2 归一化 | 线性注意力的 q、k |
| silu、sigmoid、softplus | 前馈、门控、线性注意力 |
| softmax | 全注意力 |
| RoPE（部分维度） | 全注意力的 q、k |
| 因果一维卷积 | 线性注意力 |

逐元素的加法和乘法（残差、`silu(gate) * up`）太简单，不单列。门控 delta 规则和注意力本身是把这些算子组合起来的过程，放到第 4 章。

## 数据怎么放

所有激活值（每一步的输入和输出）都是 `float`，按行主序连续存放。形状 `[n, d]` 的张量，第 `t` 行第 `i` 列在 `x[t * d + i]`。

权重是另一回事。27B 的权重全部是 BF16，共约 52 GiB；如果先全部转成 float，就是 104 GiB。所以大矩阵（嵌入表和所有线性层）不转换，算子直接从第 1 章 mmap 进来的原始字节里读：

```c
uint16_t bf16_at(const uint8_t *p, size_t i) {
    return (uint16_t)(p[2 * i] | p[2 * i + 1] << 8);
}
```

这里又一次逐字节拼，而不是把指针强转成 `uint16_t *`。原因和第 1 章读头长度时一样：safetensors 只规定了 `data_offsets` 是字节偏移，不保证对齐。一个张量的数据完全可能从奇数地址开始，按 `uint16_t *` 去读就是未定义行为。测试数据里专门在 JSON 头后面补了一个空格，让数据区从奇数偏移开始，开着 UBSan 跑。

小向量（归一化的权重、卷积核）只有几千个数，由调用方先转成 float 再交给算子，算子的代码因此简单一些。

线性层权重的形状是 `[out, in]`，每个输出一行，和 PyTorch 的 `nn.Linear` 一样。所以矩阵乘是 `y[t][o] = Σᵢ x[t][i] · w[o][i]`，读权重时沿着一行连续地读。

## BF16

BF16 是 float 的“高半截”：1 位符号、8 位指数、7 位尾数，指数的范围和 float 一样，只是尾数从 23 位砍到了 7 位。所以 BF16 转 float 只要把 16 位数左移 16 位，放到 float 的高半截，低半截补 0，转换是精确的：

```c
float bf16_to_f32(uint16_t h) {
    uint32_t u = (uint32_t)h << 16;
    float f;
    memcpy(&f, &u, sizeof f);
    return f;
}
```

`memcpy` 而不是 `*(float *)&u`，是为了不违反 C 的别名规则（C 标准不允许通过 `float *` 去读一个 `uint32_t` 对象，编译器会据此做优化，结果可能出错）。编译器会把这个 `memcpy` 优化成一条寄存器移动指令。

16 位只有 65536 种取值，所以这个函数可以穷举测试：C 和 Python 各自把 65536 个位模式全部转一遍，输出 float 的位模式，逐字节比较。Python 那边刻意不用移位，而是按定义从符号、指数、尾数算出数值。其中指数位全为 0 的是“非规格化数”：比最小的正常数还小、精度逐渐降低的那一段极小值，公式和正常数不同。

```python
if e == 0:   return sign * math.ldexp(m, -133)          # 非规格化数：m/128 · 2^-126
else:        return sign * math.ldexp(128 + m, e - 134) # (1 + m/128) · 2^(e-127)
```

NaN（not a number，比如 0/0 的结果）是唯一需要特别说明的地方。NaN 的尾数（“载荷”）不是数值，按定义算不出来。IEEE 754 规定把窄格式的 NaN 扩宽时保留符号和载荷，载荷放在高位，Python 那边按这条规则写出位模式。

## 用 double 算

这一章最重要的一个决定是：**算子内部全部用 double 计算，最后才舍入成 float。**

这不是为了模型的精度。模型训练时用的就是 BF16 和 float，用 double 算并不会让它“更聪明”。这样做是因为这一版 CPU 实现的角色：后面的每一章，包括第 7 章的 GPU 内核，都要拿它当标尺来比。标尺本身的误差越小，比较时就越能分清“GPU 内核写错了”和“只是舍入不同”。

用 double 的代价不大。以矩阵乘为例，`float` 乘 BF16 的乘积最多需要 24 + 8 = 32 位尾数，double 有 53 位，所以每一个乘积都是**精确**的，误差只来自求和。double 求和 17408 项（前馈层 down 投影的长度），误差上界约为 17408 × 2⁻⁵³ ≈ 2⁻³⁹ 倍的“各项绝对值之和”，比 float 自己的舍入误差（2⁻²⁴）小五个数量级。于是最终结果几乎就是“精确值舍入到 float”。

其他算子也一样：RMSNorm 的平方和、softmax 的分母、卷积的四项乘加都在 double 里做；`exp`、`cos`、`sin` 调的是 double 版的库函数，误差在 double 的 1 个 ulp 左右，舍入到 float 之后看不见。

## 误差要多小才算对

浮点运算有舍入，两份实现的结果一般不会逐位相同，对拍时必须允许一点误差。允许多少，是这一章的核心问题：定得太松，真正的错误会混过去；定得太紧，正确的实现也过不了。

**ulp。** 先定义一个单位。float 能表示的数是离散的，在 1 附近相邻两个 float 相差 2⁻²³，在 1024 附近相差 2⁻¹³。某个数附近相邻两个 float 的间距叫这个数的 ulp（unit in the last place）。把一个精确值舍入到最近的 float，误差最多是半个 ulp，这是 float 能做到的最好结果。

**标准。** 参考实现用 Python 的 float（就是 double）计算每个输出的精确值 r，求和一律用 `math.fsum`（它返回的是精确和的正确舍入）。C 的输出 g 是 float。判定标准是：

```
|g − r| ≤ ulp(r) + 2⁻³² · s
```

第一项是 1 个 ulp：正确舍入只要半个，多给半个是为了容纳 double 计算本身的那一点误差。第二项里的 s 是这个结果所有求和项的绝对值之和，它只在一种情况下起作用：求和项大量抵消，结果 r 比各项小得多。这时 r 的 ulp 很小，而 double 求和的误差是按各项的大小算的，可能超过 r 的 1 个 ulp。2⁻³² 比前面估计的 2⁻³⁹ 留了 100 多倍的余量。

**为什么不用更宽松的、教科书式的界。** 浮点误差分析给出过一个经典的上界：用 float 顺序求和 n 项，误差不超过 n · 2⁻²⁴ · s。按这个界定容差，看起来很“有理论依据”。但算一下：n = 17408 时，n · 2⁻²⁴ ≈ 10⁻³。而一个常见的错误，求和时漏掉一项，造成的误差大约是 s / n ≈ 6 × 10⁻⁵ · s，远小于 10⁻³ · s。也就是说，按最坏情况的界定容差，**漏掉一项的矩阵乘照样能通过**。最坏情况的界是对“所有可能的正确实现”成立的保证，拿来做对拍的容差就太松了。

我们选的是反过来的思路：先让实现足够精确（double），再把容差收到“只比正确舍入多一点”。这样，任何偏离精确值超过 1 个 ulp 的实现都会被抓出来，不管它是写错了还是精度不够。

**试一试。** 为了确认测试真的能抓住错误，我们故意把算子改坏，看测试是否失败：

| 故意引入的错误 | 结果 |
| --- | --- |
| 矩阵乘改用 float 累加 | 失败：7 项的小矩阵乘里就有 3 个元素超过 1 ulp |
| 矩阵乘漏掉第一项 | 失败 |
| RMSNorm 把 `1 + w` 写成 `w` | 失败 |
| RMSNorm 去掉 eps | 失败：全零的行变成 NaN，数值在 1 附近的行也差了几个 ulp |
| softmax 不减最大值 | 失败：数值约为 10⁴ 的那一行溢出成 NaN |
| 卷积核方向反了 | 失败 |
| RoPE 第二半的符号反了 | 失败 |
| RoPE 位置大于 1000 时差一 | 失败 |
| RoPE 用 float 计算 | 失败：240 个元素里有 8 个超过 1 ulp |

第一行和最后一行最能说明问题：它们不是“写错了”，只是精度差一点。用常见的 1e-3 相对误差做容差，它们都会通过；而它们一旦混进标尺，第 7 章 GPU 版的误差就没法和标尺的误差分开了。

## 各个算子

代码在 [`src/ops.h`](../src/ops.h) 和 [`src/ops.c`](../src/ops.c)，每个算子都是最直接的几重循环。这里只讲容易写错的地方。

### 矩阵乘

```c
for (size_t t = 0; t < n; t++)
    for (size_t o = 0; o < out; o++) {
        const uint8_t *row = w + 2 * o * in;
        double acc = 0;
        for (size_t i = 0; i < in; i++) acc += (double)x[t * in + i] * (double)bf16_to_f32(bf16_at(row, i));
        y[t * out + o] = (float)acc;
    }
```

三重循环，没有分块，没有多线程。它很慢：开着 ASan，一个 token 乘 10240 × 5120 的矩阵要 0.3 秒左右，按这个速度 27B 的一个 token 要算几分钟。但它一眼就能看出对不对，这是第一卷要的。

测试用例里有一个专门的“抵消”矩阵：x 的两列几乎相等，权重的两列互为相反数，结果比各项小好几个数量级，用来检验容差里第二项的设计。还有一个各项的数量级从 10⁻²⁰ 跨到 10²⁰ 的用例。

### 嵌入

按 id 取出嵌入表的一行，转成 float。它是纯拷贝，所以要求逐位相等，包括负零。测试用的嵌入表里放了 NaN、正负无穷、非规格化数和负零。

id 不在 `[0, 行数)` 里就报错。注意 Qwen3.8 的嵌入表有 248320 行，而真正的 token 只有 248077 个（第 2 章），多出来的 243 行在这个算子看来也是合法的行。判断一个 id 是不是真正的 token，是分词器的事。

### 两种 RMSNorm

RMSNorm 把一行数缩放到“均方根为 1”，再乘上一组可学习的权重。Qwen3.8 里有两种写法，差别只在权重怎么用，却很容易混淆：

```
RMSNorm(x)        = x / √(mean(x²) + eps) · (1 + w)        每层两次、最终归一化、q/k 归一化
带门控的 RMSNorm(x, z) = x / √(mean(x²) + eps) · w · silu(z)    线性注意力的输出
```

第一种是“零中心”的：权重存的是与 1 的差，初始化为 0，全零的权重表示不缩放。第二种的权重初始化为 1，直接相乘。两种都在官方代码里写得清清楚楚（`Qwen3_5RMSNorm` 和 `Qwen3_5RMSNormGated`），但如果凭 Llama 等其他模型的印象来写，第一种很容易写成 `· w`。拿真实权重验收时，我们本想用这几组权重的均值做一个不依赖参考实现的旁证：零中心的应当在 0 附近，带门控的应当在 1 附近。结果这个旁证并不可靠，见“在真实权重上验证”一节。

eps 从 `config.json` 的 `rms_norm_eps` 读，不写死。它的作用是兜底：一行全是 0 时，没有 eps 就是 0 / 0。测试里专门放了全零的行和数值在 10⁻⁶ 量级的行。

### L2 归一化

```
L2(x) = x / √(Σx² + eps)
```

和 RMSNorm 的区别是 Σ 而不是 mean，没有权重。线性注意力对 q 和 k 用它，eps 在官方代码里固定是 10⁻⁶，不来自配置。

### silu、sigmoid、softplus

```
silu(x)     = x / (1 + e⁻ˣ)
sigmoid(x)  = 1 / (1 + e⁻ˣ)
softplus(x) = ln(1 + eˣ)
```

难点在极端值。double 的 `exp` 在参数超过约 709 时溢出成无穷大。silu 和 sigmoid 的写法恰好不怕：e⁻ˣ 溢出时分母是无穷大，结果是 0，正是极限值。softplus 照定义写就有问题：x = 1000 时 eˣ 溢出，ln(∞) = ∞，而正确答案是 1000。我们把它改写成数学上相等的形式：

```
softplus(x) = max(x, 0) + ln(1 + e^(−|x|))
```

这样 `exp` 的参数永远不大于 0，不会溢出，而 `log1p` 在参数很小时也是精确的。

PyTorch 的 `softplus` 有一个“阈值”参数，默认 x > 20 时直接返回 x。这和精确值差 ln(1 + e⁻²⁰) ≈ 2 × 10⁻⁹，而 float 在 20 附近的 ulp 是 2 × 10⁻⁶，舍入到 float 后完全看不出区别。

测试输入除了正常范围的随机数，还有 0、负零、10⁻⁴⁵（float 最小的非规格化数）、±20、±88、±89（float 版 `exp` 溢出的边界）、±745（double 版 `exp` 下溢的边界）、±10³⁰、±3.4 × 10³⁸。

### softmax

```
softmax(x)ᵢ = e^(xᵢ − m) / Σⱼ e^(xⱼ − m)，m = max(x)
```

减去最大值在数学上不改变结果，但不减的话，x 里只要有一个数大于 709，`exp` 就溢出，结果变成 NaN。测试里有一行数值都在 10⁴ 左右。

全注意力的因果掩码会把“未来位置”的分数设成 −∞，e^(−∞) = 0，正好是想要的效果。测试里有一行混着 −∞。

### RoPE

旋转位置编码把 q 和 k 的维度两两配对，每一对看成平面上的一个点，按 token 的位置转一个角度。位置越远，转得越多；不同的维度对，转速不同。这样 q 和 k 的点积就只和两个 token 的相对位置有关。

Qwen3.8 的 RoPE 有三处要注意。

**配对方式。** 每个头的前 `rot` 维分成前后两半，第 i 维和第 i + rot/2 维配成一对，不是相邻的第 2i、2i+1 维。两种配法都有模型在用，配错了不会报错，只是位置信息全乱了。官方代码里对应的是 `rotate_half`。

**只转一部分。** `partial_rotary_factor` 是 0.25，每个头 256 维里只转前 64 维，后 192 维原样保留。

**频率。** 第 i 对的转速是 `theta^(−2i/rot)`，`theta` 是 `rope_theta`，等于 10⁷。第 0 对每个位置转 1 弧度，最后一对每个位置只转约 1.6 × 10⁻⁷ 弧度。

还有一处看起来复杂、其实可以简化的地方。官方代码里的 RoPE 叫 “mrope”：为了处理图像和视频，位置有三个分量（时间、高、宽），64 维里的 32 对按 `mrope_section = [11, 11, 10]` 交错地分给三个分量。但对纯文本，三个分量都等于 token 的序号，交错分配之后每一对拿到的还是同一个位置。所以在本书处理图像之前，RoPE 就是上面这个普通的一维形式。

测试的位置包括 0（不转，输出必须等于输入）和 262143（`max_position_embeddings` 减 1）。

### 因果一维卷积

线性注意力在投影之后，对 10240 个通道各自做一次长度为 4 的卷积：每个通道的输出，是这个通道当前 token 和前 3 个 token 的加权和。“因果”指只看过去，不看未来；序列开头之前的 token 当作 0。

```
y[t][j] = Σᵢ w[j][i] · x[t − 3 + i][j]，i = 0 … 3
```

最容易错的是卷积核的方向：`w[j][3]` 乘的是**当前** token，`w[j][0]` 乘的是往前数第 3 个。这是因为 PyTorch 的 `conv1d` 其实是互相关：数学上的卷积要把卷积核倒过来再乘，互相关不倒，深度学习里习惯把后者也叫卷积。权重在文件里的形状是 `[10240, 1, 4]`，中间那一维是分组卷积的写法（每个通道自成一组，只和自己做卷积），我们也接受 `[c, k]`。

Python 参考实现故意换了一种写法：按“往前数第几个 token”来索引，`w[j][k-1-back]` 乘 `x[t-back]`，与 C 的写法不同但应当相等。测试里有一个只有 2 个 token 的用例，比卷积核还短。

## 不信任输入

算子本身假定参数是合法的；检查放在调用它们的工具 [`tools/ops.c`](../tools/ops.c) 里，因为形状来自文件。第 4 章写真正的推理代码时，这些检查会移到加载模型的地方。

| 检查 | 防的是什么 |
| --- | --- |
| 激活值必须是 F32，维数符合算子要求，不能为空 | 把 BF16 的字节当成 float 读 |
| 矩阵乘的权重必须是二维 BF16，列数等于输入的长度 | 越界读权重 |
| 归一化的权重长度必须等于输入的最后一维 | 同上 |
| 门控 z 的形状必须与输入相同 | 同上 |
| 位置、token id 必须是 I32，个数等于 token 数 | 同上 |
| token id 必须在嵌入表的范围内 | 读到表外 |
| 卷积核必须是 `[c,k]` 或 `[c,1,k]`，c 等于通道数 | 同上 |
| `rot` 必须是正偶数且不超过 head_dim；`theta` 必须为正；`eps` 必须是非负的有限数 | 静默地算出无意义的结果 |
| 标量参数没有默认值，不认识的参数、重复的参数都报错 | 拼错一个参数名，悄悄用了默认值 |

最后一条值得说一下：eps、theta 这些数，只要给错一点，结果就会差一点，不会崩溃。所以工具不提供默认值，每次都要从模型的配置里读出来明确给出。

## 如何验证正确

测试的结构和前两章相同，只是比较方式从“逐字节相同”换成了“逐元素在容差内”。

- [`tests/make_ops_fixtures.py`](../tests/make_ops_fixtures.py) 生成输入：每个用例一个小 safetensors 文件，装着这个算子的输入张量，再写一份用例清单。用 safetensors 是因为第 1 章的读取器现成可用，而且下一节换成真实权重时，权重本来就在 safetensors 里。
- [`tools/ops.c`](../tools/ops.c) 读输入、调用算子，输出结果。每个数用 C 的 `%a` 格式打印，比如 `0x1.99999ap-4`。这是十六进制的浮点数，精确无损，Python 用 `float.fromhex` 读回来。
- [`tests/ops_ref.py`](../tests/ops_ref.py) 读同样的输入，用双精度独立地算出精确值，与 C 的输出逐元素比较，报告最大误差是多少个 ulp。

两份实现故意写得不一样：BF16 一边移位、一边按定义算；求和一边是 double 顺序累加、一边是 `math.fsum`；卷积按不同的方向索引；silu 一边是 `x / (1 + e⁻ˣ)`、一边是 `x · sigmoid(x)`，其中 sigmoid 按正负分两支算。

两边错成一样的可能依然存在，所以和第 1 章的 CRC-32 测试向量一样，还有几个不依赖 Python 的已知答案：BF16 的 `3f80` 是 1.0，`0001` 是 2⁻¹³³；四个相等的数做 softmax，每个结果恰好是 1/4，即 `0x1p-2`。

另有 25 个必须被拒绝的输入，对应上一节表格里的每一条。

## 在真实权重上验证

自造的输入覆盖了每条规则，但维度都很小。真实权重的验收拿 Qwen3.8-27B 的张量直接当算子的输入：

```
make test-ops-real MODEL=/data/models/Qwen3.8-27B
```

[`tests/make_ops_real.py`](../tests/make_ops_real.py) 从 `config.json` 读出 eps、theta、head_dim 和层的类型，按模型的真实维度生成激活值一侧的输入，然后对下面这些张量各跑一次算子：嵌入表（取几个普通 token、特殊 token 和最后一行填充）、第 0 层的输入归一化和最终归一化（输入是真实的嵌入行）、全注意力层的 q 归一化、线性注意力层的门控归一化、三个大矩阵（线性注意力的输入投影 10240 × 5120、全注意力的 q 投影 12288 × 5120、前馈的 down 投影 5120 × 17408）、卷积核，以及位置最大到 262143 的 RoPE。

## 与官方实现的差别

我们的算子是“数学上的精确值”，而官方的 transformers 在 BF16 模式下运行时，每一步都会把中间结果舍入成 BF16。读官方代码时注意到的几处：

- 线性层的输出、RMSNorm 的输出都是 BF16（只有 7 位尾数，相对误差约 0.4%）。
- 带门控的 RMSNorm 先把归一化结果舍入成 BF16，再乘权重和门控。
- RoPE 的频率和角度用 float 计算，再把 cos 和 sin 舍入成 BF16。位置在 10⁵ 量级时，float 计算角度本身就有 10⁻² 弧度量级的误差。

这些差别意味着，我们的输出和官方的输出不会逐位相同，而且层数越多差得越远。第 4 章做单层对拍、第 5 章做整模对拍时，要面对“该和谁比、差多少算对”的问题。我们的打算是保持 CPU 版的精确性不变，在对拍时把官方的这些舍入考虑进去。第 4 章“和谁比、差多少算对”一节给出了具体的做法。

## 踩过的坑

**参考实现放过了 NaN。** 写完测试，我们把 softmax 的“减最大值”删掉，想看测试失败，结果测试通过了。那一行 10⁴ 量级的数明明已经溢出成 NaN，参考实现却报告“最大误差 0.00 ulp”。

原因在比较的写法：`if err > tol: 记为失败`。g 是 NaN 时，err 也是 NaN，而 NaN 和任何数比较都是假，所以永远不会被记为失败。改成 `if not err <= tol` 就对了。

这个错误不在被测的代码里，而在测试里，而且它会让所有算子的所有 NaN 输出都蒙混过关。如果不是故意把算子改坏来验证测试，它可能一直藏着。这也是为什么上面那张“故意引入的错误”的表值得做：**测试本身也需要被测试**。
