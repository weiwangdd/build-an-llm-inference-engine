# 第 3 章 张量与算子

> 状态：初稿。本章的代码已在自造的小输入上通过对拍，包括 BF16 全部 65536 个位模式的穷举；拿 Qwen3.8-27B 真实权重做输入的验收还没有做，见“在真实权重上验证”一节。

## 要解决的问题

前两章把权重读进了内存，把文字变成了 token id。从这一章开始，我们要让模型真正算起来。

一个大模型的前向计算，拆到底只是十来种基本运算反复组合：矩阵乘、归一化、几个激活函数、softmax、位置编码。这一章把它们一个一个写出来，每一个单独验收；下一章再把它们拼成一层，第 5 章拼成整个模型。

为什么要单独验收，而不是直接拼成一层再看结果？因为一层的输出错了，你只知道“错了”，不知道是哪一步。而且有些错误在整层的输出里根本看不出来：把 RMSNorm 的 `1 + w` 写成 `w`，模型照样输出一串数字，只是每一层都被缩小了几十倍。一个算子一个算子地比，出错的地方就是那个算子。

本章的验收标准：

**每个算子的每个输出元素，与精确值的误差不超过 float 的 1 个 ulp（加上一项只在大量抵消时起作用的余量）；纯拷贝的算子要求完全相等。**

这个标准比通常的“相对误差小于 1e-3”严得多。后面“误差要多小才算对”一节解释它从哪里来、为什么定这么严。

## 先看模型由哪些算子组成

做哪些算子，不能凭印象。Qwen3.8-27B 的 `config.json` 里 `model_type` 是 `qwen3_5`，官方的计算方式写在 transformers 库的 `models/qwen3_5/modeling_qwen3_5.py` 里（我们读的是 5.23.0 版）。这一节的结构和公式都来自这份代码，数字来自模型的 `config.json` 和第 1 章读出的权重形状。

整个模型是 64 层，每层的骨架相同：

```
h = 嵌入(token id)                                        [n, 5120]
重复 64 次：
    h = h + 注意力(RMSNorm(h))       ← 第 4、8、12 … 层是全注意力，其余 48 层是线性注意力
    h = h + 前馈(RMSNorm(h))
logits = 线性(RMSNorm(h))                                 [n, 248320]
```

每 4 层一组，前 3 层是“线性注意力”，第 4 层是普通的“全注意力”。两种注意力用到的算子不同。

**前馈层**（每层都有）：

```
前馈(x) = down( silu(gate(x)) * up(x) )        gate、up: 5120 → 17408，down: 17408 → 5120
```

**全注意力层**（16 层）：24 个查询头、4 个键值头，每个头 256 维。

```
[q, 门控] = q_proj(x)            5120 → 24 × (256 + 256)，每个头的 512 维里前一半是 q，后一半是门控
k = k_proj(x), v = v_proj(x)     5120 → 4 × 256
q, k 各自按头做 RMSNorm（256 维）
q, k 做 RoPE，只转每个头的前 64 维
每个头：softmax(q kᵀ / 16 + 因果掩码) v      16 = √256
输出 × sigmoid(门控)，再 o_proj: 24×256 → 5120
```

**线性注意力层**（48 层）：16 个键头、48 个值头，每个头 128 维。

```
qkv = in_proj_qkv(x)            5120 → 2×16×128 + 48×128 = 10240
qkv = silu(因果卷积(qkv))         每个通道独立，卷积核长 4
q, k 做 L2 归一化（每个头 128 维）
β = sigmoid(in_proj_b(x)),  g = -exp(A_log) · softplus(in_proj_a(x) + dt_bias)
门控 delta 规则（一个逐 token 更新的状态矩阵，第 4 章）
输出做带门控的 RMSNorm（门控来自 in_proj_z(x)），再 out_proj: 48×128 → 5120
```

把这些式子里的运算收集起来，就是本章要做的算子：

| 算子 | 用在哪里 |
| --- | --- |
| BF16 转 float | 所有权重 |
| 嵌入（按 id 取行） | 模型入口 |
| 矩阵乘（线性层） | 所有投影、前馈、输出层 |
| RMSNorm（1 + w 形式） | 每层两次、最终归一化、q/k 归一化 |
| 带门控的 RMSNorm（w 形式） | 线性注意力的输出 |
| L2 归一化 | 线性注意力的 q、k |
| silu、sigmoid、softplus | 前馈、门控、线性注意力 |
| softmax | 全注意力 |
| RoPE（部分维度） | 全注意力的 q、k |
| 因果一维卷积 | 线性注意力 |

逐元素的加法和乘法（残差、`silu(gate) * up`）太简单，不单列。门控 delta 规则和注意力本身是把这些算子组合起来的过程，放到第 4 章。

## 数据怎么放

所有激活值（每一步的输入和输出）都是 `float`，按行主序连续存放。形状 `[n, d]` 的张量，第 `t` 行第 `i` 列在 `x[t * d + i]`。

权重是另一回事。27B 的权重全部是 BF16，共约 52 GiB；如果先全部转成 float，就是 104 GiB。所以大矩阵（嵌入表和所有线性层）不转换，算子直接从第 1 章 mmap 进来的原始字节里读：

```c
uint16_t bf16_at(const uint8_t *p, size_t i) {
    return (uint16_t)(p[2 * i] | p[2 * i + 1] << 8);
}
```

这里又一次逐字节拼，而不是把指针强转成 `uint16_t *`。原因和第 1 章读头长度时一样：safetensors 只规定了 `data_offsets` 是字节偏移，不保证对齐。一个张量的数据完全可能从奇数地址开始，按 `uint16_t *` 去读就是未定义行为。测试数据里专门在 JSON 头后面补了一个空格，让数据区从奇数偏移开始，开着 UBSan 跑。

小向量（归一化的权重、卷积核）只有几千个数，由调用方先转成 float 再交给算子，算子的代码因此简单一些。

线性层权重的形状是 `[out, in]`，每个输出一行，和 PyTorch 的 `nn.Linear` 一样。所以矩阵乘是 `y[t][o] = Σᵢ x[t][i] · w[o][i]`，读权重时沿着一行连续地读。

## BF16

BF16 是 float 的“高半截”：1 位符号、8 位指数、7 位尾数，指数的范围和 float 一样，只是尾数从 23 位砍到了 7 位。所以 BF16 转 float 只要把 16 位数左移 16 位，放到 float 的高半截，低半截补 0，转换是精确的：

```c
float bf16_to_f32(uint16_t h) {
    uint32_t u = (uint32_t)h << 16;
    float f;
    memcpy(&f, &u, sizeof f);
    return f;
}
```

`memcpy` 而不是 `*(float *)&u`，是为了不违反 C 的别名规则。编译器会把这个 `memcpy` 优化成一条寄存器移动指令。

16 位只有 65536 种取值，所以这个函数可以穷举测试：C 和 Python 各自把 65536 个位模式全部转一遍，输出 float 的位模式，逐字节比较。Python 那边刻意不用移位，而是按定义从符号、指数、尾数算出数值：

```python
if e == 0:   return sign * math.ldexp(m, -133)          # 非规格化数：m/128 · 2^-126
else:        return sign * math.ldexp(128 + m, e - 134) # (1 + m/128) · 2^(e-127)
```

NaN 是唯一需要特别说明的地方。NaN 的尾数（“载荷”）不是数值，按定义算不出来。IEEE 754 规定把窄格式的 NaN 扩宽时保留符号和载荷，载荷放在高位，Python 那边按这条规则写出位模式。

## 用 double 算

这一章最重要的一个决定是：**算子内部全部用 double 计算，最后才舍入成 float。**

这不是为了模型的精度。模型训练时用的就是 BF16 和 float，用 double 算并不会让它“更聪明”。这样做是因为这一版 CPU 实现的角色：后面的每一章，包括第 7 章的 GPU 内核，都要拿它当标尺来比。标尺本身的误差越小，比较时就越能分清“GPU 内核写错了”和“只是舍入不同”。

用 double 的代价不大。以矩阵乘为例，`float` 乘 BF16 的乘积最多需要 24 + 8 = 32 位尾数，double 有 53 位，所以每一个乘积都是**精确**的，误差只来自求和。double 求和 17408 项（前馈层 down 投影的长度），误差上界约为 17408 × 2⁻⁵³ ≈ 2⁻³⁹ 倍的“各项绝对值之和”，比 float 自己的舍入误差（2⁻²⁴）小五个数量级。于是最终结果几乎就是“精确值舍入到 float”。

其他算子也一样：RMSNorm 的平方和、softmax 的分母、卷积的四项乘加都在 double 里做；`exp`、`cos`、`sin` 调的是 double 版的库函数，误差在 double 的 1 个 ulp 左右，舍入到 float 之后看不见。

## 误差要多小才算对

浮点运算有舍入，两份实现的结果一般不会逐位相同，对拍时必须允许一点误差。允许多少，是这一章的核心问题：定得太松，真正的错误会混过去；定得太紧，正确的实现也过不了。

**ulp。** 先定义一个单位。float 能表示的数是离散的，在 1 附近相邻两个 float 相差 2⁻²³，在 1024 附近相差 2⁻¹³。某个数附近相邻两个 float 的间距叫这个数的 ulp（unit in the last place）。把一个精确值舍入到最近的 float，误差最多是半个 ulp，这是 float 能做到的最好结果。

**标准。** 参考实现用 Python 的 float（就是 double）计算每个输出的精确值 r，求和一律用 `math.fsum`（它返回的是精确和的正确舍入）。C 的输出 g 是 float。判定标准是：

```
|g − r| ≤ ulp(r) + 2⁻³² · s
```

第一项是 1 个 ulp：正确舍入只要半个，多给半个是为了容纳 double 计算本身的那一点误差。第二项里的 s 是这个结果所有求和项的绝对值之和，它只在一种情况下起作用：求和项大量抵消，结果 r 比各项小得多。这时 r 的 ulp 很小，而 double 求和的误差是按各项的大小算的，可能超过 r 的 1 个 ulp。2⁻³² 比前面估计的 2⁻³⁹ 留了 100 多倍的余量。

**为什么不用更宽松的、教科书式的界。** 浮点误差分析给出过一个经典的上界：用 float 顺序求和 n 项，误差不超过 n · 2⁻²⁴ · s。按这个界定容差，看起来很“有理论依据”。但算一下：n = 17408 时，n · 2⁻²⁴ ≈ 10⁻³。而一个常见的错误，求和时漏掉一项，造成的误差大约是 s / n ≈ 6 × 10⁻⁵ · s，远小于 10⁻³ · s。也就是说，按最坏情况的界定容差，**漏掉一项的矩阵乘照样能通过**。最坏情况的界是对“所有可能的正确实现”成立的保证，拿来做对拍的容差就太松了。

我们选的是反过来的思路：先让实现足够精确（double），再把容差收到“只比正确舍入多一点”。这样，任何偏离精确值超过 1 个 ulp 的实现都会被抓出来，不管它是写错了还是精度不够。

**试一试。** 为了确认测试真的能抓住错误，我们故意把算子改坏，看测试是否失败：

| 故意引入的错误 | 结果 |
| --- | --- |
| 矩阵乘改用 float 累加 | 失败：7 项的小矩阵乘里就有 3 个元素超过 1 ulp |
| 矩阵乘漏掉第一项 | 失败 |
| RMSNorm 把 `1 + w` 写成 `w` | 失败 |
| RMSNorm 去掉 eps | 失败：全零的行变成 NaN，数值在 1 附近的行也差了几个 ulp |
| softmax 不减最大值 | 失败：数值约为 10⁴ 的那一行溢出成 NaN |
| 卷积核方向反了 | 失败 |
| RoPE 第二半的符号反了 | 失败 |
| RoPE 位置大于 1000 时差一 | 失败 |
| RoPE 用 float 计算 | 失败：240 个元素里有 8 个超过 1 ulp |

第一行和最后一行最能说明问题：它们不是“写错了”，只是精度差一点。用常见的 1e-3 相对误差做容差，它们都会通过；而它们一旦混进标尺，第 7 章 GPU 版的误差就没法和标尺的误差分开了。

## 各个算子

代码在 [`src/ops.h`](../src/ops.h) 和 [`src/ops.c`](../src/ops.c)，每个算子都是最直接的几重循环。这里只讲容易写错的地方。

### 矩阵乘

```c
for (size_t t = 0; t < n; t++)
    for (size_t o = 0; o < out; o++) {
        const uint8_t *row = w + 2 * o * in;
        double acc = 0;
        for (size_t i = 0; i < in; i++) acc += (double)x[t * in + i] * (double)bf16_to_f32(bf16_at(row, i));
        y[t * out + o] = (float)acc;
    }
```

三重循环，没有分块，没有多线程。它很慢：开着 ASan，一个 token 乘 10240 × 5120 的矩阵要 0.3 秒左右，按这个速度 27B 的一个 token 要算几分钟。但它一眼就能看出对不对，这是第一卷要的。

测试用例里有一个专门的“抵消”矩阵：x 的两列几乎相等，权重的两列互为相反数，结果比各项小好几个数量级，用来检验容差里第二项的设计。还有一个各项的数量级从 10⁻²⁰ 跨到 10²⁰ 的用例。

### 嵌入

按 id 取出嵌入表的一行，转成 float。它是纯拷贝，所以要求逐位相等，包括负零。测试用的嵌入表里放了 NaN、正负无穷、非规格化数和负零。

id 不在 `[0, 行数)` 里就报错。注意 Qwen3.8 的嵌入表有 248320 行，而真正的 token 只有 248077 个（第 2 章），多出来的 243 行在这个算子看来也是合法的行。判断一个 id 是不是真正的 token，是分词器的事。

### 两种 RMSNorm

RMSNorm 把一行数缩放到“均方根为 1”，再乘上一组可学习的权重。Qwen3.8 里有两种写法，差别只在权重怎么用，却很容易混淆：

```
RMSNorm(x)        = x / √(mean(x²) + eps) · (1 + w)        每层两次、最终归一化、q/k 归一化
带门控的 RMSNorm(x, z) = x / √(mean(x²) + eps) · w · silu(z)    线性注意力的输出
```

第一种是“零中心”的：权重存的是与 1 的差，初始化为 0，全零的权重表示不缩放。第二种的权重初始化为 1，直接相乘。两种都在官方代码里写得清清楚楚（`Qwen3_5RMSNorm` 和 `Qwen3_5RMSNormGated`），但如果凭 Llama 等其他模型的印象来写，第一种很容易写成 `· w`。拿真实权重验收时，我们会顺便打印这几组权重的均值：零中心的应当在 0 附近，带门控的应当在 1 附近，这是一个不依赖任何参考实现的旁证。

eps 从 `config.json` 的 `rms_norm_eps` 读，不写死。它的作用是兜底：一行全是 0 时，没有 eps 就是 0 / 0。测试里专门放了全零的行和数值在 10⁻⁶ 量级的行。

### L2 归一化

```
L2(x) = x / √(Σx² + eps)
```

和 RMSNorm 的区别是 Σ 而不是 mean，没有权重。线性注意力对 q 和 k 用它，eps 在官方代码里固定是 10⁻⁶，不来自配置。

### silu、sigmoid、softplus

```
silu(x)     = x / (1 + e⁻ˣ)
sigmoid(x)  = 1 / (1 + e⁻ˣ)
softplus(x) = ln(1 + eˣ)
```

难点在极端值。double 的 `exp` 在参数超过约 709 时溢出成无穷大。silu 和 sigmoid 的写法恰好不怕：e⁻ˣ 溢出时分母是无穷大，结果是 0，正是极限值。softplus 照定义写就有问题：x = 1000 时 eˣ 溢出，ln(∞) = ∞，而正确答案是 1000。我们把它改写成数学上相等的形式：

```
softplus(x) = max(x, 0) + ln(1 + e^(−|x|))
```

这样 `exp` 的参数永远不大于 0，不会溢出，而 `log1p` 在参数很小时也是精确的。

PyTorch 的 `softplus` 有一个“阈值”参数，默认 x > 20 时直接返回 x。这和精确值差 ln(1 + e⁻²⁰) ≈ 2 × 10⁻⁹，而 float 在 20 附近的 ulp 是 2 × 10⁻⁶，舍入到 float 后完全看不出区别。

测试输入除了正常范围的随机数，还有 0、负零、10⁻⁴⁵（float 最小的非规格化数）、±20、±88、±89（float 版 `exp` 溢出的边界）、±745（double 版 `exp` 下溢的边界）、±10³⁰、±3.4 × 10³⁸。

### softmax

```
softmax(x)ᵢ = e^(xᵢ − m) / Σⱼ e^(xⱼ − m)，m = max(x)
```

减去最大值在数学上不改变结果，但不减的话，x 里只要有一个数大于 709，`exp` 就溢出，结果变成 NaN。测试里有一行数值都在 10⁴ 左右。

全注意力的因果掩码会把“未来位置”的分数设成 −∞，e^(−∞) = 0，正好是想要的效果。测试里有一行混着 −∞。

### RoPE

旋转位置编码把 q 和 k 的维度两两配对，每一对看成平面上的一个点，按 token 的位置转一个角度。位置越远，转得越多；不同的维度对，转速不同。这样 q 和 k 的点积就只和两个 token 的相对位置有关。

Qwen3.8 的 RoPE 有三处要注意。

**配对方式。** 每个头的前 `rot` 维分成前后两半，第 i 维和第 i + rot/2 维配成一对，不是相邻的第 2i、2i+1 维。两种配法都有模型在用，配错了不会报错，只是位置信息全乱了。官方代码里对应的是 `rotate_half`。

**只转一部分。** `partial_rotary_factor` 是 0.25，每个头 256 维里只转前 64 维，后 192 维原样保留。

**频率。** 第 i 对的转速是 `theta^(−2i/rot)`，`theta` 是 `rope_theta`，等于 10⁷。第 0 对每个位置转 1 弧度，最后一对每个位置只转约 1.6 × 10⁻⁷ 弧度。

还有一处看起来复杂、其实可以简化的地方。官方代码里的 RoPE 叫 “mrope”：为了处理图像和视频，位置有三个分量（时间、高、宽），64 维里的 32 对按 `mrope_section = [11, 11, 10]` 交错地分给三个分量。但对纯文本，三个分量都等于 token 的序号，交错分配之后每一对拿到的还是同一个位置。所以在本书处理图像之前，RoPE 就是上面这个普通的一维形式。

测试的位置包括 0（不转，输出必须等于输入）和 262143（`max_position_embeddings` 减 1）。

### 因果一维卷积

线性注意力在投影之后，对 10240 个通道各自做一次长度为 4 的卷积：每个通道的输出，是这个通道当前 token 和前 3 个 token 的加权和。“因果”指只看过去，不看未来；序列开头之前的 token 当作 0。

```
y[t][j] = Σᵢ w[j][i] · x[t − 3 + i][j]，i = 0 … 3
```

最容易错的是卷积核的方向：`w[j][3]` 乘的是**当前** token，`w[j][0]` 乘的是往前数第 3 个。这是因为 PyTorch 的 `conv1d` 其实是互相关，不翻转卷积核。权重在文件里的形状是 `[10240, 1, 4]`，中间那一维是分组卷积的写法，我们也接受 `[c, k]`。

Python 参考实现故意换了一种写法：按“往前数第几个 token”来索引，`w[j][k-1-back]` 乘 `x[t-back]`，与 C 的写法不同但应当相等。测试里有一个只有 2 个 token 的用例，比卷积核还短。

## 不信任输入

算子本身假定参数是合法的；检查放在调用它们的工具 [`tools/ops.c`](../tools/ops.c) 里，因为形状来自文件。第 4 章写真正的推理代码时，这些检查会移到加载模型的地方。

| 检查 | 防的是什么 |
| --- | --- |
| 激活值必须是 F32，维数符合算子要求，不能为空 | 把 BF16 的字节当成 float 读 |
| 矩阵乘的权重必须是二维 BF16，列数等于输入的长度 | 越界读权重 |
| 归一化的权重长度必须等于输入的最后一维 | 同上 |
| 门控 z 的形状必须与输入相同 | 同上 |
| 位置、token id 必须是 I32，个数等于 token 数 | 同上 |
| token id 必须在嵌入表的范围内 | 读到表外 |
| 卷积核必须是 `[c,k]` 或 `[c,1,k]`，c 等于通道数 | 同上 |
| `rot` 必须是正偶数且不超过 head_dim；`theta` 必须为正；`eps` 必须是非负的有限数 | 静默地算出无意义的结果 |
| 标量参数没有默认值，不认识的参数、重复的参数都报错 | 拼错一个参数名，悄悄用了默认值 |

最后一条值得说一下：eps、theta 这些数，只要给错一点，结果就会差一点，不会崩溃。所以工具不提供默认值，每次都要从模型的配置里读出来明确给出。

## 如何验证正确

测试的结构和前两章相同，只是比较方式从“逐字节相同”换成了“逐元素在容差内”。

- [`tests/make_ops_fixtures.py`](../tests/make_ops_fixtures.py) 生成输入：每个用例一个小 safetensors 文件，装着这个算子的输入张量，再写一份用例清单。用 safetensors 是因为第 1 章的读取器现成可用，而且下一节换成真实权重时，权重本来就在 safetensors 里。
- [`tools/ops.c`](../tools/ops.c) 读输入、调用算子，输出结果。每个数用 C 的 `%a` 格式打印，比如 `0x1.99999ap-4`。这是十六进制的浮点数，精确无损，Python 用 `float.fromhex` 读回来。
- [`tests/ops_ref.py`](../tests/ops_ref.py) 读同样的输入，用双精度独立地算出精确值，与 C 的输出逐元素比较，报告最大误差是多少个 ulp。

两份实现故意写得不一样：BF16 一边移位、一边按定义算；求和一边是 double 顺序累加、一边是 `math.fsum`；卷积按不同的方向索引；silu 一边是 `x / (1 + e⁻ˣ)`、一边是 `x · sigmoid(x)`，其中 sigmoid 按正负分两支算。

两边错成一样的可能依然存在，所以和第 1 章的 CRC-32 测试向量一样，还有几个不依赖 Python 的已知答案：BF16 的 `3f80` 是 1.0，`0001` 是 2⁻¹³³；四个相等的数做 softmax，每个结果恰好是 1/4，即 `0x1p-2`。

另有 25 个必须被拒绝的输入，对应上一节表格里的每一条。

```
$ make test
...
ok   BF16 转 float：全部 65536 个位模式一致
ok   BF16 已知答案
ok   matmul_small：15 个元素，最大误差 0.47 ulp
ok   matmul：260 个元素，最大误差 0.50 ulp
ok   matmul_range：18 个元素，最大误差 0.49 ulp
ok   matmul_cancel：16 个元素，最大误差 0.00 ulp
ok   embed：96 个元素，完全一致
ok   rmsnorm：256 个元素，最大误差 0.49 ulp
...
ok   rope_partial：240 个元素，最大误差 0.50 ulp
ok   conv1d：30 个元素，最大误差 0.47 ulp
ok   softmax 已知答案
ok   拒绝 未知算子：错误：不认识的算子 gelu
ok   拒绝 缺少eps：错误：缺少参数 eps
ok   拒绝 嵌入id越界：错误：第 1 个 token id 50 超出嵌入表范围 [0, 50)

```

所有算子的最大误差都不超过 0.50 ulp，也就是说，C 的每一个输出都是精确值的正确舍入。这比标准要求的 1 个 ulp 还好，是 double 计算带来的。

本章的参考实现只用 Python 标准库，没有引入 NumPy 或 PyTorch。

## 在真实权重上验证

自造的输入覆盖了每条规则，但维度都很小。真实权重的验收拿 Qwen3.8-27B 的张量直接当算子的输入：

```
make test-ops-real MODEL=/data/models/Qwen3.8-27B
```

[`tests/make_ops_real.py`](../tests/make_ops_real.py) 从 `config.json` 读出 eps、theta、head_dim 和层的类型，按模型的真实维度生成激活值一侧的输入，然后对下面这些张量各跑一次算子：嵌入表（取几个普通 token、特殊 token 和最后一行填充）、第 0 层的输入归一化和最终归一化（输入是真实的嵌入行）、全注意力层的 q 归一化、线性注意力层的门控归一化、三个大矩阵（线性注意力的输入投影 10240 × 5120、全注意力的 q 投影 12288 × 5120、前馈的 down 投影 5120 × 17408）、卷积核，以及位置最大到 262143 的 RoPE。

这一步要在目标机器上做，结果待补。

## 与官方实现的差别

我们的算子是“数学上的精确值”，而官方的 transformers 在 BF16 模式下运行时，每一步都会把中间结果舍入成 BF16。读官方代码时注意到的几处：

- 线性层的输出、RMSNorm 的输出都是 BF16（只有 7 位尾数，相对误差约 0.4%）。
- 带门控的 RMSNorm 先把归一化结果舍入成 BF16，再乘权重和门控。
- RoPE 的频率和角度用 float 计算，再把 cos 和 sin 舍入成 BF16。位置在 10⁵ 量级时，float 计算角度本身就有 10⁻² 弧度量级的误差。

这些差别意味着，我们的输出和官方的输出不会逐位相同，而且层数越多差得越远。第 4 章做单层对拍、第 5 章做整模对拍时，要面对“该和谁比、差多少算对”的问题。我们的打算是保持 CPU 版的精确性不变，在对拍时把官方的这些舍入考虑进去，具体怎么做到那一章再定。

## 踩过的坑

**参考实现放过了 NaN。** 写完测试，我们把 softmax 的“减最大值”删掉，想看测试失败，结果测试通过了。那一行 10⁴ 量级的数明明已经溢出成 NaN，参考实现却报告“最大误差 0.00 ulp”。

原因在比较的写法：`if err > tol: 记为失败`。g 是 NaN 时，err 也是 NaN，而 NaN 和任何数比较都是假，所以永远不会被记为失败。改成 `if not err <= tol` 就对了。

这个错误不在被测的代码里，而在测试里，而且它会让所有算子的所有 NaN 输出都蒙混过关。如果不是故意把算子改坏来验证测试，它可能一直藏着。这也是为什么上面那张“故意引入的错误”的表值得做：**测试本身也需要被测试**。
