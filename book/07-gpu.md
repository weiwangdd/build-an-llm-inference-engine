# 第 7 章 单卡 GPU 后端

> 状态：初稿。本章的代码已在第 4、5、6 章的随机小模型上通过全部对拍，GPU 与 CPU 的输出逐位相同；真实模型上的结果见“在真实权重上验证”一节。

## 要解决的问题

第 6 章结束时，引擎能按对话模板回答问题、自己停下，但每个 token 要 13.5 秒。原因第 6 章说过：时间几乎全花在矩阵乘上，每个 token 都要做约 260 亿次乘加，CPU 上一个线程一次只能做一个。

目标机器上有两张显卡（GPU），每张有 96 GB 显存，能同时运行几万个线程。这一章把整个模型搬到其中一张上算。

前言里这一章的验收标准是“GPU 与 CPU 结果逐层对拍通过”。和前几章一样，我们先把“对拍通过”说清楚，再写代码。

## 几个新概念

**主机和设备。** 写 GPU 程序时，CPU 和它的内存叫主机（host），GPU 和它的显存叫设备（device）。两边各有各的内存，CPU 不能直接读写显存，GPU 也不能直接读写内存（严格地说有办法，但很慢，我们不用）。数据要用 `cudaMemcpy` 这样的函数显式地拷过去、拷回来。

**CUDA。** NVIDIA 显卡的编程方式。我们用的是它的 C++ 方言：在普通的 C 代码里加几个关键字，就能写出在 GPU 上运行的函数。编译器是 `nvcc`。

**内核、线程、线程块、网格。** 在 GPU 上运行的函数叫内核（kernel）。启动一个内核时要说明启动多少个线程，这些线程同时执行同一个函数，每个线程通过自己的编号决定处理哪一份数据。线程按固定大小分组，一组叫一个线程块（block，我们每块 128 个线程），一次启动的全部线程块叫网格（grid）。同一个线程块里的线程可以通过共享内存交换数据，并用 `__syncthreads()` 互相等待；不同线程块之间不能。

**异步。** CPU 启动一个内核之后马上就往下执行，不等它算完。后面启动的内核按顺序排在它后面。只有在需要结果时（比如把结果拷回内存），CPU 才会停下来等。好处是 CPU 安排工作和 GPU 干活可以重叠；坏处是内核里出了错（比如访问越界），要等到下一次“等”的时候才报出来，报错的位置不一定是出错的位置。

**FMA。** 融合乘加（fused multiply-add）：一条指令算 `a × b + c`，只在最后舍入一次。普通的写法是先算 `a × b` 舍入一次，再加 `c` 再舍入一次。两种结果可能差一个 ulp（第 3 章：相邻两个浮点数之间的距离）。GPU 的编译器默认会把 `a * b + c` 合并成 FMA。

**双精度的吞吐。** 我们的算子内部全用 double（第 3 章）。这张卡（RTX PRO 6000）算 double 的速度只有算 float 的 1/64，这是为图形和 AI 设计的显卡的通常做法。一个 token 的 260 亿次乘加换成 double，理论上仍只要几十毫秒，比 CPU 快得多；所以这一章不改精度。

## 和谁比、差多少算对

GPU 上的浮点结果通常与 CPU 不逐位相同，原因有三个：

1. **求和次序。** 高性能的 GPU 实现会把一个长的求和拆成很多段并行地加，再把各段的和加起来。浮点加法不满足结合律，次序一变，结果就可能差几个 ulp。
2. **FMA。** 上面说的，编译器自动合并乘加，舍入次数变了。
3. **数学函数。** `exp`、`sin`、`cos`、`pow` 这些函数，CUDA 和 C 标准库（glibc）是两套独立的实现，都只保证误差在一两个 ulp 以内，不保证逐位相同。

第 3 章的算子是后面各章的标尺，我们希望 GPU 版不只是与它“差不多”。所以有三种定标准的办法：

- **GPU 也用 double，照搬求和次序，关掉 FMA。** 前两个原因就没有了，只剩数学函数。每一步的结果仍然交给第 3 到 6 章的参考实现，按原来的容差检查；再与 CPU 逐层比较，要求生成的 token 完全相同。
- **要求与 CPU 逐位相同。** 还要把数学函数也换成两边共用的同一份实现。这样 CPU 的结果也会变，第 3 到 6 章要全部重新验证。
- **GPU 用 float 并行求和，按相对误差 2⁻¹² 判定。** 更接近以后的高性能写法，但容差比前几章松了几个数量级。

我们选第一种（Wei 定的）。`ops.h` 的开头早就写着：“这样每个结果都几乎等于‘精确值舍入到 float’，后面各章（包括 GPU 版）都拿它当标尺。”第一种办法保住了这句话：GPU 版的每一步都要通过与 CPU 版完全相同的检查。

数学函数那一条，实际影响比看上去小。这些函数在 double 下差一个 ulp，相当于相对误差 2⁻⁵³ 左右；结果最后要舍入成 float，float 的一个 ulp 是 2⁻²⁴ 左右。只有 double 的结果恰好落在两个 float 的正中间附近（距离小于 2⁻²⁹ 个 float ulp）时，两边才会舍入到不同的 float。所以我们预计绝大多数时候 GPU 与 CPU 逐位相同，偶尔差一个 ulp。实测见后面。

具体的验收标准是：

**一、GPU 版的每一步都正确舍入。** 第 3 到 6 章的测试脚本原样拿 GPU 版的程序再跑一遍，全部通过。这包括算子与标准库精确值的逐元素对拍（≤ 0.5 ulp 加求和误差）、单层和整模的逐步对拍、与官方 transformers 的对拍、带缓存与不带缓存逐字节相同、采样的两层对拍、每一个必须被拒绝的输入。

**二、GPU 与 CPU 逐层一致。** 同样的输入交给两边，步骤名、形状、生成的 token、停止的位置完全相同；每个张量的最大误差不超过它均方根的 2⁻¹²；并报告有多少个元素逐位相同。

## 设计：同一套结构体，指针指向显存

最省事的接口，是让调用方几乎感觉不到 GPU 的存在：

```c
model M;
model_load(&M, config, &shards, err, cap);   // 第 5 章：读配置，检查每个张量
model_to_gpu(&M, err, cap);                  // 第 7 章：把权重拷进显存
model_forward(&M, ids, n, logits, ...);      // 照旧，算在 GPU 上
```

`model_to_gpu` 做的事情很简单：新建一个 `model`，把 CPU 上那一份的每个张量拷进显存，新结构体里的指针都指向显存，再把它挂在原来那个模型的 `gpu` 字段上。`layer_w`、`model_cache` 也是这样：结构体本身在内存里，里面的指针指向显存。所以第 4 到 6 章的结构体一个都不用改，只多了两个字段：

```c
typedef struct model {
    ...
    struct model *gpu;    /* model_to_gpu 之后指向显存里的那一份，否则为 NULL */
} model;

typedef struct {
    ...
    int gpu;              /* 1 表示 layers 里的指针指向显存 */
} model_cache;
```

`model_forward`、`model_step` 开头加了一行：模型在 GPU 上，就交给 GPU 版的实现。`model_cache_init` 改成接收模型而不是配置，模型在 GPU 上时缓存也建在显存里。生成循环 `gen.c` 一个字没改（除了 `model_cache_init` 的参数），所以第 6 章的采样、停止条件、提示词分块，在 GPU 上走的是同一份代码。

代码分成三个文件：

- [`src/07-gpu/gpu_ops.cu`](../src/07-gpu/gpu_ops.cu)：内核。这是唯一一个 CUDA 文件，每个内核对应 `ops.c` 的一个算子，接口在 [`src/07-gpu/gpu_ops.h`](../src/07-gpu/gpu_ops.h)，与 `ops.h` 一一对应，参数相同，只是指针指向显存。另有几个分配、拷贝显存的函数。
- [`src/07-gpu/gpu_model.c`](../src/07-gpu/gpu_model.c)：普通的 C，和其余代码一样用 gcc 加全部警告编译。它负责安排：分配显存、按顺序调用内核。里面的 `layer_run`、`full_attention`、`linear_attention`、`model_run` 与 `model.c` 里的同名函数一行一行对应。
- [`src/07-gpu/gpu_none.c`](../src/07-gpu/gpu_none.c)：没有 CUDA 的机器上用它代替上面两个，`model_to_gpu` 一律报错“编译时没有启用 CUDA”。这样 Mac 和没有显卡的机器照样能编译、测试前 6 章。

`gpu_model.c` 和 `model.c` 有一半是重复的。也可以只写一份，把“调用哪个算子、怎么分配内存”做成一张函数表，CPU 和 GPU 各填一张。我们没有这么做：两份代码并排放着，一眼就能看出一一对应；步骤名或次序写错了，测试会发现（参考实现要求步骤名和顺序完全一致）。

## 内核

### 一个线程算一个输出

CPU 上的算子都是“对每个输出，算一个求和”。搬到 GPU 上最直接的写法是：每个线程负责一个输出，线程内部的循环与 CPU 一字不差。矩阵乘就是这样：

```cuda
__global__ static void k_matmul(float *y, const float *x, const uint8_t *w, size_t n, size_t in, size_t out) {
    FOR_EACH(idx, n * out) {
        size_t t = idx / out, o = idx % out;
        const float *xt = x + t * in;
        const uint8_t *row = w + 2 * o * in;
        double acc = 0;
        for (size_t i = 0; i < in; i++) acc += (double)xt[i] * (double)bf16(row, i);
        y[idx] = (float)acc;
    }
}
```

`__global__` 表示这是一个内核。`FOR_EACH` 是一个“网格跨步循环”：

```cuda
#define FOR_EACH(i, n) for (size_t i = (size_t)blockIdx.x * blockDim.x + threadIdx.x; i < (n); \
                            i += (size_t)gridDim.x * blockDim.x)
```

`blockIdx.x` 是线程块的编号，`blockDim.x` 是每块的线程数，`threadIdx.x` 是线程在块里的编号，`gridDim.x` 是线程块的个数，四个都是 CUDA 内置的变量。第一行算出这个线程的全局编号 i；如果输出比线程多，处理完第 i 个就跳到第 i + 线程总数 个，依此类推。这样启动多少线程与输出有多少个无关，不会超出 CUDA 对网格大小的限制。

求和仍由一个线程从 i = 0 加到 in − 1，次序与 `op_matmul` 相同。乘积 `x × w` 在 double 里是精确的（float 的 24 位尾数乘 BF16 的 8 位尾数，32 位，放得进 double 的 53 位），所以即使编译器合并成 FMA 也不影响矩阵乘；但归一化、门控 delta 规则里有不精确的乘法，所以我们在编译选项里关掉 FMA：`nvcc --fmad=false`。

归一化、softmax、L2 归一化也是这样，只是每个线程负责一整行；逐元素的激活函数每个线程负责一个元素。RoPE 每个线程负责一个头里的一个维度：在前半的线程算一对 `y[i]`、`y[i + rot/2]`，在 `rot` 之后的线程原样复制。

这些写法都很慢（一个线程从头到尾做 5120 次 double 乘加，相邻的线程读的是权重的不同行，访问显存的方式很不理想），但一眼就能看出它们和 CPU 算的是同一件事。性能留到第二卷。

### 注意力：一个线程块合作

注意力不能简单地“一个线程一个输出”：第 t 个 token、第 h 个头的输出有 d = 256 维，每一维都要先算出全部 softmax 概率 p[s]，让 256 个线程各自重算一遍就浪费了 256 倍。我们让一个线程块负责一个（t, h），块里的线程分三段合作：

1. 各线程分头算 `p[s] = scale · q·k[s]`，每个点积仍由一个线程从 i = 0 加到 d − 1。
2. 0 号线程独自求最大值 m；然后大家分头算 `p[s] = e^(p[s] − m)`；0 号线程再从 s = 0 起依次加出总和。
3. 线程 i 负责输出的第 i 维：从 s = 0 起依次加 `p[s] · v[s][i]`，最后除以总和。

每一段之间用 `__syncthreads()` 等齐。每一个求和都只由一个线程按 CPU 的次序做，所以与 `op_attention_past` 逐位相同。让 0 号线程独自做求和，其余线程干等，很浪费，但这一章不在乎。p 放在显存里而不是共享内存里，因为序列可能很长（最长 262144 个位置）。

### 门控 delta 规则：一个线程一列

门控 delta 规则（第 4 章）对每个值头维护一个 dk × dv 的状态矩阵 S，逐个 token 更新：

```
S    = e^g · S
u    = beta · (v − Sᵀk)
S    = S + k uᵀ
y    = Sᵀ q / √dk
```

仔细看每一列：第 c 列的衰减只动第 c 列；`(Sᵀk)[c] = Σ_r S[r][c] k[r]` 只读第 c 列；`u[c]` 只用到第 c 列的预测；`S + k uᵀ` 的第 c 列只加 `k · u[c]`；`y[c]` 也只读第 c 列。**各列之间完全独立。** 所以每个线程负责一个值头的一列（27B 上是 48 × 128 = 6144 个线程），按 token 顺序往下算，各列互不等待，也不需要任何同步。每一列里的求和次序与 CPU 相同。

状态按 `[dk][dv]` 存放，相邻的线程负责相邻的列，读写的正好是相邻的地址，这是显存最喜欢的访问方式。这是本章唯一一个“顺手”就快的内核。

### 内核不能报错

CPU 上的 `op_embed` 遇到越界的 token id 会报错返回。内核里没法这样做：几千个线程同时在跑，没有办法把一条错误信息交还给调用方。所以 `gop_embed` 不检查，由 `gpu_model.c` 在把 id 拷进显存之前，在 CPU 上先检查一遍，错误信息与 `op_embed` 相同。这是“严格拒绝”在 GPU 上的样子：凡是能出错的检查，都在启动内核之前做完。

内核本身出了错（比如越界访问显存），CUDA 会在下一次等待时报告。`gpu_model.c` 在每一层的最后调用一次 `gpu_sync` 等这一层算完，这样出错时至少能知道是哪一层。

## 显存的分配

CPU 版的每个函数用 `malloc` 分配临时缓冲区、用完 `free`。GPU 版照样这么写，只是换成 `cudaMallocAsync` 和 `cudaFreeAsync`：它们从一个显存池里分配，按顺序排在内核后面执行，不会让 CPU 停下来等。默认情况下，池子在每次同步时会把空闲的显存还给驱动，下次再要；我们每一层都分配、释放一批缓冲区，所以在 `gpu_init` 里让池子留着它们（`cudaMemPoolAttrReleaseThreshold` 设成最大）。

权重用同样的办法分配。27B 跑起来时显存一共用了约 51 GiB（nvidia-smi 报告的最大值 52223 MiB），几乎全是语言模型部分的权重（视觉部分的权重用不到，没有拷），一张 96 GB 的卡还剩四成多。嵌入表也放在显存里（2.5 GB），虽然每个 token 只读它的一行。

## 构建

```
make gpu                 # 构建 GPU 版到 build/gpu：ops、layer、forward、generate 等，用法和输出与 CPU 版完全相同
make test-gpu PYTHON=…   # 第 3 到 6 章的测试换成 GPU 版再跑一遍，再加 GPU 与 CPU 的比较
make test-gpu-real MODEL=<模型目录> PYTHON=…   # 真实模型
```

`make gpu` 用 `GPU=1` 重新调用自己：链接 `gpu_model.c` 和 nvcc 编译的 `gpu_ops.o`，不再链接 `gpu_none.c`；四个命令行工具用 `-DUSE_GPU` 编译，加载模型之后多一行 `model_to_gpu`。CUDA 的位置用 `CUDA` 变量指定，默认 `/usr/local/cuda`；目标架构用 `CUDA_ARCH`，默认 `sm_120`（RTX PRO 6000 这一代 Blackwell 显卡）。

nvcc 的选项和 gcc 的一样严：`-Werror all-warnings` 把所有警告当错误，`-Xcompiler -Wall,-Wextra` 让它调用的 gcc 也打开警告。

GPU 版的小模型测试仍然开着 ASan 和 UBSan（第 1 章），检查的是主机这一侧的代码。CUDA 的运行库与 ASan 的默认设置冲突：ASan 预留了一大段地址空间，CUDA 驱动也要用其中的一部分。所以运行 GPU 版时要设 `ASAN_OPTIONS=protect_shadow_gap=0`，`make test-gpu` 已经设好了。ASan 的泄漏检查我们也关掉了（`detect_leaks=0`），因为 CUDA 驱动自己有一些不释放的内存。显存这一侧的越界检查，CUDA 自带一个工具 `compute-sanitizer`，作用和 ASan 类似，见“如何验证正确”。

`tools/ask.sh` 多了一个 `-G` 选项，在 GPU 上回答问题。

## 如何验证正确

测试分两部分。

**第 3 到 6 章的全部测试，原样换成 GPU 版。** 这些脚本的第一个参数是 build 目录，`make test-gpu` 传给它们 `build/gpu`，于是脚本调用的 `ops`、`layer`、`forward`、`generate` 都是 GPU 版，其余一切不变：同样的小模型，同样的参考实现，同样的容差，同样的必须被拒绝的输入。第 6 章的“带缓存、不带缓存、分块，输出逐字节相同”这一条，现在检查的是 GPU 上的缓存。

第 4 章的 `layer` 工具在 GPU 版里只把那一层放到 GPU 上，嵌入和最终归一化仍在 CPU 上算；这两步的 GPU 内核由第 3 章的 `ops`（嵌入）和第 5 章的 `forward`（两者都有）检查。

**GPU 与 CPU 逐层比较**，入口是 [`tests/07-gpu/run_gpu.sh`](../tests/07-gpu/run_gpu.sh)，比较由 [`tests/07-gpu/gpu_cmp.py`](../tests/07-gpu/gpu_cmp.py) 做（只用标准库）。第 4 章的 7 个单层用例、第 5 章的 6 个整模用例（`all` 方式，每层每一步都打印）、第 6 章的 8 个生成用例（`--dump`，每一步的 logits），两边各跑一次，要求步骤名、形状、token、停止原因完全相同，每个张量误差不超过均方根的 2⁻¹²，并报告逐位相同的元素有多少、最多差几个 ulp。

“差几个 ulp”是这样算的：把 float 的 32 位按有符号整数的大小排好（正数照原样，负数取反），相邻的两个 float 正好差 1，两个数的 ulp 距离就是这两个整数之差。


第 3 到 6 章的 207 项测试换成 GPU 版全部通过，21 组 GPU 与 CPU 的比较全部逐位相同，一共 228 项，两分多钟。前面估计数学函数偶尔会让结果差一个 ulp，在这些小模型的约 160 万个元素上一次也没有发生。第 3 章的算子换成 GPU 版之后，各算子与精确值的最大误差同样是 0.50 ulp，嵌入完全一致。

**显存一侧的检查。** ASan 只管主机这一侧。显存里的越界、读未初始化的显存、线程之间的竞争（两个线程同时读写同一个地址、没有用 `__syncthreads()` 隔开），用 CUDA 自带的 `compute-sanitizer` 检查。它的用法和 ASan 不同：不用重新编译，直接把程序套在它下面运行，所以用的是不带 ASan 的那份：

```
compute-sanitizer --tool memcheck --leak-check full build/gpu/fast/forward <小模型> 3,17,17,0,39 3 all …
compute-sanitizer --tool racecheck  build/gpu/fast/forward …
compute-sanitizer --tool initcheck  build/gpu/fast/forward …
compute-sanitizer --tool memcheck --leak-check full build/gpu/fast/generate … 6 --chunk 2 …
```

四项都是 0 个错误：没有越界，没有泄漏显存，注意力内核里 0 号线程写、其余线程读的那几个共享变量没有竞争，也没有读到没写过的显存。它们没有放进 `make test-gpu`：`compute-sanitizer` 会让程序慢几十倍，而且它的报告默认写在标准输出上，和我们的输出混在一起（要加 `--log-file`）。改了内核之后应当手工跑一遍。

## 在真实权重上验证

```
make test-gpu-real MODEL=/data/models/Qwen3.8-27B PYTHON=$HOME/venvs/x/bin/python
```

依次是：第 4 章的四层逐步对拍（第 0、3、62、63 层）、第 5 章的整模贪心解码 8 个 token、第 6 章的带缓存贪心和对话采样，都换成 GPU 版；最后对同一个提示词，CPU 版和 GPU 版各做一次整模前向，比较每一层的输出和 logits。跑整个模型的几份程序和第 5、6 章一样用 `-O2`、不带 ASan 另建。

全部 19 项通过，18 分 22 秒，大部分时间花在 Python 的参考实现上。

- **第 4 章的四层。** GPU 版的第 0、3、62、63 层，每一步都与精确值相差不超过 0.50 ulp，与官方 float64 的最大相对误差 1.7 × 10⁻⁵，和第 4 章 CPU 版的结果一样。
- **第 5 章的整模贪心。** “中国的首都是”，生成“北京，而北京位于中国的北方。”，8 个 token 与官方 float64 完全相同，64 层逐层最大误差 1.2 × 10⁻⁵。第 5 章 CPU 版没有缓存，从 3 个 token 生成 8 个要 726 秒；同样的事 GPU 版 52 秒，其中包括把 55.6 GB 权重拷进显存。
- **第 6 章的缓存和采样。** 带缓存与不带缓存逐位相同（第 6 章末尾留了一个问题：换成 GPU 以后这条标准还能不能保持。能，因为 GPU 版的三个“接着往下算”的算子照搬了 CPU 版的求和次序）；对话采样还是“中国的首都是北京。”，在 `<|im_end|>` 处停下，随机数、分布、停止位置全部通过两层对拍。
- **GPU 与 CPU 逐层比较。** 同一个提示词各做一次整模前向，64 层的输出、最终归一化和 logits，一共 67 个张量、175 万多个元素，**全部逐位相同**。

所以在我们见过的所有输入上，GPU 版与 CPU 版不是“差不多”，而是一模一样。这让后面的工作简单了很多：第 3 到 6 章对 CPU 版证明过的每一件事（与官方 float64 一致、贪心 token 相同、缓存逐位相同），对 GPU 版自动成立；以后要做性能优化，手里有两份逐位相同、彼此印证的实现当标尺。

速度。用 `generate` 从同一个提示词贪心生成 1 个和 65 个 token，两次用时相减，再除以 64，得到每多生成一个 token 的用时：

| | 生成 1 个（含加载权重、预填充） | 每多一个 token |
| --- | --- | --- |
| CPU（第 6 章，单线程） | 40.5 秒 | 13.3 秒 |
| GPU（本章） | 4.4 秒 | 0.80 秒 |

快了约 17 倍。这个数要这样看：每个 token 要从显存读一遍 55.6 GB 权重，这张卡的显存带宽约 1.8 TB/s，光读一遍就要 30 毫秒左右，这是不改算法时的下限；0.8 秒离它还差 25 倍以上，差距全在本章故意没做的地方（一个线程从头到尾做几千次 double 乘加、读权重的方式不理想、很多内核只有几十个线程在干活）。第二卷从这里开始。

生成的 65 个 token 也值得一看。模型说完“北京，而北京位于中国的北方。”之后没有停（这里没有结束符，不套对话模板），而是自己写出了一段 `<think>`：“用户陈述了两个事实：1. 中国的首都是北京 2. 北京位于中国的北方……我应该确认这些信息的正确性”，然后开始回答“是的”。用 CPU 生成 65 个要 15 分钟，用 GPU 不到一分钟，这样的观察才变得顺手。

## 踩过的坑

**云端没有显卡。** 本书的代码是在一台没有 GPU 的云端机器上写的，在目标机器上运行。云端只能装上 Ubuntu 自带的 CUDA 12.0，它不认识 Blackwell（`sm_120`），只能按上一代架构编译，用来检查代码能不能编译、有没有警告；第一次真正运行是在目标机器上。所幸第一次就全部通过。

**nvcc 不在 PATH 里。** 目标机器上装的 CUDA 13.1 在 `/usr/local/cuda/bin`，没有加进 PATH。所以 Makefile 里 nvcc 的默认值写成 `$(CUDA)/bin/nvcc`，而不是指望它在 PATH 里。

**工具包比驱动新。** 目标机器的驱动（580）报告支持 CUDA 13.0，工具包却是 13.1。同一个大版本里，用新一点的工具包编译的程序可以在旧一点的驱动上运行，前提是不用新版本才有的功能，并且编译出的是这张卡能直接执行的机器码（`-arch=sm_120` 同时生成了机器码和 PTX 中间码）。实际运行没有问题。

**一个警告。** 第一次编译 `gpu_model.c` 时 gcc 报了 `'*' in boolean context`：`rows * cols ? rows * cols : 1` 在 gcc 看来像是把 `&&` 写成了 `*`。先把乘积存进一个变量再判断。

## 还没做的事

- **性能。** 这一章的内核只求和 CPU 版算的是同一件事。矩阵乘每个线程一个输出、读权重的方式很不理想，没有用 float、没有用张量核心（GPU 上专做矩阵乘的单元）、没有用 cuBLAS 这样的现成库，归一化每行只有一个线程，0 号线程独自求和。这些都留到第二卷，到时手里有一份逐位可信的 GPU 实现可以用来比对。
- **权重只能整体拷进显存。** 拷的时候要从 mmap 读一遍 55.6 GB，冷启动受硬盘速度限制。
- **只用一张卡。** 第 9 章把模型按层切到两张卡上。
