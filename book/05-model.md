# 第 5 章 整模前向

> 状态：初稿。本章的代码已在一个结构与 Qwen3.8 相同的 8 层随机小模型上通过两层对拍，并在目标机器上用 Qwen3.8-27B 的真实权重通过了验收，见“在真实权重上验证”一节。

## 要解决的问题

第 4 章把模型的一层算对了。这一章把 64 层串起来，最后接上输出层，得到 logits，再用 logits 做最简单的生成：每次选分数最高的 token，接在后面，重复几次。做完这一章，引擎第一次能“说话”：给它“中国的首都是”，它会接着写下去。

串起来本身没有新的数学，难点又一次在“怎么知道算对了”：

1. 第 4 章的两层对拍是一层一层做的。64 层串起来以后，误差会不会一层层累积？逐层对拍的 2⁻¹² 还够不够？
2. 第 4 章发现，官方 BF16 跑一层，个别元素的误差就能到 0.5 个均方根。64 层累积下来，官方 BF16 选出的 token 和精确计算选出的还一样吗？如果不一样，该以谁为准？
3. 27B 每生成一个 token 都要从头算一遍，每个 token 约 260 亿次乘加。纯 C、单线程、内部用 double，测试要跑多久？官方代码在 float64 下要 216 GB 内存，放不进目标机器的 186 GB。

本章的验收标准：

**第一层：C 的每一步，以它自己的输入为准，都与精确值相差不超过第 3 章的容差；贪心解码选出的每个 token 都是那一行 logits 里分数最大的。第二层：每一层、最终归一化和输出层，拿 C 的上一步结果当输入交给官方代码（float64），误差不超过均方根的 2⁻¹²；官方代码从嵌入开始自己串起全部层，贪心解码选出的 token 必须与 C 完全相同。官方 BF16 的结果只记录，不做判定。**

前言里这一章的验收标准写的是“贪心解码的 token 与参考完全相同”。“参考”指哪一份，是本章要定的事，见“和谁比”一节。

## 几个新概念

**输出层（lm_head）。** 最后一层之后的那个线性层，把每个 token 的 5120 维向量变成 248320 个数，词表里每个 token 一个，就是 logits。权重是 `lm_head.weight`，形状 [248320, 5120]，和嵌入表一样大，但不是同一个矩阵（第 3 章“读懂 config.json”一节的 `tie_word_embeddings`）。名字里的 head 是“头”，指网络最后接上的那一小部分，和注意力头无关。

**argmax。** 一组数里最大的那个数的**位置**（而不是最大值本身）。贪心解码就是对最后一行 logits 取 argmax，得到的位置就是下一个 token 的 id。

**因果性。** 第 t 个位置的输出只取决于第 0 到 t 个 token，与它后面的 token 无关。全注意力只看前面（第 4 章的掩码），线性注意力和卷积都是从前往后递推的，其余步骤都是逐个 token 独立算的，所以整个模型是因果的。这一性质本章要用两次：一次用来省掉大量计算，一次当作不依赖 Python 的已知答案。

**教师强制。** 训练时常用的一种做法：不让模型用自己生成的 token 接着往下算，而是直接把一整段“标准答案”喂进去，一次算出每个位置的预测。本章借用它来检查生成的结果，见“逐行检查贪心解码”一节。

## 整个模型的结构

```
h = 嵌入(ids)                          [n, 5120]，嵌入表 model.language_model.embed_tokens.weight
for i in 0 .. 63:
    h = 第 i 层(h)                      第 4 章，层的类型按 layer_types：每 4 层里前 3 层线性注意力、第 4 层全注意力
x = RMSNorm(h)                         model.language_model.norm.weight，1 + w 形式
logits = lm_head(x)                    [n, 248320]，权重是顶层的 lm_head.weight
```

就这么多。要小心的只有两处：输出层的权重名字没有 `model.language_model.` 前缀；位置从 0 开始编号。后面会看到，第二处写错了，官方对拍是发现不了的。

**贪心解码。** 给定提示词的 n 个 token：

```
重复 m 次：
    logits = 模型(当前全部 token)        每一次都从头算
    下一个 = argmax(logits 的最后一行)
    把它接在后面
```

每一步都把整个序列从头算一遍，第 k 步要算 n + k 个 token，前面那些 token 的结果上一步已经算过了，这里又算一遍。把它们存起来复用就是缓存，是第 6 章的事。这一章故意不做，原因是：最朴素的版本是第 6 章的标准答案，第 6 章的验收标准就是“带缓存与不带缓存的输出一致”。

## 代码

代码在 [`src/model.c`](../src/model.c) 的后半部分和 [`tools/forward.c`](../tools/forward.c)。

`model_load` 读配置，按配置检查并加载嵌入表、64 层、最终归一化和输出层。大矩阵仍然只是指向 mmap 区域的指针（第 1 章），加载不到一秒。配置里的 `tie_word_embeddings` 在顶层和 `text_config` 里各有一份，哪一份是 true 都报错：那种模型没有单独的 `lm_head.weight`，我们没有实现。

`model_forward` 就是上面那段伪代码：

```c
if (op_embed(h, m->embed, c->vocab, H, ids, n, err, cap)) goto done;
tr(T, ctx, "embed", h, n, H);
for (size_t i = 0; i < c->n_layers; i++) {        /* 每一层的输出就是下一层的输入 */
    prefix_ctx pc = {T, ctx, i};
    if (layer_forward(h, n, pos, c, &m->layers[i], T ? prefixed : NULL, &pc, err, cap)) goto done;
}
op_rmsnorm(x, h, m->final_norm, n, H, c->eps);    tr(T, ctx, "final_norm", x, n, H);
mm(logits, x, &m->lm_head, n);                    tr(T, ctx, "logits", logits, n, c->vocab);
```

第 4 章的 `layer_forward` 每算完一步就调用一次回调，报告“attn_in”“q_proj”这样的步骤名。整个模型有 64 层，同一个名字会出现 64 次，所以 `model_forward` 在中间垫了一个小函数 `prefixed`，把名字改成 `layers.3.q_proj` 再交给调用方。

`logits_argmax` 取一行里最大的那个，有几个同样大时取 id 最小的，和 PyTorch 的 `argmax` 一样。行里有 NaN（“不是一个数”，0/0 这类运算的结果）就报错：NaN 和任何数比较都是假，不报错的话，选出的 token 取决于 NaN 出现在哪里。

命令行工具 `forward` 做贪心解码，只打印最后一次前向的中间结果：

```
forward <config.json> <token id，逗号分隔> <生成个数 m> <all|layers> <分片 ...>
```

`all` 打印每一层的每一步，小模型的测试用；`layers` 只打印每一层的输出，真实模型用。27B 的一层有二十多步，每一步几百万个数，全部打印出来是几十 GB。最后一段是生成的 token id。

## 和谁比、差多少算对

### 先看官方 BF16 会差多远

在第 4 章的小模型上，官方 BF16 一层的结果离精确值 1% 到 3%。串起 8 层的小模型（结构见“如何验证正确”一节），每一层的输出和 C 差多少（最大误差除以均方根）：

```
    layers.0.out     官方 float64 串起来差 1.2e-06，官方 BF16 串起来差 5.6e-02
    layers.1.out     官方 float64 串起来差 2.5e-06，官方 BF16 串起来差 1.1e-01
    layers.3.out     官方 float64 串起来差 3.6e-06，官方 BF16 串起来差 1.1e-01
    layers.5.out     官方 float64 串起来差 3.4e-06，官方 BF16 串起来差 3.6e-01
    layers.7.out     官方 float64 串起来差 5.6e-06，官方 BF16 串起来差 7.2e-01
    logits           官方 float64 串起来差 5.4e-06，官方 BF16 串起来差 6.8e-01
```

官方 float64 串起来，误差几乎不增长，到最后还是 10⁻⁶ 量级；官方 BF16 每过几层就翻一倍，8 层之后已经差了 0.7 个均方根。从 62 个 token 生成 6 个的用例里，BF16 的 logits 差到 1.0，6 步里有 1 步选了与 C 不同的 token。

所以官方 BF16 当不了标准答案：它离精确值的距离，和“读错一个公式”造成的误差（第 4 章，0.5 到 8）是同一个量级。拿它当标准，要么容差大到什么都抓不住，要么正确的实现也会失败。

### 和官方 float64 比

标准答案用官方代码在 float64 下的结果（这是 Wei 定的方案）。官方 BF16 照样跑一遍，打印它选的 token 有几个和我们相同、logits 差多少，写进书里，但不影响测试通过与否。这个数在真实模型上是多少，见“在真实权重上验证”一节。

第二层对拍 [`tests/model_official.py`](../tests/model_official.py) 做三件事。

**一、逐层对拍。** 对每一层 i，把 C 算出的第 i − 1 层输出交给官方的 `Qwen3_5DecoderLayer`，在 float64 下算第 i 层，和 C 的第 i 层输出比。最终归一化和输出层也一样，用 C 的上一步当输入。判定标准与第 4 章完全相同，2⁻¹²。

为什么拿 C 的结果当输入，而不是让官方自己从头串起来、只比最后的 logits？道理和第 4 章第一层“拿 C 的输入算”一样：每一层的误差只来自这一层本身，不会累积，所以 64 层每一层都能用和单层一样严的标准。它检查的是：C 的第 i 层用的确实是第 i 层的权重、层的类型没有错位、层与层之间确实是“上一层的输出就是下一层的输入”。

**二、官方自己串起来，贪心解码的 token 必须完全相同。** 第一件事只说明每一层都对，第二件事回答前言里的验收标准：从嵌入开始，官方 float64 自己一层一层算下去，最后选出的 token 是不是和 C 一样。这里不再给 logits 定容差，只看 token。原因是 token 就是我们真正关心的输出，而 logits 的误差已经被第一件事逐层管住了。

**三、官方 BF16 串起来，只报告。**

### 逐行检查贪心解码

C 的贪心解码生成 m 个 token 要做 m 次前向。官方代码要不要也做 m 次？不用，这里用上因果性。

设提示词是 n 个 token，C 生成了 g₁ … g_m。把“提示词加上 g₁ … g_{m−1}”一次性交给官方代码（这就是教师强制），得到 n + m − 1 行 logits。因为模型是因果的，第 n − 1 行只取决于提示词本身，正好是官方生成第一个 token 时看的那一行；第 n 行只取决于提示词加 g₁，如果官方第一步也选了 g₁，这一行就正好是官方生成第二个 token 时看的那一行；依此类推。所以只要检查每一行的 argmax 都等于 C 选的那个 token，就能断定：官方自己做贪心解码，会生成完全相同的 m 个 token。一次前向，代替了 m 次。

C 的工具打印的正是最后一次前向（长度 n + m − 1）的结果，所以第一层 [`tests/model_ref.py`](../tests/model_ref.py) 也按同样的办法检查：第 k 个生成的 token 必须是第 n − 2 + k 行的 argmax。最后一次前向的嵌入要求逐位相同，所以如果 C 在某一步接错了 token，嵌入那一步就对不上。

C 自己的前几次前向结果并没有打印出来，凭什么说最后一次的前几行就等于它们？这正是下面“已知答案”一节要检查的：前缀的 logits 逐位相同。

### 第一名领先多少

只比 token 有一个风险：如果某一步第一名和第二名的分数几乎一样，C 和官方之间正常的舍入差异（10⁻⁶ 量级）就可能让它们选得不一样。这时测试会失败，但并不说明谁错了。

我们的办法是如实报告：每次检查都打印官方 float64 那几行里，第一名最少领先第二名多少。小模型上最小的是 0.05，比 C 与官方 logits 之间的差（10⁻⁶ 到 10⁻⁴）大几百倍以上。如果哪天真遇到了几乎平局的提示词，失败信息会把领先量打印出来，到时再看。

### 小模型上还能直接用官方的整个模型

27B 只能逐层加载，那么“逐层串起来”和官方的整个模型 `Qwen3_5ForCausalLM` 算的是一回事吗？在小模型上可以直接检查：构造官方的整个模型，载入同样的权重，结果和逐层串起来的逐位相同（误差 0）。小模型上还调用官方的 `generate`（transformers 里真正用来生成文本的函数，带缓存）做一次贪心解码，生成的 token 也和 C 完全相同。

## 跑得动吗

**C 端。** 27B 每个 token 约 260 亿次乘加：每层 3.8 亿次左右，64 层，加上输出层 248320 × 5120 ≈ 13 亿次。云端的测试机上，我们最朴素的矩阵乘（每个乘加都在 double 里做，BF16 逐字节拼出来）开着 ASan 是每次乘加约 4 纳秒，用 -O2、不开 ASan 是约 0.8 纳秒。比如从 4 个 token 的提示词生成 8 个，要做 8 次前向，长度从 4 到 11，一共 60 个 token，也就是约 1.6 万亿次乘加：按云端的速度，开着 ASan 要一个多小时，-O2 也要二十分钟左右。目标机器上的实际用时见“在真实权重上验证”一节。

我们的选择：

- 代码不改。不加多线程，不用 SIMD（一条指令同时处理多个数的 CPU 指令），矩阵乘还是第 3 章那个三重循环。这些都是第二卷的事。
- 真实模型的测试 `make test-model-real` 另外用 -O2、不带 ASan 编译一份 `forward` 到 `build/fast`。ASan（地址检查）和 UBSan（未定义行为检查）由 `make test` 在小模型上做，走的是完全相同的代码路径：只是维度小，循环少转几圈。
- 提示词选短的，只生成 8 个 token。

**参考实现。** 第一层是纯 Python，算 27B 的一层要几分钟，64 层要几个小时。所以真实模型上第一层只检查嵌入、最终归一化和最后一行 logits（24.8 万个数，约两分钟），各层内部的每一步第 4 章已经在真实权重上逐步检查过了，层与层之间的衔接由第二层逐层检查。

第二层的官方代码在 float64 下，整个模型要 27B × 8 字节 = 216 GB，目标机器只有 186 GB 内存。所以三件事都逐层做：每次只从 safetensors 里读一层的权重，三种算法（逐层、float64 串联、BF16 串联）都跑完再释放这一层。输出层也是 24.8 万行，转成 float64 要 10 GB，按 16384 行一块分块算。

## 测试本身也要测

和前两章一样，我们故意把代码改坏，看哪一层测试能发现。“两边”指 C 和 `model_ref.py` 改成同一种错误：

| 故意引入的错误 | 第一层（逐步） | 第二层（官方） |
| --- | --- | --- |
| C 把层的顺序弄反（第 i 步用第 63 − i 层的权重） | 失败 | 失败 |
| 两边都把层的顺序弄反 | **通过** | 失败 |
| 两边都漏了最终归一化 | **通过** | 失败 |
| 两边都把嵌入表当成输出层 | **通过** | 失败 |
| C 贪心解码时取了第一行而不是最后一行 | 失败 | 失败 |
| C 的输出层用 float 累加 | 失败 | **通过** |
| C 的位置从 1 开始编号 | 失败 | **通过** |

前几行和第 4 章一样：两边读错成一样，只有官方对拍能发现；精度问题只有逐步对拍能发现。

最后一行值得多说几句。位置从 1 开始编号，官方对拍居然通过了，而且贪心解码的 token 也完全相同。原因在 RoPE（第 3 章）：它把第 p 个位置的 q 和 k 都旋转 p 倍的角度，两个位置的分数只取决于两个角度之差，也就是两个 token 的相对距离。所有位置都加 1，距离不变，注意力的分数在数学上就不变，只有舍入不同。逐步对拍能发现它，是因为 `layer_ref.py` 自己按“位置就是 token 的序号”算 RoPE，C 的 `q_rope` 那一步立刻就对不上。

这说明第二层对拍检查的是“输出对不对”，而不是“每一步是不是照官方的写法做的”。位置从 1 开始在这一章没有任何影响，但到了第 6 章，缓存里存的是旋转之后的 k，如果新 token 的位置和缓存里的位置用了不同的起点，相对距离就错了。所以位置的约定要由第一层守住。

## 如何验证正确

测试的结构和前几章相同：

- [`tests/make_model_fixtures.py`](../tests/make_model_fixtures.py) 生成一个随机小模型：8 层（两组“3 个线性注意力加 1 个全注意力”），宽 64，词表 40，加上输出层。层的配置和权重的生成方式沿用第 4 章的 [`tests/make_layer_fixtures.py`](../tests/make_layer_fixtures.py)，每一层的权重都不同，所以层用错了一定看得出来。
- 用例有 1 个、8 个、70 个 token 的一次前向，以及三个贪心解码：从 1 个 token 生成 8 个，从 8 个生成 6 个，从 62 个生成 6 个（前向的长度从 62 到 67，越过官方分块算法的块长 64）。
- 第一层 `model_ref.py` 只用标准库，每一层的步骤直接用第 4 章 `layer_ref.py` 里的 `layer_plan`：第 i 层的输入是第 i − 1 层的输出。为此把 `layer_ref.py` 的主函数拆成了两半，第 4 章的测试不受影响。
- 第二层 `model_official.py` 需要 torch 和 transformers，没装时打印 SKIP，不算通过。
- 两个不依赖 Python 的已知答案，都来自因果性：8 个 token 的 logits，前 5 行必须与只给前 5 个 token 时**逐位**相同；从 1 个 token 贪心生成 8 个，与“从这个 token 加上生成的前 3 个出发，再生成 5 个”，结果必须相同。C 的每一步都只按 token 的先后顺序算，后面的 token 不会参与前面的任何一次求和，所以这里要求的是逐位相同，而不只是相近。
- 12 个必须被拒绝的输入：输出层复用嵌入表的配置（两处各一个）、层数比权重多、缺少或形状不对的输出层、缺少第 7 层的张量、logits 里有 NaN，以及写坏的命令行参数。

## 在真实权重上验证

```
make test-model-real MODEL=/data/models/Qwen3.8-27B PYTHON=$HOME/venvs/x/bin/python
```

提示词默认是“中国的首都是”，用第 2 章的分词器编码，不套对话模板，让模型直接续写 8 个 token；可以用环境变量 `PROMPT` 和 `GEN` 换。脚本最后把生成的 token 用第 2 章的解码器变回文字打印出来。

我们在目标机器上（32 核，186 GB 内存，Ubuntu 24.04，gcc 13.3）用提交 `d283b44` 跑了一遍，Python 环境里是 torch 2.9.1 和 transformers 5.8.0.dev0。同一台机器上 `make test` 的 166 项快速测试也全部通过。

```

C 端用时 726 秒

ok   真实模型 逐步：64 层，检查了 3 步、350720 个元素，最大误差 0.50 ulp；贪心生成的 8 个 token 都是分数最大的
ok   真实模型 官方：64 层逐层对拍，最大相对误差 1.2e-05；官方 float64 串起 64 层后 logits 与 C 差 1.1e-06；
     贪心解码的 8 个 token 与官方 float64 完全相同（第一名最少领先 3.52e-02）；官方 BF16：logits 差 4.5e-02，8 步中有 8 步选的 token 相同
```

引擎第一次说出了一句话：“中国的首都是”后面，它接的是“北京，而北京位于中国的北方。”这 8 个 token 与官方 float64 自己串起 64 层选出的完全相同。

几个数：

- **用时。** C 端 726 秒，也就是 3 个 token 的提示词生成 8 个，8 次前向一共算了 3 + 4 + … + 10 = 52 个 token，平均每个 token 14 秒，相当于每次乘加约 0.5 纳秒。整个测试（加上两层参考实现）用了 14 分 42 秒，峰值内存约 49 GB，大部分是 mmap 进来的权重。
- **逐层对拍。** 64 层每一层、最终归一化和输出层，最大误差 1.2 × 10⁻⁵（第 18 层），在 2⁻¹² ≈ 2.4 × 10⁻⁴ 以内，留了 20 倍余量。和第 4 章单独测的四层是同一个量级。
- **官方 float64 串起 64 层。** 每一层的输出与 C 最多差 2.2 × 10⁻⁵，到 logits 只差 1.1 × 10⁻⁶，误差没有随层数累积。和小模型上 70 个 token 的用例（2.8 × 10⁻⁴）相比小得多，原因是这里只有 10 个 token，官方分块算法的 float32 累加远没有那么极端（第 4 章“第二层容差一开始定得太紧”）。
- **领先量。** 8 步里第一名最少领先第二名 0.035（logits 的单位，不是相对误差）。C 与官方 float64 的 logits 差是均方根的 10⁻⁶ 倍，离能改变选择还差几个数量级。

**第 4 章留下的问题有了答案。** 官方 BF16 串起 64 层，中间各层的输出离 C 很远：

```
    layers.0.out     官方 float64 串起来差 7.5e-06，官方 BF16 串起来差 3.4e-01
    layers.19.out    官方 float64 串起来差 1.8e-05，官方 BF16 串起来差 1.0e+00
    layers.23.out    官方 float64 串起来差 2.1e-05，官方 BF16 串起来差 1.4e+00
    layers.45.out    官方 float64 串起来差 1.5e-05，官方 BF16 串起来差 9.5e-01
    layers.63.out    官方 float64 串起来差 6.2e-06，官方 BF16 串起来差 2.8e-01
    logits           官方 float64 串起来差 1.1e-06，官方 BF16 串起来差 4.5e-02
```

中间几十层的最大误差超过一个均方根，但到了 logits 只差 4.5%，8 步选的 token 全部相同。误差没有像小模型那样一路翻倍，到后面的层反而变小了。我们的推测是：真实模型的残差流里有少数几个数值特别大的维度，“最大误差除以均方根”被它们主导；而最终归一化和输出层看的是整个向量的方向，个别维度的误差影响有限。这只是推测，没有专门验证。

所以在这一句话上，官方 BF16 和精确计算说的是同一句话，但这只是一个提示词、8 个 token 的结果，不能推广成“BF16 总是选出相同的 token”。小模型上我们已经看到过不同的情况。按 Wei 定的方案，BF16 的结果只记录，标准答案仍是 float64。

## 踩过的坑

**官方的 generate 把 token 0 当成了填充。** 小模型上第一次用官方 `generate` 核对时，从 8 个 token 生成 6 个的用例失败了：官方生成的是 `34, 32, 34, 35, 15, 35`，C 是 `21, 5, 21, 19, 7, 19`，完全不同。可是同一个用例用教师强制检查，C 的每一步都和官方 float64 一致。

两种检查的区别只在于有没有经过 `generate`。查下去发现，这个用例的提示词 `3,17,17,0,39,5,22,8` 里有一个 0，而我们调用 `generate` 时为了不让它报警告，传了 `pad_token_id=0`。`generate` 在没有给出 `attention_mask` 时，会把所有等于 `pad_token_id` 的 token 当成填充（为了凑齐长度而补上的、不该参与计算的 token），在注意力里把它遮掉。模型看到的输入少了一个 token，结果当然不同。显式传一个全 1 的 `attention_mask` 之后，`generate` 的结果与 C 完全相同。

还是参考实现的问题，C 端没有错。这次是教师强制的结果先帮我们排除了 C：两种方式本该等价，只有一种失败，问题就在不同的那部分。
