# 第 1 章 读取权重文件

> 状态：初稿。本章的代码已通过自造测试文件和两个真实模型权重上的对拍，结果见“在真实权重上验证”一节。

## 要解决的问题

一个大模型发布出来，主体就是一组权重：几百到几千个多维数组，每个有名字、元素类型和形状。推理引擎要做的第一件事，是把它们从磁盘上原样读出来。

“原样”两个字是这一章的全部重点。如果某个张量读错了一个字节，或者两个张量的名字对调了，后面的程序不会崩溃，只会算出一个略有不同的结果。所以这一章的验收标准定得很死：

**对文件里的每一个张量，我们读到的名字、类型、形状和全部字节的校验和，必须与一份独立的参考实现完全一致。**

## safetensors 格式

现在的开源模型大多用 safetensors 格式发布权重。它的布局只有三段：

```
偏移 0        8                8+N                    文件末尾
     ┌────────┬────────────────┬──────────────────────┐
     │ N      │ JSON 头        │ 数据区               │
     │ 8 字节 │ N 字节         │ 所有张量的原始字节   │
     └────────┴────────────────┴──────────────────────┘
```

- 开头 8 个字节是一个小端序的 64 位无符号整数 N，表示 JSON 头的长度。
- 接下来 N 个字节是一段 UTF-8 编码的 JSON。
- 剩下的全部是数据区。

JSON 头是一个对象，键是张量的名字，值描述这个张量：

```json
{
  "model.embed.weight": {"dtype": "BF16", "shape": [50, 16], "data_offsets": [0, 1600]},
  "__metadata__": {"format": "pt"}
}
```

`data_offsets` 是 `[起点, 终点)`，相对于数据区的起点而不是文件的起点。`__metadata__` 是一个特殊的键，存放任意的字符串键值对，不是张量。

这个格式没有压缩，数据就是数组在内存里的样子。这意味着我们可以直接把文件映射进内存，让每个张量的指针指向映射区域的内部，一个字节都不用拷贝。

## 实现

代码在 [`src/st.h`](../src/st.h) 和 [`src/st.c`](../src/st.c)。读单个文件的接口只有三个函数：

```c
int  st_open(st_file *f, const char *path, char *err, size_t errcap);
void st_close(st_file *f);
const st_tensor *st_find(const st_file *f, const char *name);
```

`st_open` 做三件事。

**第一，映射文件。** 用 `mmap` 把整个文件只读地映射进地址空间。几十 GB 的文件也是瞬间完成，因为操作系统只在我们真正访问某一页时才去读磁盘。

**第二，读头长度。** 这 8 个字节我们逐字节拼起来，而不是把指针强转成 `uint64_t *` 去读：

```c
for (int i = 7; i >= 0; i--) hlen = hlen << 8 | base[i];
```

这样写不依赖运行机器的字节序，也不会有未对齐访问的问题。

**第三，解析 JSON 头。** 这是代码量最大的部分。我们没有引入 JSON 库，而是写了一个只够用的解析器，大约两百行。它只认识这个格式里会出现的东西：字符串、非负整数、数组和对象；遇到 `__metadata__` 或不认识的字段就整体跳过。

字符串解析是其中唯一有点麻烦的地方。张量的名字是任意的 Unicode 字符串，JSON 允许把字符写成 `\uXXXX` 的转义形式，超出基本平面的字符还会写成两个转义组成的代理对。我们把它们全部解码成 UTF-8，这样同一个名字不管在文件里怎么转义，读出来都是同一串字节。

## 多个分片

大模型的权重不会放在一个文件里。Qwen3.8-27B 拆成了 18 个文件，名字是 `model-00001-of-00018.safetensors` 这样的格式，每个文件都是一个完整的 safetensors，各有各的头。一个张量整个落在某一个分片里，不会跨文件。

对引擎的其他部分来说，分片是不该操心的细节：它只想按名字要一个张量。所以我们在单文件读取器上面加一层 `st_set`：

```c
int  st_set_open(st_set *s, const char *const *paths, size_t n, char *err, size_t errcap);
void st_set_close(st_set *s);
const st_tensor *st_set_find(const st_set *s, const char *name);
```

它逐个打开分片，把所有张量的指针收进一个数组，按名字排序，查找时用二分。这里只多出一条检查：**同一个名字不能出现在两个分片里**。如果出现了，我们无从知道哪一份才是对的，所以直接报错。

## 不信任输入

权重文件是从网上下载的。一个推理引擎如果因为文件里的一个数字写错了就越界读内存，那它离商用还很远。所以读取器对每一个张量都做这些检查，任何一项不满足就报错退出：

| 检查 | 防的是什么 |
| --- | --- |
| 头长度不超过文件大小 | 一上来就越界 |
| `data_offsets` 的起点不大于终点，终点不超过数据区大小 | 张量指针指到映射区域之外 |
| 字节数恰好等于各维度之积乘以元素大小 | 形状和数据对不上 |
| 计算各维度之积时检查乘法溢出 | 用一个巨大的形状让乘积回绕成小数字，骗过上一条检查 |
| `dtype` 必须是已知类型 | 默默把未知类型当成别的类型 |
| 张量名不能重复 | 后一个悄悄覆盖前一个 |
| JSON 头结束后不能有多余内容 | 格式不合规的文件 |

溢出检查那一条值得多说一句。形状 `[2^62, 4]` 的 32 位浮点张量，字节数是 2^62 × 4 × 4 = 2^66，在 64 位整数里回绕后恰好是 0。如果不检查溢出，一个声称自己有 2^64 个元素、实际数据为空的张量就能通过校验。测试里的 `bad_overflow` 就是这个例子。

还有一项检查目前没有做：两个张量的数据区间不应重叠。重叠不会导致越界，所以先不处理，记在这里。

## 如何验证正确

验证靠两份独立的实现互相比对。

- [`tools/st_dump.c`](../tools/st_dump.c) 用我们的读取器打开文件，对每个张量输出一行：校验和、类型、形状、名字。
- [`tests/ref_dump.py`](../tests/ref_dump.py) 用 Python 标准库里的 `json` 和 `mmap` 做同样的事，输出同样的格式。

两者的输出逐字节相同才算通过。校验和用的是 CRC-32，和 zlib、PNG、以太网用的是同一种。C 这边自己实现，查表法十几行；Python 那边直接调用标准库的 `zlib.crc32`。

两份实现互相比对有一个盲区：如果两边错成一样，对拍照样通过。所以测试里还放了一个已知答案：ASCII 字符串 `123456789` 的 CRC-32 是 `cbf43926`，这是这个算法公认的测试向量，C 这边必须算出这个值。

测试文件由 [`tests/make_fixtures.py`](../tests/make_fixtures.py) 生成，分两类：

- **合法文件**。包含各种类型、零维标量、有一个维度为 0 的空张量，以及一个名字里带引号、反斜杠、换行、中文和表情符号的张量。同样的内容还会用全转义的 JSON 再写一份，两份文件读出来必须一样。
- **分片**。把合法文件里的张量交替拆进两个分片，合并读出的结果必须与单文件完全相同，而且与传入分片的顺序无关。另有两个反例：同一个张量名出现在两个分片里，以及某个分片不存在，都必须被拒绝。
- **损坏文件**，共 11 个，每个故意违反上面表格里的一条规则。读取器必须明确拒绝它们：退出码为 1 并给出错误信息，既不能崩溃，也不能当作成功。

测试程序在编译时打开了 AddressSanitizer 和 UndefinedBehaviorSanitizer，所以越界访问、内存泄漏和未定义行为也会让测试失败。

```
$ make test
ok   good.safetensors
ok   good_escaped.safetensors
ok   CRC-32 测试向量
ok   两个分片合并
ok   跨分片重名：错误：张量名在多个分片中重复：a
ok   bad_dtype.safetensors：错误：张量 t：不支持的 dtype "F128"
ok   bad_dup.safetensors：错误：张量名重复：t
...
```

## 在真实权重上验证

自造的测试文件只有几 KB。读取器真正要面对的是几十 GB 的文件，所以我们在目标机器上（两张 RTX PRO 6000 Blackwell，Ryzen 9 9950X，Ubuntu 24.04，gcc 13.3，Python 3.12）用两个真实模型各跑了一遍，提交为 `df91385`。每个模型的全部分片一次合并读入，每个张量的全部字节都参与校验。

| 模型 | 分片数 | 总大小 | 张量数 | 类型 | 结果 |
| --- | --- | --- | --- | --- | --- |
| Qwen3-4B-Instruct-2507 | 3 | 约 8 GB | 398 | 全部 BF16 | 两份输出完全一致 |
| Qwen3.8-27B | 18 | 约 52 GiB | 1199 | 全部 BF16 | 两份输出完全一致 |

真实文件也让我们第一次看到目标模型的样子。Qwen3.8-27B 的 1199 个张量按名字前缀分成四组：

| 前缀 | 张量数 | 是什么 |
| --- | --- | --- |
| `model.language_model.` | 850 | 语言模型主体 |
| `model.visual.` | 333 | 图像编码器 |
| `mtp.` | 15 | 多 token 预测模块 |
| `lm_head.` | 1 | 输出层 |

几个有代表性的张量：

```
model.language_model.embed_tokens.weight                      BF16 [248320,5120]
model.language_model.layers.0.linear_attn.in_proj_qkv.weight  BF16 [10240,5120]
model.language_model.layers.3.self_attn.q_proj.weight         BF16 [12288,5120]
model.language_model.layers.3.self_attn.k_proj.weight         BF16 [1024,5120]
model.language_model.layers.0.mlp.gate_proj.weight            BF16 [17408,5120]
lm_head.weight                                                BF16 [248320,5120]
```

从这里能直接读出几件事：词表大小是 248320，隐藏维度是 5120；第 0 层用的是 `linear_attn`，第 3 层用的是 `self_attn`，两种注意力层混合排布。这些都会在后面的章节里用到。

我们还顺手拿一个 FP8 量化模型（Qwen3.8-Flash-Next-FP8）的分片试了一下，读取器按设计拒绝了它：

```
错误：张量 model.language_model.layers.2.mlp.experts.0.down_proj.weight：不支持的 dtype "F8_E4M3"
```

`F8_E4M3` 是 8 位浮点类型。现在不认识它是对的，等第 10 章做量化时再加。

## 踩过的坑

**参考实现慢到没法用。** 第一版的校验和是 FNV-1a 哈希，选它是因为两种语言里都只要三行。在测试文件上一切正常，一到真实权重上就出了问题：

```
分片                     大小      C（带 ASan）   Python（纯 Python 逐字节哈希）
Qwen3-4B  00001          3.96 GB   3.00 s         191.2 s
Qwen3.8-27B 00005        2.10 GB   1.50 s          95.8 s
```

Python 每 GB 要将近 50 秒，27B 的 18 个分片全算一遍要四十多分钟。第一次验证时我们只好对一个分片做完整校验，其余 17 个只比较名字、类型和形状，留下了一个缺口。

改成 CRC-32 之后，Python 这边调用的是 zlib 里用 C 写的实现，情况反了过来：

```
模型          C（-O1，带 ASan）   C（-O2）   Python（zlib.crc32）
Qwen3-4B      11.4 s              -          0.93 s
Qwen3.8-27B   78.1 s              77.5 s     5.8 s
```

现在是我们自己的 C 代码慢了 13 倍，而且开不开优化几乎没有区别。原因在算法本身：查表法每处理一个字节都要等上一个字节的结果，是一条很长的依赖链，编译器无法并行化；zlib 用的是处理器的专用指令，一次处理很多字节。

这正好是“先正确，后性能”的一个小例子。78 秒完全够用，而十几行的查表法一眼就能看出对不对，所以现在不动它。

这件事的教训是：**参考实现也要能在真实数据规模上跑得动**，否则对拍就只能做一部分，而没被覆盖的那部分恰恰是最容易出问题的。

**排序规则。** 为了让两份输出能逐行比较，两边都要把张量按名字排序。C 这边用 `strcmp`，比较的是 UTF-8 字节；Python 的 `sorted` 默认比较的是 Unicode 码点。这两种顺序在绝大多数情况下相同，但对拍不能依赖“绝大多数情况”，所以 Python 这边显式地按 `name.encode("utf-8")` 排序。

**名字里的换行。** 测试里有一个张量的名字包含换行符。如果原样打印，一个张量会占两行，逐行比对就乱了。两边都改成把控制字符按 `\uXXXX` 输出。
